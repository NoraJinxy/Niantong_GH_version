# 数据库前后一致性审计

文档生成时间：2026-05-24 +08:00

## 背景

对 `elys_project/database/`、`elys_project/backend/app/models/`、`elys_project/backend/alembic/`、`elys_project/deploy/deploy.sh`、`elys_project/frontend/elys-web/src/` 以及阿里云远程库（`8.135.40.150` 入口 / `8.135.57.42` 计算）做一次端到端的数据库一致性审计，验证：

1. **schema ↔ migrations 累加结果**：基线 `schema/00_current_schema.sql` 与依次执行 `migrations/0001 → 0006` 之后的状态是否一致。
2. **migrations ↔ 部署入口**：`init.sql` / `init_core.sql` 与 `app/services/schema_compat.py` 是否把全部 migrations 都引入了。
3. **ORM ↔ schema**：`backend/app/models/*` 的字段、外键、关系是否与 schema 当前形态对得上。
4. **业务代码 ↔ schema**：backend routers/pipeline、frontend `src/` 是否还引用了已删除的表/字段。
5. **远程库实际状态 ↔ schema**：阿里云计算服务器（`8.135.57.42`）上 PostgreSQL 的真实表结构、约束、Alembic 状态是否与代码仓库期望一致。

审计依据：
- `elys_project/database/schema/00_current_schema.sql`（713 行 baseline DDL）
- `elys_project/database/migrations/20260521_0001 … 20260524_0006`（6 个 SQL）
- `elys_project/database/init.sql`、`init_core.sql`
- `elys_project/backend/app/models/{user,role,project,derived_dataset}.py`
- `elys_project/backend/app/services/schema_compat.py`
- `elys_project/backend/alembic/versions/20260521_0001 … 20260524_0006`（6 个 .py）
- `elys_project/deploy/deploy.sh`
- 阿里云 `8.135.57.42` 上 `psql -d elys` 实测（`\dt`、`pg_constraint`、`alembic_version`）

## 一、问题清单（按优先级排序）

下面每条都标注：**位置**、**实际情况**、**建议处理方式**、**状态**，便于逐条讨论。

### 🔴 高优先级——影响线上库一致性

#### 问题 ① `init.sql` / `init_core.sql` 漏引入 0005 / 0006 两个 migration

- **位置**：
  - `elys_project/database/init.sql`
  - `elys_project/database/init_core.sql`
- **原文**：两个文件的 `\ir` 列表只到 `0004_derived_datasets.sql`，后续 `0005_drop_dataset_derivatives.sql`（删僵尸表）和 `0006_normalize_cancelled_to_canceled.sql`（拼写规范化）都未引入。
- **实际情况**：
  - `deploy.sh:388-399` 每次部署都跑 `init.sql`，所以这两条迁移从未通过部署链路落到远程库
  - 远程 `8.135.57.42` 实测结果（2026-05-24）：
    - `dataset_derivatives` 表仍存在（0 行数据，但表结构占着）——本应被 `0005` DROP
    - `pipeline_runs.status` / `async_tasks.status` / `task_events.status` 的 CHECK 约束**同时允许 `canceled` 和 `cancelled` 两种拼写**——本应被 `0006` 收紧到只允许 `canceled`
- **建议**：
  1. 在 `init.sql` 和 `init_core.sql` 的 `\ir` 列表里追加：
     ```
     \ir migrations/20260524_0005_drop_dataset_derivatives.sql
     \ir migrations/20260524_0006_normalize_cancelled_to_canceled.sql
     ```
  2. 立刻到 `8.135.57.42` 手工补一次：
     ```
     psql -d elys -v ON_ERROR_STOP=1 -f migrations/20260524_0005_drop_dataset_derivatives.sql
     psql -d elys -v ON_ERROR_STOP=1 -f migrations/20260524_0006_normalize_cancelled_to_canceled.sql
     ```
- **状态**：⏳ 待修复

#### 问题 ② `schema_compat.py` 兼容迁移列表停留在 0003

- **位置**：`elys_project/backend/app/services/schema_compat.py:13-17`
- **原文**：
  ```python
  COMPAT_SQL_PATHS = (
      DATABASE_DIR / "migrations" / "20260521_0001_compat_v1_to_current.sql",
      DATABASE_DIR / "migrations" / "20260521_0002_file_management_min_fields.sql",
      DATABASE_DIR / "migrations" / "20260521_0003_pipeline_run_input_file_snapshot.sql",
  )
  ```
- **实际情况**：
  - `RUN_SCHEMA_COMPAT_ON_STARTUP=true` 时该函数被调用，但只能跑到 0003
  - 0004（derived_datasets）/ 0005（drop 僵尸表）/ 0006（拼写规范化）全部不在列
  - 这个开关现在等于"半残"，启用了也补不齐
- **建议**：
  - 把 0004、0005、0006 也追加到 `COMPAT_SQL_PATHS`
  - 或者：既然项目计划走 Alembic，直接把 `schema_compat.py` 标记 deprecated，并在文档里强制走 `alembic upgrade head`
- **状态**：⏳ 待修复

---

#### 问题 ③ Alembic 框架已写完 0001-0006，但远程从未启用

- **位置**：
  - `elys_project/backend/alembic/versions/`（已有 6 个版本文件，对应 6 个 SQL migration）
  - `elys_project/deploy/deploy.sh:388-399`（部署链路只跑 `init.sql`）
- **实际情况**：
  - 远程 `8.135.57.42` 实测：`SELECT * FROM alembic_version` → `ERROR: relation "alembic_version" does not exist`
  - 意味着 Alembic 在生产/测试环境从未跑过，仅作为代码仓库里的"摆设"
  - 风险：如果未来某天有人想 `alembic upgrade head`，它会从 0001 开始重放，而库已经是 0004 状态——必定冲突
- **建议**（二选一）：
  - **方案 A：完全启用 Alembic**：在 `deploy.sh` 里改成 `alembic upgrade head`，初次启用前先 `alembic stamp <current_head>` 把远程库的当前状态打标；并把 `init.sql` 改为仅 schema + seed，不再叠加 migration
  - **方案 B：不启用 Alembic**：把 `alembic/` 目录删掉或在 README 里明确写"Alembic 未启用，仅做参考"，避免误导
- **状态**：⏳ 待决策

### 🟡 中优先级——影响开发体验，但不影响运行

#### 问题 ④ `init.sql` 中 `0001` 会先创建被 `0004` 立刻删掉的旧表

- **位置**：`elys_project/database/migrations/20260521_0001_compat_v1_to_current.sql:586-755`
- **原文**：0001 中 `CREATE TABLE IF NOT EXISTS pipeline_artifacts / analysis_results / dataset_derivatives`
- **实际情况**：
  - 新库初始化路径：schema 不创建这三表 → 0001 反而 CREATE 出来 → 0004 又 DROP `pipeline_artifacts` 和 `analysis_results` → 0005 才 DROP `dataset_derivatives`
  - 结果是绕一圈又删掉，浪费 I/O，新库初始化日志里会刷一堆"创建-删除"
  - 当前没出错，因为都是幂等操作，但对运维不友好
- **建议**：
  - 长期：把 0001 改名为 "legacy v1 → MVP" 兼容迁移，明确说明它只适合升级老库，新库初始化应走 schema + seeds，不再叠加 0001
  - 短期：在 `init.sql` 注释里加一句"0001 兼容迁移仅为升级 v1 旧库设计，新库可跳过，但目前为简化保留"
- **状态**：⏳ 待讨论

#### 问题 ⑤ `recordings_view` / `recording_versions_view` 被 ORM 当成普通表

- **位置**：
  - schema：`schema/00_current_schema.sql:340-395`（定义为 VIEW）
  - ORM：`backend/app/models/project.py:424-474`（`Recording` / `RecordingVersion` 类用 `__tablename__` 指向 view）
- **实际情况**：
  - SQLAlchemy 把 view 当成只读表来映射没问题，但 `Recording.id` 标了 `primary_key=True` 仅是为了让 ORM 能识别主键——这是俗成约定，不算错
  - 当前正常工作；提一下是为了让后续维护者知道"recordings 不是真表"
- **建议**：
  - 在 `Recording`/`RecordingVersion` 类的 docstring 里加一行"映射的是 `recordings_view` 视图，由 `datasets` + `dataset_uploads` 投影而来，只读"
- **状态**：⏳ 可选

### 🟢 低优先级——已正确处理，仅做记录

#### ⑥ ORM 字段、外键、JSONB 默认值与 schema 全部对齐

- 5 个 model 文件（`user.py` / `role.py` / `project.py` / `derived_dataset.py` / `__init__.py`）共 24 个表，每个列都对得上 schema
- `metadata` 字段统一通过 `Column("metadata", JSONB, ...)` 重命名为 `metadata_json`，绕开 SQLAlchemy 保留字
- `study_settings` 的 4 个 JSONB 默认值（`default_dataset_filter` / `run_policy` / `artifact_retention_policy` / `storage_policy`）与 schema 完全一致

#### ⑦ ORM 中的外键已全部从旧表迁到 derived_datasets

- `PipelineRunInput.upstream_dataset_id → derived_datasets`（原 `upstream_artifact_id → pipeline_artifacts`）
- `PipelineRunDependency.upstream_dataset_id → derived_datasets`（同上）
- `DatasetFileDerivation.derived_dataset_id → derived_datasets`（原 `artifact_id → pipeline_artifacts`）
- 没有任何 ORM 类还指向 `pipeline_artifacts` / `analysis_results` / `dataset_derivatives`

#### ⑧ 业务代码无残留旧表引用

- `backend/app/`（routers + pipeline + services）搜索 `pipeline_artifacts|analysis_results|dataset_derivatives` 仅在以下位置出现，全部合规：
  - `app/pipeline/output.py` 注释（"旧实现写入 analysis_results 表（已删除）"）
  - `app/models/derived_dataset.py` docstring（说明 derived_datasets 是替代）
  - `alembic/versions/0004` 和 `0005`（迁移文件本身）
- `frontend/elys-web/src/` 搜索同样字符串：仅 [PipelinePage.vue:5273](../../elys_project/frontend/elys-web/src/views/PipelinePage.vue) 保留 `artifact_id` 作为 fallback key 兜底（`item.derived_dataset_id || item.upstream_dataset_id || item.artifact_id || ...`），属于合理的旧字段回落
- `dist/`、`node_modules/` 里的命中都是编译产物或第三方依赖，无需处理

#### ⑨ `cancelled` → `canceled` 拼写已统一

- backend `app/` 源码搜不到 `cancelled`，只在 `alembic/versions/20260524_0006_normalize_cancelled_to_canceled.py` 里出现（正常——这是规范化迁移本身）
- frontend `src/` 源码也搜不到 `cancelled`，命中都集中在 `dist/` 编译产物和 `node_modules/`（Vue/Router 等依赖的英式拼写无需关心）
