### 任务 1 · 🆕 新增 `dataset_assets.disclosure_level`（可见粒度轴）

- **改哪里**：
  - `03_datasets.sql` `dataset_assets` 建表块（紧跟 `visibility` 列后）新增列。
  - `models/study.py` `class DatasetAsset` 同步加 `disclosure_level = Column(String(16), nullable=False, default="metadata")`。
- **字段定义**：
  ```sql
  disclosure_level VARCHAR(16) NOT NULL DEFAULT 'metadata'
      CHECK (disclosure_level IN ('metadata', 'data'));
  COMMENT ON COLUMN dataset_assets.disclosure_level IS
      '可见粒度（设计 §4.3）：metadata=他人仅见描述/统计，data=他人可下载/使用原始数据与 FIF。默认 metadata 保守。仅对 shared/public 有意义；private 时该值不影响（owner+团队恒可见数据）。';
  ```
- **口径**（写进 COMMENT，避免后端 / 前端理解漂移）：
  - `disclosure_level` 是**数据闸**（能不能下载数据）；`visibility` 是**元数据闸**（能不能看见它存在 / 描述）。两者正交，见任务 3 口径表。
  - 默认 `metadata`（设计 F-10：保守安全，owner 主动开放才到 `data`）。
- **验收点**：DROP 重建后 `\d dataset_assets` 含 `disclosure_level`，默认值 `metadata`，非法值（如 `full`）被 CHECK 拒绝；ORM 查询返回该字段。
- **风险**：低。新增非空列带默认值，DROP 重建无存量数据需回填。唯一注意：前端 / 后端读该字段前必须先部署本次 schema，否则查不到列 → 本轮与后端轨道**同批部署**。

### 任务 2 · 🆕 描述结构化落点（`dataset_versions.metadata_json.description{}`）

- **改哪里**：**不加物理列**——设计 §4.6 第 5 点明确用 `dataset_versions.metadata_json.description` 结构化存储（JSONB 内嵌）。DB 侧只需：
  - 在 `03_datasets.sql` `dataset_versions.metadata_json` 列的 COMMENT 里写明约定结构（让后续接手者 / 后端知道 key 形状）。
  - `models/study.py` 不变（`metadata_json` 已是 JSONB）。
- **约定结构**（写进 COMMENT + 本计划，作为后端读写契约）：
  ```jsonc
  // dataset_versions.metadata_json
  {
    "description": {
      "abstract": "",   // 摘要（必填项，发布前可改 / 发布后只读）
      "methods":  "",   // 采集方法
      "usage":    "",   // 使用说明（Usage Notes）
      "ethics":   ""    // 伦理
    }
    // ... 其他版本级元数据（license / citation 等发布后字段也走这里，归后端轨道定义）
  }
  ```
- **口径**：
  - 描述**归版本**（`dataset_versions`）不归资产（`dataset_assets.description`）——因为"发布后描述冻结、引用稳定"要绑到不可变的版本快照上（设计 §4.6 规则 1）。
  - 现 `dataset_assets.description`（单一 TEXT，`study.py:203`）语义降级为"资产级一句话简介 / 显示名补充"，**不承载结构化科学描述**。是否保留由后端轨道决定；DB 侧不删（删它属后端/前端展示决策，避免越界），但在 COMMENT 标注"结构化科学描述见 dataset_versions.metadata_json.description"。
  - 可编辑性（发布前可改、发布后只读）是**后端 API 层强制**，DB 不加触发器（JSONB 子键无法用 CHECK 优雅约束可变性），DB 侧只定结构。
- **验收点**：COMMENT 落地；后端按此 key 读写；一条 published 版本的 `metadata_json->'description'->>'abstract'` 可正常 SQL 取出。
- **风险**：中。JSONB 无 schema 强约束，key 拼写错（如 `usage_notes` vs `usage`）只能靠后端契约 + 测试兜底。**缓解**：本计划把四个 key 钉死为 `abstract/methods/usage/ethics`，后端轨道与前端轨道引用本节为唯一事实源。

### 任务 3 · 🚧 厘清两轴口径 + 🆕 新增"未发布 ⟹ private"约束

- **背景**：设计 §4.4 铁律 1「发布前只能私有」、铁律 2「发布 ≠ 公开」。当前 DB **无此约束**，且 `dataset_lifecycle.py:352-356` 在发布时强行 `private→shared`（与"发布≠公开"**直接冲突**）。DB 轨道负责：① 把两轴口径写进 COMMENT 当事实源；② 加约束保证"未发布必私有"。后端轨道负责删掉那段 private→shared 逻辑（本计划在"依赖契约"里点名）。
- **两轴口径**（钉死，写进 schema COMMENT）：

  | 轴 | 列 | 取值 | 管什么 | 何时可变 |
  |---|---|---|---|---|
  | 发布状态 | `dataset_versions.state` | `draft`(=未发布) / `published` / `withdraw_requested` / `withdrawn` | 不可变性 / 生命周期 | 状态机驱动 |
  | 可见性 | `dataset_assets.visibility` | `private` / `shared` / `public` | 谁能看见"它存在 / 描述"（元数据闸） | 仅 published 后可改；draft 锁 private |
  | 可见粒度 | `dataset_assets.disclosure_level` | `metadata` / `data` | 谁能"拿到数据"（数据闸） | 仅 published 后有意义；private 时不约束 |

  > 注：`state` 在**版本**层、`visibility`/`disclosure_level` 在**资产**层。约束需跨表表达（见下）。

- **约束实现方案**（跨表，三选一，按推荐度排序）：
  - **方案 A（推荐，MVP）· service 层强制 + 不加 DB 触发器**：DB 仅靠 COMMENT 记口径，"未发布⟹private"由后端 `dataset_lifecycle` / `PATCH /dataset-assets` 强制（draft 想设 shared/public → 403）。理由：跨表 CHECK 在 Postgres 不被支持（CHECK 不能引用其他表），触发器是唯一 DB 手段但调试期增加复杂度且与 §4.5「service 强制」一致。
  - **方案 B（加固，可选）· 跨表触发器**：`dataset_versions` UPDATE/INSERT 与 `dataset_assets` UPDATE 上各挂一个 `BEFORE` 触发器，校验"存在任一非 published 版本时该 asset.visibility 必须 = private"。**缺点**：asset:version 是 1:N，"draft⟹private"的精确语义（是"当前版本"还是"任一版本"）依赖 `current_version_id`，触发器逻辑易写歪；调试期不建议。
  - **方案 C（最强但越界）· 把 visibility 下放到 version 层**：让可见性也归版本，则可在 `dataset_versions` 单表加 `CHECK (state='draft' ⟹ visibility='private')`。**不采纳**：设计 §4.5 明确 visibility 在 asset 层、与 state 解耦，改表结构会动后端 / 前端大面，超出本次范围。
- **采纳**：**方案 A**。DB 任务 = 在 `dataset_assets.visibility` 与 `dataset_versions.state` 的 COMMENT 中写明铁律与"约束由 service 强制"，并在本计划"依赖契约"里把强制点交给后端轨道。
- **改哪里**：
  - `03_datasets.sql`：更新 `dataset_assets.visibility` COMMENT（删旧"发布时自动 private→shared"表述，改为"draft 锁 private；published 后可在 private/shared/public 间切换，发布本身不改 visibility"）；新增 `disclosure_level` COMMENT（见任务 1）。
  - `03_datasets.sql`：更新 `dataset_versions.state` COMMENT，补"draft=未发布、强制 private"。
- **验收点**：schema COMMENT 与设计 §4.4 一致；后端实现后，draft 资产 `PATCH visibility=public` 返回 403；publish 不再改 visibility（这两条验收实际由后端轨道执行，DB 轨道只验 COMMENT + CHECK 取值集合正确）。
- **风险**：中。方案 A 把约束交给 service，DB 层无硬保证——若后端漏判，可能出现"draft 但 shared"的脏状态。**缓解**：① COMMENT 明确写"DB 不强制、service 必须强制"；② 后端轨道加单测覆盖 draft 改可见性的 403 路径；③ 二期若上 `dataset_members` 真授权再评估补触发器。

### 任务 5 · 🆕 新增 `dataset_addenda` 表（发布后补充信息 + 审核）

- **背景**：设计 §4.6 规则 2 + F-12：发布后描述只读，仅可**追加补充信息**（勘误 / 补充说明 / 新被试说明），且**走管理员审核**后才对外可见。设计 §4.6「各层增量」给了两个落点选项（独立表 `dataset_addenda` 或 `metadata_json.addenda[]`）。
- **决策：用独立表 `dataset_addenda`**（不用 `metadata_json.addenda[]`）：
  - 理由：补充信息有**审核状态机**（pending→approved/rejected）+ **审计字段**（submitted_by / reviewed_by / reviewed_at），需被独立查询（"待审核队列"）、需外键到 users，JSONB 数组难以加索引 / 难以做审核工作流。独立表与现有 `dataset_withdrawal_requests`（审核表，`03_datasets.sql:261`）风格一致。
- **改哪里**：`03_datasets.sql` 新增建表块（放在 `dataset_withdrawal_requests` 之后、索引区之前）；`models/study.py` 新增 `class DatasetAddendum`。
- **表定义**：
  ```sql
  CREATE TABLE IF NOT EXISTS dataset_addenda (
      id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
      dataset_version_id  UUID NOT NULL REFERENCES dataset_versions(id) ON DELETE CASCADE,
      content             TEXT NOT NULL,                       -- 追加的补充正文（勘误 / 补充说明）
      submitted_by        UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
      submitted_at        TIMESTAMP NOT NULL DEFAULT NOW(),
      status              VARCHAR(16) NOT NULL DEFAULT 'pending'
                              CHECK (status IN ('pending', 'approved', 'rejected')),
      reviewed_by         UUID REFERENCES users(id) ON DELETE SET NULL,
      reviewed_at         TIMESTAMP,
      review_notes        TEXT                                 -- 审核意见（拒绝原因等）
  );
  COMMENT ON TABLE dataset_addenda IS
      '发布后补充信息（设计 §4.6 / F-12）。已发布版本描述只读，补充信息只追加且走管理员审核；status=approved 后才对外可见，审核动作写 audit_events。';
  COMMENT ON COLUMN dataset_addenda.dataset_version_id IS '挂到具体已发布版本（绑版本不绑资产，保证补充信息随引用稳定）。';
  COMMENT ON COLUMN dataset_addenda.status IS 'pending=待审 / approved=已公开 / rejected=驳回。仅 approved 对外可见。';
  ```
- **配套索引**（放索引区）：
  ```sql
  CREATE INDEX IF NOT EXISTS idx_dataset_addenda_version ON dataset_addenda(dataset_version_id);
  CREATE INDEX IF NOT EXISTS idx_dataset_addenda_status ON dataset_addenda(status);     -- 待审队列
  CREATE INDEX IF NOT EXISTS idx_dataset_addenda_submitted_by ON dataset_addenda(submitted_by);
  ```
- **口径**：
  - addenda 挂 `dataset_version_id`（已发布版本）——只有 published 版本才能加补充（draft 直接改描述即可）。DB 不强制"仅 published 可加"（跨表语义），由后端 `POST .../addenda` 校验 version.state=published。
  - 审核通过的可见性 = 后端查询时 `WHERE status='approved'`；DB 不做行级可见性。
- **验收点**：DROP 重建后 `\d dataset_addenda` 结构正确；`status` CHECK 拒非法值；待审队列查询 `SELECT * FROM dataset_addenda WHERE status='pending'` 走索引；ORM `DatasetAddendum` 可增删查。
- **风险**：低。纯新增表 + 审计流，不碰文件、不碰现有表结构（设计 §4.6「📁 文件存储：零影响」）。唯一依赖：`users` 表（`01_auth.sql`，加载序在 03 之前，外键成立）。

### 任务 6 · 🚧 releases 冻结清单落点确认（DB 侧定边界）

- **背景**：设计 §12.3 + §4.5「唯一关联：发布仍写 `releases/v{semver}.json` 冻结清单」。这是**磁盘文件**（`datasets/{asset}/releases/v{semver}.json`），靠 append-only 保证不可变，**零复制**。
- **DB 轨道决策：releases 清单不入库、不新建表**。
  - 理由：设计 §12.3 明确清单是磁盘 JSON；DB 侧发布元数据已有 `dataset_versions`（state/content_hash/version_doi/published_at/published_by）承载，清单只是磁盘冻结边界，重复入库违反单一事实源。
