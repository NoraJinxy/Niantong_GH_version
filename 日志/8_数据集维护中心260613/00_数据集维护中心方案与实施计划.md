## 0. 一句话目标

把 datasets 详情页从「**只读查看 + 发布 / 共享**」扩成「**看得清、管得动**」的维护中心:**三层导航**(数据集窄轨 / 被试树 / 记录主表)+ **记录抽屉**(两套维数 + 可编辑元数据)+ **体检提醒**,补上现页面缺的「**理 / 改 / 补**」。

---

## 1. 背景与设计纲领

- **受众 = 医生 / 心理学 / 神经科学家,不是工程师**(memory `elys-design-persona`)。纲领:让脑电数据处理**显得简单、fancy,而非复杂**。
- 推论:**用领域语言**(被试 / 会话 / 任务 / run),不用文件系统语言(路径 / 扩展名 / sha256);工程细节折叠;首屏只回答「这是什么数据 / 哪儿要处理」。
- **现页面的结构性缺口**:把「**进**(导入)/ **发**(版本 · DOI)/ **享**(授权 · 公开)」做得不错,但「**理 / 改 / 补**」——日常维护的大头——几乎是空的。本方案补的就是这缺掉的半壁。

| 现成数据 | 来源 | 用途 |
|---|---|---|

### 2.3 存储两层(详见 doc 4,本文只引用,不重定义)

- `sourcedata/original_uploads/upload-XXX/` = 原始上传,**只写不改、永久保留、owner-only、含 PII**。
- `BIDSdata/` = canonical FIF,BIDS 命名,分析就绪,**可从 sourcedata 重建**。
- `raw_bids` = 纯 DB 逻辑索引,无物理文件。
- file_role:`original_upload`(sourcedata)+ `fif`(BIDSdata)+ sidecar + provenance。
- **关键:全部写操作(改名 / 移动 / 删除 / 重生成 / 重试)目前后端均不存在**——这是本方案的主投入,也是「看 / 改」工作量分水岭的由来。

## 4. 目标设计

### 4.1 三层导航(布局骨架)

```
┌─────────────────────────────────────────────────────────────┐
│ [数据集名 ▾]  私有          [发布][共享][⋯]   ← 数据集级管理 │  顶栏
├─────────────────────────────────────────────────────────────┤
│ ⚠ 1 待生成 FIF · 1 导入失败 · 1 质控待查         [去修复 →]  │  体检条
├───────┬──────────┬──────────────────────────────┬───────────┤
│ 我的  │ 被试树   │ 采集记录主表                 │ 记录抽屉  │
│ 数据集│ sub-01 ⚠│ 会话 | 任务 | run | 状态     │ 元数据    │
│ ▸ A ● │ sub-02   │ ses-01  rest    1   ·        │ 两套维数  │
│ ▸ B ● │ sub-03 ✗│ ses-01  oddball 1   待生成[生]│ 操作      │
│ + 新建│          │ ...                          │           │
└───────┴──────────┴──────────────────────────────┴───────────┘
   L0        L1              L2(主)                  L2(详情)
```

- **L0 远左 · 数据集窄轨**:列出 owner 的数据集 + 体检灯,点选**切换**;窄、可收。
- **L1 中左 · 被试 / 记录树**:被试 →(会话,仅多会话时显)→ 记录;每个节点挂健康灯。它是**导航 / 筛选器**。
- **L2 主区**:默认密集**记录主表**(4.2);点单条 → 右侧滑出**抽屉**(4.3)。

### 4.2 主表:列只承载「会变」的(列设计原则)

- 按被试**分组**;列 = `会话 | 任务 | run | 单一状态列 | ⋯`。
- **原则:列只配给「会变」的信息。**
  - 原始数据 = 每条记录必有(它就是上传本体)→ 恒 ✓ → **不设列**,降进抽屉。
  - 标准 FIF = 默认自动生成、极少缺 → **不设独立列**,并进「状态」列,仅 *待生成 / 失败* 时亮一颗可点钮。
  - 会话 / run = 有的数据集多、有的只一个 → **给列,但整个数据集只有单一取值时自动隐藏**(无会话的数据集不显会话列)。
  - 结果:多数行**安静**(被试 / 会话 / 任务 / run + 空状态),**出事的行才跳色**——平时清爽、出事显眼。
- `表格 / 矩阵` 切换:矩阵 = **被试 × 任务覆盖网格**(绿齐 / 灰缺 / 黄有问题),一眼看穿缺口。
- 多选 → 浮出**批量条**(重生成 FIF / 标记 / 删除)。

### 4.3 记录抽屉:两套维数 + 可编辑元数据

- **可编辑元数据**:任务 / 会话 / run(改这些 = 改 BIDS 实体,见 §6 Q3,阻塞)。
- **两套维数**:`sourcedata 原始(.bdf,只读永久)` → 标准化 → `BIDSdata 标准 FIF`(缺则「生成」钮)。两套维数从主表列里退到这里——在表里它俩恒绿无信息量,在抽屉里配上「生成」才有用。
- **操作**:重命名(实为改实体)/ 标记排除 / 删除记录。

### 4.4 体检 / 提醒(原方案 C,镶进 A)

三级提醒,哪儿有问题在哪儿修:① 顶部**体检条**(汇总 + 去修复)② 树**健康灯** ③ 缺失 / 失败处**就地小钮**(生成 · 重试)。

### 4.5 数据集级管理 + 窄轨(回答「左栏 or 顶栏」)

**两者都要,但分工**:窄轨负责「在我的数据集之间游走 + 一眼组合体检」;顶栏负责「管好脚下这一个」(发布 / 共享 / 重命名 / 删除 / 切换 ▾)。互不挤占。

### 4.6 两条克制线

- **不给下载链接**:维护工具非分发站。要导出走另一入口(BIDSdata 按需导出,doc 4 §2.1),不在维护页放下载钮。
- **「移动 / 改被试号」先放灰**:本质是改 BIDS 四元组归属,阻塞于唯一性未决(§6 Q3)。其余删除 / 标记 / 重生成 / 重试不受影响。

### 6.1 坏数据重采集 / 替换(Q1.5 展开)

场景:某被试一条记录坏了(信号差 / 伪迹),重做实验补齐。同一件事两个角度:

- **sourcedata 角度 = 只多一次上传**。原 `upload-001/` 留着(只进不出,Q1.1),新数据进 `upload-002/`。原始层永不删,保可追溯。
- **BIDS 角度 = 把槽位「换」掉,但不是物理删除,是版本替换**:doc 4 §2.5 的 `recording_versions`(status `current` / `replaced`)正为此设计。重采集 →(upload-002)→ 生成新 FIF → **新版本设 `current`,旧版本设 `replaced`(文件留痕、不删)**。BIDS 四元组(sub/ses/task/run)不变,永远解析到 `current`。比真删好:旧版本跑过的分析仍可重现。

三条结论写进设计:

1. **新增动作「重新采集 / 替换」**(记录抽屉内),区别于「删除记录」与「重生成 FIF(同源重转)」——它是「换源 + 重转 + 版本切换」。
2. **不阻塞于 Q3**。替换**不改四元组**(同槽换数据),不踩唯一性,落 **M3**;只有「改任务名 / 被试号」(换槽位)才踩 Q3、留 M4。
3. **FIF 不手动重组**。FIF 是派生层、按实体命名;用户通过「替换源 / 改实体」这些**逻辑操作**驱动,物理 FIF 跟着走;旧版本在抽屉「历史 / 技术」折叠区可见(可回滚、可重现)。
4. **替换 vs 补齐分清**:坏了重做 = 同槽**替换**(版本 swap);缺某任务 = 新槽**新记录**(正常新上传)。UI 两个不同入口。

> 以下 Q1–Q8 详述为决策背景,口径以上表为准。

### Q1 sourcedata 交互(本轮重点,用户点名)

维护页是「面向 recording(逻辑)」的,而 sourcedata 是「面向 upload 批次(物理、永久)」的,两者并不一一对应。要敲定的边界:

1. **能不能在 UI 删 sourcedata?** sourcedata 定位「只写不改、永久、重建/追溯的唯一源」。倾向:**抽屉里 sourcedata 原始那行,删除 / 重命名一律禁用(置灰 + 提示「原始存档不可改」)**;可删的只有 BIDSdata(可重建)。待确认。
2. **upload 批次 vs recording 视角。** 一次导入(`upload-001/`)可产出**多条** recording(多被试 / 多任务)。维护页是 recording-centric;是否还需要一个「**按导入批次**」视角(看某次上传带进来哪些记录、**整批回滚**一次错误导入)?倾向:主线 recording-centric,导入批次作为「导入」tab 的历史/回滚入口,不混进维护主表。待确认。
3. **「删除记录」时 sourcedata 何去何从。** 删一条 recording = 删它的 BIDSdata(可重建)+ recordings 行;但它的 sourcedata 原件是永久层。三个选项:(a) 保留 sourcedata 原件(只解绑 recording);(b) 进 `trash/`(doc 4 已有 TRASH_STORAGE_ROOT);(c) owner 二次确认才物理清。倾向 (a)/(b),**默认不物理删原件**。待拍板。
4. **共享物理文件。** 若将来支持「一个 .bdf 切成多条 recording」,多条 recording 共享同一 sourcedata 物理文件 → 删一条 recording **不能**删物理文件。删除逻辑需按「最后一个引用」判定。先记下,当前是否一对一需对账代码。
5. **抽屉「生成标准 FIF」的源。** 明确文案:从 sourcedata 重新标准化,不是凭空生成;sourcedata 缺失(理论上不该)时该钮禁用。

### Q2 删除语义(文件级 vs 记录级)

- 文件级删除危险:删了 FIF 的某个 sidecar(events.tsv / channels.tsv)会破坏 BIDS 完整性。倾向:**UI 只暴露「记录级删除」与「重生成」,不开放散删单个 sidecar**;散文件操作留给「技术 / 高级」折叠区(若需要)。待确认粒度。

### Q3 改 BIDS 实体 = 四元组唯一性(已知阻塞)

- 改 task / ses / run / subject,或「移动到其他被试」,本质都是改 recording 的四元组归属。而**「重命名」在 BIDS 里不是自由文本**——文件名由实体派生,所以「重命名」=「改实体」=「改四元组」。
- 这踩 memory `pending-design-decisions` 的**四元组唯一性(Study / Asset 级)未决**:改实体可能撞唯一约束。**先放灰,等那条拍板再点亮 M4**。

### Q4 被试人口学模型

### Q5 质控处置语义
