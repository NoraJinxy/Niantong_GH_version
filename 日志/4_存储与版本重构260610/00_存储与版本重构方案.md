> 整理日期：2026-06-10。本文档把近期关于「上传数据怎么存、版本怎么发、文件怎么选、PII 怎么管」的设计讨论收敛成一份可执行方案。

## 0. 一句话目标

把数据集的磁盘结构从「**意图三层、实际混乱**」收敛成「**两层物理 + 一套 DB 逻辑索引 + 清单式版本**」，顺带补上发布时的 PII 强制脱敏，并把 LoadData 的选择模型从「前端塌缩成固定 ID 列表」改成「过滤器持久化 + 执行时展开」。

### 1.2 版本 / 发布现状（**重磅：物理版本未实现**）

发布逻辑 `publish_dataset_version`（[`dataset_lifecycle.py:358-414`](../../elys_project/backend/app/services/dataset_lifecycle.py)）的全部副作用：

- `version.state = 'published'`
- `version.version_label` 从 `'working'` 改名为 SemVer（如 `1.0.0`）
- 写 `published_at` / `published_by` / `version_doi`
- `asset.current_version_id` 指向该版本；首发初始化 `concept_doi`
- 写审计事件（含脱敏/伦理/版权声明留痕）

**没有任何物理文件动作**——不复制、不重命名目录、不更新 `version.storage_uri`（它仍指向 `.../versions/working`）。

**自相矛盾点**：丢弃草稿 `discard_draft_version`（[`dataset_versions.py:288-295`](../../elys_project/backend/app/routers/dataset_versions.py)）却调用 `shutil.rmtree(dataset_version_root(asset_id, label))`，即假设 `versions/{label}/` 物理目录真实存在。也就是说：**路径构造层按「物理版本目录」设计，发布层按「纯 DB 状态」实现，两边对不上。**

结论：**当前根本没有可用的物理版本管理**。这反而给重构留足了空间——没有历史包袱要兼容（调试期，无真实数据）。

发布合规关口（[`dataset_lifecycle.py:318-326`](../../elys_project/backend/app/services/dataset_lifecycle.py) + [`schemas/dataset_lifecycle.py:26-69`](../../elys_project/backend/app/schemas/dataset_lifecycle.py)）：发布时强制三项——`deidentified_confirmed`（勾选）、`ethics_statement`、`license_statement`（非空文本），缺一 422。**纯自我声明，无技术核验**。

## 2. 目标设计

### 2.1 两层物理目录（核心简化）

```
datasets/{asset_id}/
├── sourcedata/
│   └── original_uploads/
│       ├── upload-001/        第一次导入（物理文件，原始格式原名）
│       └── upload-002/        重传批次
└── BIDSdata/                  canonical FIF，BIDS 实体命名，分析就绪层（物理文件）
    └── sub-001/ses-01/eeg/
        ├── sub-001_ses-01_task-rest_run-01_eeg.fif
        ├── sub-001_ses-01_task-rest_run-01_eeg.json
        ├── sub-001_ses-01_task-rest_run-01_channels.tsv
        └── sub-001_ses-01_task-rest_run-01_events.tsv
```

三个语义层各归其位：

| 层 | 物理 | 角色 | 对应旧结构 |
|---|---|---|---|
| `sourcedata/` | ✅ 物理文件 | 原始存档，只写不改，永久保留 | 不变 |
| `BIDSdata/` | ✅ 物理文件 | canonical FIF + BIDS 命名，Pipeline 实际消费 | 取代 `derivatives/elys-canonical-fif/`，**去掉 task/run/upload 子目录** |
| ~~`raw_bids/`~~ | ❌ 删除物理层 | 降为 DB 逻辑索引 | 见 2.2 |
| `derivatives/`（科学产物） | —— | **不在数据集里** | 已在 `studies/{study_id}/outputs/`，研究域，不动 |

要点：
- **`derivatives/` 不属于数据集**。BIDS 原意的 derivatives = 科学处理产物（ICA、epoch、功率谱、连接矩阵），在 ELYS 属于研究项的 StudyOutput，存 `studies/{study_id}/outputs/`，与数据集解耦——这个现状是对的，不改。canonical FIF 是「格式归一化」不是「科学衍生」，所以从 `derivatives/` 挪到独立的 `BIDSdata/` 层，命名更诚实。
- **BIDSdata 是「BIDS 结构」不是「BIDS 校验通过」**。FIF 不是 BIDS 认可的 EEG raw 扩展名，所以 `BIDSdata/` 是平台内部的 BIDS 风格 canonical 层，validator 不会绿。真要对外交付标准 BIDS 包，走「按需导出」（从 sourcedata + sidecar 物化），不常驻磁盘。

### 2.2 raw_bids 降为纯逻辑索引

`raw_bids/` 不再作为目录概念。它原本想回答的「给我 sub-001/ses-01/task-rest 的原始文件」，由两处现成数据回答：

- **BIDS 实体映射** → 查 `recordings` 表（`bids_subject_id` + `session` + `task` + `run` 四字段齐全）。
- **原始文件位置** → 查 `dataset_files` 里 `file_role='original_upload'` 行的 `storage_uri`。

`dataset_files` 中 `raw_bids_data` / `raw_bids_*` 这些 file_role 行可以**删除**（它们只是把 recordings 的信息冗余存了一遍）。保留 `original_upload` 与 `fif`（见下）两类即可。

### 2.3 文件角色精简

| 保留 | 含义 |
|---|---|
| `original_upload` | sourcedata 原始上传文件 |
| `fif` | BIDSdata 的 canonical FIF（取代 `canonical_fif`） |
| `fif_eeg_json` / `fif_channels` / `fif_events` | FIF 同目录 sidecar |
| `fif_provenance` | 转换溯源 JSON |

删除：`raw_bids_data` / `raw_bids_eeg_json` / `raw_bids_channels` / `raw_bids_events` / `raw_source` / `sidecar`（旧兼容角色）。

### 2.4 版本管理：清单式 + 逻辑链接（取代物理快照）

**原则：物理文件只存一份，版本是「哪些文件属于这个版本」的清单，发布是 DB 操作 + 目录重命名，不复制大文件。**

发布流程（用户拟定的「重命名 + 逻辑链接」模型）：

```
未发布：随便改 BIDSdata/，文件随意增删改
   │ 发布 v1.0.0
   ▼
① mv BIDSdata/ → ver1.0.0/        （OS 重命名，瞬间，不复制）
② mkdir 新的空 BIDSdata/
③ DB：v1.0.0 的文件 storage_uri 指向 ver1.0.0/，冻结成清单
   │ 继续编辑：改了 sub-002 的 trigger，重新转 FIF
   ▼
新 FIF 物理写进 BIDSdata/sub-002/...，sub-001/sub-003 没动
   │ 发布 v1.0.1
   ▼
④ 改过的文件（sub-002）→ 物理落到 ver1.0.1/，新 dataset_files 行
⑤ 没改的文件（sub-001/003）→ 清单「逻辑链接」回 ver1.0.0/ 的物理文件
```

**实现方式：DB 清单表（不用 OS 符号链接）**

```sql
CREATE TABLE dataset_version_files (
    dataset_version_id  UUID NOT NULL REFERENCES dataset_versions(id) ON DELETE CASCADE,
    dataset_file_id     UUID NOT NULL REFERENCES dataset_files(id)    ON DELETE RESTRICT,
    PRIMARY KEY (dataset_version_id, dataset_file_id)
);
```

- 一个物理文件 = 一条 `dataset_files` 行（`storage_uri` 指向它真实所在的版本目录）。
- 「版本包含哪些文件」= 查 `dataset_version_files` 清单。
- v1.0.1 的清单 = （sub-002 的新行）+（指回 sub-001/003 旧行的清单条目）。**「逻辑链接」= 清单行复用旧 file_id，无需文件系统 symlink。**
- `dataset_files.dataset_version_id` 语义改为「该物理文件诞生于哪个版本目录」（物理归属），版本成员关系交给清单表。

为什么不用 OS symlink：ELYS 用户不直接 SFTP 翻服务器，文件访问全走平台 API（wiki `2-70` §4：无 Nginx 直通）。DB 清单实现最简单、不依赖文件系统特性、不怕跨盘。

### 2.5 同路径不同内容（trigger 修改）天然解决

「同一条 recording，改了 trigger，重转 FIF，BIDS 路径完全一样」这个难题，在版本目录模型下自动化解：

- v1.0.0 的 FIF 物理在 `ver1.0.0/sub-002/.../eeg.fif`（旧 trigger）
- v1.0.1 的 FIF 物理在 `ver1.0.1/sub-002/.../eeg.fif`（新 trigger）
- 两行 `dataset_files` 的 `logical_path` 相同（同一 BIDS 路径），但 `storage_uri` 指向不同版本目录的不同物理文件
- 用 v1.0.0 重跑 Pipeline → 查 v1.0.0 清单 → 拿到旧 file_id → 读旧物理文件 → **可重现**

底层由 `recording_versions`（`status: current/replaced`）记录「同一条 recording 的多次上传/重转」，新版本产生新 `recording_version`，旧版本 `replaced` 但文件保留。

### 2.6 PII 强制脱敏（补合规缺口）

把「自我声明制」升级为「技术执行 + 声明留痕」双保险。**两件事、两个阶段、互补，谁也不替代谁：**

| 阶段 | 干什么 | 性质 |
|---|---|---|
| **导入**（转 FIF 时） | `raw.anonymize()` 擦文件头 `subject_info` + 日期 | **技术地板**——机器保证，不靠人自觉 |
| **发布**（转公开前） | 勾「已脱敏」+ 伦理/版权声明（保留现状） | **人工天花板**——用户担责，覆盖机器抓不到的（事件标签/标注里的人名、知情同意范围） |

**为什么在导入时擦，不在发布时**：canonical FIF 是整个工作期分析都在读的工作副本，发布前 pipeline 已反复消费它。若拖到发布才擦，整个分析期 PII 在 FIF 里裸奔、输出/预览图可能带出去。所以 **FIF 必须「出生即干净」**。

技术脱敏细节（导入阶段）：
- **转 FIF 时强制 `raw.anonymize()`**（在 `generate_canonical_fif` 的 `raw.save()` 之前）：清空 `raw.info["subject_info"]`、采集日期清零（默认；如需相对时序可改 date-shift）。`BIDSdata/` 里的 FIF **天生无文件头 PII**。
- 转换后**校验** `raw.info["subject_info"]` 已空，否则拒绝导入并提示。
- `sourcedata/` 原始文件**不擦**，仍含完整 PII，定位为「事实源 / 存档，限 owner、永不对外」——擦了就失去重导/追溯能力。对外只发 BIDSdata/ 导出包。

**身份映射不会因脱敏丢失**（澄清常见误解）：`anonymize()` 擦的是文件头里设备塞进去的真名，**不动 `sub-001` 这个假名标签**。「哪个 FIF 是 sub-001」永远在（文件名 + `recordings.bids_subject_id`）。要查「sub-001 = 哪个真人」，三处都行：

1. **你自己的被试登记表**（BIDS 标准做法，存系统外安全处）——这层 `sub-001↔张三` 对照从上传时就由你建立（导入界面要求你指定 subject），从一开始就在你手里，不在 FIF 里。
2. **ELYS owner-only 身份表**（可选，将来要录真名时单独建限权表，绝不进数据集主链路）。
3. **`sourcedata/` 原件**（owner 专属，头里真名/真日期完整）。

去标识的**本意**就是让分析系统不持有真名：脱敏数据（sub-001）进流水线，真名对照锁在 owner 侧。所以「owner 始终查得到、分析链路始终碰不到」是目标而非副作用。

### 2.7 LoadData 选择模型

**这一节只管「怎么挑文件」**，与后台「怎么跑」无关（执行粒度见文末说明，是引擎的事）。

选择 = 按 BIDS 维度筛 `recordings`。四个维度各自可「全部」或「多选」：

| 维度 | 取值 |
|---|---|
| 被试 subject | 全部 / 多选 / 单选 |
| session | 全部 / 多选 / 单选 |
| 任务 task | 全部 / 多选 / 单选 |
| run | 全部 / 多选 / 单选 |

两个典型场景直接落到维度组合：

| 场景 | filter 设置 | 选出 |
|---|---|---|
| 一个被试多个条件 | `subjects=[sub-001]`, `tasks=[rest, motor, visual]` | 这个人的 3 条 |
| 所有被试一个条件 | `subjects=all`, `tasks=[rest]` | 所有人的 rest，N 条 |

selector 两种持久化模式（解决现状「前端塌缩成固定 ID」的问题）：

```jsonc
// filter 模式（默认）：存「规则」，数据集后续加了新被试自动纳入，跑时才展开
{ "selection_mode": "filter", "dataset_asset_id": "uuid",
  "filters": { "subjects": "all", "sessions": "all", "tasks": ["task-rest"], "runs": "all" } }
// explicit 模式：存「固定 recording 列表」，锁定重现某次分析，不随数据集变化
{ "selection_mode": "explicit", "dataset_asset_id": "uuid",
  "recording_ids": ["uuid-1", "uuid-2"] }
```

前端：filter 维度控件 + **实时匹配预览**（选的时候就显示「当前匹配 12 条」+ 前 20 条列表）+ **快捷场景按钮**（一键设成「单被试多条件」「全被试单条件」）+ 模式切换（动态 filter / 锁定 explicit）。**保存时按所选模式存，filter 不再塌缩成 explicit ID 列表**。

> **执行粒度（逐条 vs 整批）不是选择问题，不在 LoadData 暴露给用户。** 由引擎按节点类型自动判断：滤波 / ICA 等天生逐条（每条 recording 独立 Job，并行、失败隔离）；组平均 / 跨被试统计等聚合节点天生整批（一次拿全体）。聚合类节点本身 P2 再做。

### 2.8 发布与转公开：审核挪到「转公开」这一步（Q1 定稿）

**核心原则：发布 ≠ 曝光。** 系统已有两条正交轴——发布态（unpublished→published→withdrawn）× 可见范围（private→shared→public）。PII/伦理/版权的真实暴露只发生在进入 `public`（全网可搜）那一刻，不在 `published`（冻结+铸DOI）那一刻。所以审核装在「转公开」，不装在「发布」。

```
                      可见范围 visibility →
发布态 ↓      private          shared            public
unpublished   草稿(编辑中)      —                 —
published     有DOI·仅自己      有DOI·可邀好友看    有DOI·全网可搜 ← 唯一需审核的转换
```

**发布（unpublished → published）= 完全自助（A）**
- 即时冻结 + 铸 DOI，可见范围保持 private/shared，**无管理员审核**。
- 发布的意义与可见性无关，买到三样：① 不可变冻结（`working`→`v1.0.0`，任何人改不动）；② 永久 DOI（论文可引，私有也铸、解析到受限落地页）；③ 可被他人挂载引用（仅已发布版本能被别的研究项挂载、被执行项锁为稳定依赖）。这三样私有状态下就成立。
- 保留的关口：导入已强制脱敏（§2.6）+ 发布时自我声明（勾「已脱敏」+伦理+版权，进审计）。受众有限（owner + 受邀好友），这两道够。

**转公开（shared → public）= 先审后开（B）**
- `shared → public` 需管理员批准；批准前数据集是「已发布 + 可邀请」，能私下传 DOI 链接，但**不进平台搜索、不对全网开放**。批准后才真正 public。
- 为什么预审而非事后：public 是**不可逆曝光**（别人下载、搜索引擎收录），「先公开再撤」对 PII 为时已晚；`published` 可撤回还有救，`public` 泼出去收不回。
- **调试期默认 auto-approve**：审核钩子建好，但无管理员策略时自动通过——上线随时能开人工审，调试期不添堵。

实现照抄现成的撤回审核那套（`dataset_withdrawal_requests` + admin 队列 + `AdminWithdrawalsPage.vue`），加一张镜像的 `dataset_publicization_requests` 表即可（见 §3）。

### Q1 决策说明（发布 / 转公开）

定稿走「**发布自助 + 转公开预审**」混合（详见 §2.8）。被否的两个纯方案及理由：
- **纯 A 先发后审**（审核 publish 步）：publish 不曝光，事后审挡不住已铸 DOI 的 PII 风险，又给非曝光步骤添阻力 → 否。
- **纯 B 发布前待审核**（审核 publish 步）：gate 错了对象（DOI 铸号不是曝光风险源），同样给非曝光步骤添阻力 → 否。
- 二者都把审核装在「发布」，但本系统 **publish ≠ expose**，审核应装在唯一真实曝光的「转公开」步。记忆 [[todo-publish-review-workflow]] 已更新为定稿。
