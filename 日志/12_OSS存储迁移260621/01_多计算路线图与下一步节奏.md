# OSS 迁移 · 下一程：通往「多计算服务器」的路线图与节奏

> 整理日期：2026-06-23。承接 [`00_OSS存储迁移改造清单.md`](00_OSS存储迁移改造清单.md)。00 那篇是「上 OSS」的总清单；本篇回答一个具体问题——**A/B 阶段 + ACTIVE_SET 都落地之后，离「真·多计算服务器」还差什么、按什么节奏走、现在该不该上第二台。**
>
> 事实源口径：P0 = 当前代码（分支 `feat/figure`）；状态判断以代码为准。本篇是**路线 + 节奏**，不改代码；动手时按惯例补 wiki `9-00` / `9-0x`。
>
> 背景术语（第一次出现先铺垫，读者也含非全栈成员）：
> - **多计算服务器（横向扩计算 / scale-out）**：同一套部署里挂**多台**计算服务器，共享同一份数据 + 同一个任务队列，把「跑流程」的活分摊到多台机器扛吞吐。
> - **无状态计算节点（stateless compute）**：一台计算机本地磁盘上不存「别人也需要、却只有它有」的东西——持久数据全在共享存储（OSS）+ 共享数据库里。无状态才能随便复制 / 加机器 / 挂掉重来。
> - **broker（消息中间件，这里是 Redis）**：Celery 用它当「任务队列」。多台 worker 要分担同一批活，必须连**同一个** broker 才能从同一个队列抢任务。

---

## 0. 当前位置（你在地图的哪儿）

一句话：**「多计算总开关」的存储那一半已经合上（OSS + ACTIVE_SET），但计算那一半——共享 DB/broker + 计算节点脱本地 + 部署扇出到多台——还没动。**

```
现在的真实拓扑（单计算服务器全家桶）：

  浏览器/脚本 ─登录/列表(轻API)─→ 入口服(瘦 2C2G·3M)
  浏览器/脚本 ─上传/跑流程/看图─→ 计算服(8C16G·100M) ┐
                                    ├ FastAPI(uvicorn)
                                    ├ PostgreSQL      │ 全都挤在
                                    ├ Redis(broker)   │ 这一台
                                    ├ Celery worker   │
                                    └ 数据 ← 现在落 OSS（A/B 已接），元数据面仍读本地副本
```

存储已经是共享的（OSS）；但 DB、broker、worker 还全挤在同一台计算机上，且部署只认这一台。所以现在加第二台计算机，它**连不进**这套状态。

---

## 1. 关键澄清：ACTIVE_SET ≠ 多计算服务器

这两件事是**正交的两根轴**，别混：

| | ACTIVE_SET（已做） | 多计算服务器（本篇主题） |
|---|---|---|
| 解决什么 | 在**多套**(入口+计算+桶)资源之间**切换** | 一套里挂**多台**计算机**并行** |
| 一套里有几台计算机 | 始终**一台** | **多台** |
| 怎么用 | 改 `aliyun-test.env` 的 `ACTIVE_SET=setA\|setB` 一行 | 需 deploy 扇出 + 共享 DB/broker（见 §3） |
| 类比 | 切换「用哪台机器」 | 「同时用好几台机器」 |

所以：**你现在能一行切 setA/setB，但每套里还是单机。** 走向多计算是另一程，下面是它的依赖链。

---

## 2. 已经做完了什么（2026-06-23）

存储平面的「多计算总开关」三步已落地（详见 memory `deploy_active_set_switching` 与 wiki `9-02`）：

- **A 阶段**：`StorageService` 加字节后端（local/oss 双实现，默认 local 一键回退）；流水线**读**（`engine/io.py` → `materialize_reference`）、**写**（`pipeline/study_output_store.py` → `_persist_to_oss`）、**导入**（`routers/dataset_imports.py` 单一咽喉上传）三向接 OSS。真机端到端验通（上传→转 FIF→读→跑流程→产物全落 OSS）。
- **B 阶段**：观察/波形等**非流水线读路径**（`resolve_study_output_path`、`_raw_path_from_data_info`）改走 `materialize`，为多机解耦——这些读不再依赖「恰好留在本地的副本」。
- **ACTIVE_SET**：部署资源（双服务器 + OSS 桶）一行切换；11 个读取方加向后兼容解析。合并 `9233f22` + 补漏 `b3319ef`。

**关键缺口（多机前置）**：**元数据面读取仍读本地副本**——LoadData 取通道名、质控（QA）、文件浏览器这类「只要文件头/元信息」的路径，还是直接 open 本地文件，没走 StorageService。单机无碍；上第二台会崩（它没有这些本地文件）。这就是 §3 的第 ① 步。

## 3. 多计算的闸门 = 共享状态（依赖链）

第二台计算机能加入的前提：**它和第一台共享一切、且自己不依赖任何本地独有文件。** 按依赖顺序，有四步闸门，每步解锁下一步：

```
① 读路径彻底脱本地  →  ② 中心化 DB+Redis  →  ③ 部署扇出到 N 台  →  ④ 拆队列 + 多 worker
  (元数据入库/materialize)   (从计算机盒拆出来)      (deploy 读 IP 列表)     (上传/流程分队列)
       │                          │                       │                      │
  没做完→第二台一读           DB/Redis 还在计算机       deploy_remote 现在        现在单队列/2槽/
  通道名·QA·文件浏览          盒上，第二台连不进         只对一台计算机             一台机=真卡顿根源
  就崩(本地无此文件)          (memory 估 ~1 天)        (ACTIVE_SET 是切单套,
                                                       非一套多机)
```

### ① 读路径彻底脱本地（元数据入库 / materialize）
- **现状**：流水线读写已 OSS（A/B），但元数据面（通道名/QA/文件浏览）仍 open 本地。
- **要做**：把通道名、采样率、时长等元数据**写进 DB**（拿元数据不再下整文件），或这些读路径也走 `materialize`。
- **双重收益**：① 拆掉第二台的本地依赖；② 顺带治「**MNE 惰性读被 OSS 吃掉**」——`preload=False` 本想只读文件头，但 OSS 没有 `seek()`，只能把整文件拉到 scratch 才能读，元数据访问从「读几 KB 头」退化成「下载整个几百 MB」。元数据入库后，列表/概览不再触发整文件下载（这也是你现在就感觉到的加载慢 + N+1 的一部分）。

### ② 中心化 DB + Redis（broker）
- **现状**：PostgreSQL + Redis 与 worker 同机（计算服全家桶）。
- **要做**：拆到独立 DB 盒（2C2G 够，全走私网），两台计算机都连它。这是**结构性前提**——共享 broker 后多台 worker 才能从同一队列抢任务、共享 DB 才能看到同一份元数据。
- **工时**：memory `deployment-architecture-scaling` 步骤 3 估 **~1 天·零应用改动**，难点全在运维（PG `listen`/`pg_hba` 远程认证、Redis `requirepass`、安全组只放行内网）。

### ③ 部署扇出到 N 台
- **现状**：`deploy/deploy_remote.ps1` 只对**一台** `COMPUTE_SERVER_IP` 部署（ACTIVE_SET 也是「切单套」，不是「一套多机」）。
- **要做**：profile 把计算机 IP 改成**列表**，`deploy_remote` 循环扇出到 N 台；每台只装 worker（DB/broker/入口都在别处）。
- 复用已有：ACTIVE_SET 的解析骨架可扩成「一套里多台」；`buy_ecs`/`release_ecs` 批量化。

### ④ 拆 Celery 队列 + 多 worker
- **现状**：上传与跑流程**共用同一队列 / 2 槽 / 一台机**（memory `shared_queue_bottleneck`），上传一忙就把跑流程的槽占了 = 假卡顿。
- **要做**：上传一条队列、跑流程一条队列；多台 worker 各认队列。共享 broker（②）后这步直接复用，且**单机时就值得做**——它治的是你现在就疼的卡顿。

---

## 4. 推荐节奏

| 时机 | 做什么 | 为什么 |
|---|---|---|
| **现在**（无悔，单机就回本、又在多机路上） | ① 元数据入库 / 读路径收尾　④ 拆 Celery 队列 + 恢复改异步 | ① 治惰性读慢 + N+1（**现在就疼**）且拆本地依赖；④ 治单队列卡顿（**现在就疼**）且多机直接复用 |
| **触发条件满足再做**（见 §6） | ② DB+Redis 拆盒（~1 天）→ ③ 买第二台 + 部署扇出 | 纯为吞吐，无负载时收益为零 |
| **现在别做** | 别为「先有」就买第二台；别先搞 STS 直传 / scratch LRU 等纯运维优化 | 按量实例白烧钱；没并发就没收益 |

**一句话**：多计算的价值是「扛吞吐」。你现在没吞吐压力，所以**别急着加机器**。把「元数据入库 + 拆队列」这两件**现在就疼、又恰好是多机前提**的事做了，等真有负载，再拆 DB 盒 + 上第二台，那时几乎水到渠成。

---

## 5. 为什么现在别上第二台（把账算清）

- **经济账**：计算服是阿里云按量实例（memory `project_infra`：每次部署 IP 都变）。第二台空转 = 纯烧钱，调试期没真实数据、没并发用户，吞吐根本用不上。
- **工程账**：在 ①②③ 没做完前硬上第二台，它一读元数据就崩（本地无文件）、连不进 broker（在第一台上）、deploy 也扇不到它——加了等于没加，还多一台要维护。
- **正确的「先有」是把闸门修好**：①+④ 做完，单机本身更快更稳；②③ 是「按一个按钮就能扩」的待命状态。等负载真来，几天内拉起第二台，而不是现在养着。

---

## 6. 触发条件与「到那一步该验什么」

**什么信号 = 该上多计算了：**
- 单台计算机的 worker 长期跑满（concurrency 提到内存上限仍排队），且**批量/并发**是真实需求（多人同时跑、大批量数据集）——不是偶发卡顿（那是 ④ 队列问题，先用 ④ 解）。
- 单机加内存/加核（先把 8C16G 的核用满，见 wiki `9-02` 的 `WORKER_CONCURRENCY` 可配 + Resample 优化）已到顶，仍不够。

**真上多机时，验收要确认（无状态闭环）：**
1. 第二台**不**依赖任何本地文件：断开/重建 scratch 后，跑流程仍能从 OSS materialize 成功。
2. 两台 worker 连同一 broker，任务在两台间真分摊（看 Celery 各 worker 的 task 计数）。
3. 任一台挂掉，在跑的任务可被另一台/重试接走（取消/重试语义见 memory `failure_recovery_playbook`）。
4. 产物落 OSS 后，从**另一台**计算机能立即读到（共享存储一致性）。
