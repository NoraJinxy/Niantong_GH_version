## 2. 先肯定做对了什么（重构时勿误伤）

| 优点 | 位置 | 为什么是对的 |
|---|---|---|
| 后端四层分层 | `routers/ → services/ → models/ → schemas/` | 关注点分离，业务逻辑多数已在 service 层 |
| service 层 flush-only | 如 `services/study_locks.py` | 只 `flush` 不 `commit`，把事务边界让给上层——`get_db` 兜底后正是该推广的范式 |
| 节点注册表模式 | `pipeline/registry.py` + `nodes/*.json` | 能力清单放数据里、不写死代码 |
| 任务队列 | Celery + Redis | 长耗时 EEG 计算不卡 HTTP 请求 |
| Execution 不可变快照 | `pipeline_executions` + 输入/输出索引 | 科研可复现的命根子 |
| router 共享层 | `routers/_pipeline_shared.py` | 拆分时把跨子领域 helper 收一处，避免循环 import |
| API client 单飞刷新 | 前端 `api/client.ts` | 并发 401 共享一次 token 刷新 |
| 前端 composable 拆分 | `composables/pipeline/`、`composables/datasets/` | 上帝组件按职责切片，AI 协作友好 |

## 5. 明确不做（YAGNI）

当前规模 = 单人 + AI 代理、调试期、用户数≈0。下列现在做是另一种债：

- **拆 Tasks + Executions**（pipelines.py 剩余核心）：两者通过 `retry_async_task → retry_pipeline_execution` 循环 import 血肉相连，且 cancel/retry/inline 执行逻辑共享一大堆 helper。强拆引入的**循环 import 本地验不出**（compileall/pyflakes 都不执行 import，只有部署才崩），等于拿部署赌；它们本就是内聚的执行引擎核心。**保留在 pipelines.py 是健康终点，不是没拆完。**
- **微服务**：解决"几百人改一个仓库互踩"的组织问题，本项目没有；单体 + 分层是正确形态。
- **Airflow / Prefect**：自研 dispatcher + Celery 对 8 个 EEG 节点合理，工作流是产品核心应自己握着。
- **Kubernetes / 全面容器化**：双服务器 + systemd 够用。
- **追求测试覆盖率指标**：按被咬补测，不刷数字。
