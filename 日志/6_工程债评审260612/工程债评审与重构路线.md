## 2. 先肯定做对了什么（重构时勿误伤）

| 优点 | 位置 | 为什么对 |
|---|---|---|
| 后端四层分层 | `routers/ → services/ → models/ → schemas/` | 关注点分离 |
| service 层 flush-only | 如 `services/study_locks.py` | 事务边界让给上层，get_db 兜底后正是该推广的范式 |
| 节点注册表模式 | `pipeline/registry.py` + `nodes/*.json` | 能力清单放数据里 |
| Execution 不可变快照 | `pipeline_executions` + 输入/输出索引 | 科研可复现命根子 |
| router 共享层 | `routers/_pipeline_shared.py` | 拆分时收跨子领域 helper，避免循环 import（拆 datasets.py 照搬） |
| 前端 composable 拆分 | `composables/pipeline/`、`composables/datasets/` | 上帝组件按职责切片，AI 协作友好 |

## 4. `datasets.py` 拆分时机分析（v4 新增 · ✅ 2026-06-13 已据此执行）

`datasets.py` 是剩余最大债，套路与刚拆完的 `pipelines.py` 完全一致（按子领域拆 + `_dataset_shared.py` 共享层 + pyflakes 验漏 import）。**关键是和「维护中心」（日志/8）的时机咬合**：

- 维护中心 **M1 看层完全不碰后端**（纯现成数据重排）；**M2–M4 才往 `datasets.py` 加 recordings 写接口**（`regenerate-fif` / `retry` / `PATCH recordings` / `DELETE recordings` + 批量版）。
- 维护中心方案 **2026-06-13 刚定稿、后端尚未动工**（文档明写“只给方案、不改代码”）。
- **结论：现在是拆 `datasets.py` 的黄金窗口。** 趁后端没人改先拆成清晰子文件，维护中心接下来的写接口直接落到干净的 `recording_router`，而非堆进 3451 行怪物。**拆它不是和维护中心抢，是给它铺路。** 错过窗口（接口加进去后再拆）成本翻倍。
- 前提：拆的过程需要一个「并行会话不同时改 `datasets.py` 后端」的**轻量窗口**（远比 filter-repo 容易——只是移动代码 + 提交，不重写历史）。

**天然子领域**（现有 router 划分，即拆分边界）：`asset_router`（资产）/ `recording_router`（采集记录）/ `mount_router`（挂载）/ `file_router`（文件浏览）/ 导入。拆法：建 `routers/_dataset_shared.py` 收跨子领域 helper（study 守卫 / 404-getter / 响应转换）+ 按 router 拆 4–5 个文件。

## 7. 不做（YAGNI）

当前规模 = 单人 + AI 代理、调试期、用户数≈0。下列现在做是另一种债：

- **拆 Tasks+Executions**（pipelines.py 剩余核心）：`retry_async_task→retry_pipeline_execution` 循环 import 血肉相连，强拆引入的循环 import 本地验不出（compileall/pyflakes 不执行 import）；它们本就是内聚执行引擎核心，**保留是健康终点**。
- **微服务 / Airflow / K8s**：解决的组织/规模问题本项目没有；单体 + 分层 + 自研 dispatcher + Celery + 双服务器 systemd 是正确形态。
- **追求测试覆盖率指标**：按被咬补测，不刷数字。
