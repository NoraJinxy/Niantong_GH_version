## 1. 总体结论

当前实现已经完成了很多“数据库概念层”的准备，例如：

1. 有 `dataset_assets` 表表达平台级 Dataset 资产。
2. 有 `study_dataset_mounts` 表表达 Study 对 Dataset 的挂载。
3. 有 `dataset_files` 表记录 raw source、canonical FIF、sidecar 文件。
4. 有 `pipeline_run_inputs` 冻结 Run 输入快照。
5. 有 `pipeline_artifacts.storage_uri`、`sha256`、`retention_status` 等输出追溯字段。
6. 有 `async_tasks` / `task_events` 支撑 Pipeline Run 异步执行。
7. 有 `study_locks` 支撑 Pipeline Run 运行锁。

但当前文件管理系统仍然是旧架构主导：

```text
/mnt/elys_data/projects/{project_id}/
  source_uploads/
  fifdata/
  upload_staging/
  pipeline_runs/{run_id}/nodes/{node_id}/
  bids_exports/
```

目标方案要求的是：

```text
/mnt/elys_data/storage/
  datasets/{dataset_asset_id}/versions/{version}/
    sourcedata/original_uploads/
    raw_bids/
    derivatives/elys-canonical-fif/
  studies/{study_id}/
    runs/{run_id}/run_manifest.json
    artifacts/{hash_prefix}/{content_hash}/
    previews/
    temp/
    exports/
```

所以目前最核心的问题不是“数据库表完全没有”，而是“数据库新概念已经出现，但文件落点、路径解析、API 语义和运行时读写仍然以 Project 根目录为中心”。这会导致 Dataset / Study / Pipeline / Run 的边界在产品上说得清楚，但代码里仍然互相掺在一起。

一句话判断：

> 现有实现可以继续支撑 MVP 跑通上传和 Pipeline Run，但如果要落实最新文件管理方案，必须优先改造存储根目录、Dataset 文件写入、Raw BIDS 逻辑视图、StorageService、Run Artifact 存储和 Run Manifest。

## 2. 目标方案的关键标准

目标方案有四条硬边界：

| 对象 | 文件责任 | 不应负责 |
| --- | --- | --- |
| Dataset | 原始上传证据、Raw BIDS 权威入口、canonical FIF 工作副本、基础 QC 和摘要索引 | 某个研究问题下的滤波、ICA、epoch、ERP、统计结果 |
| Study | 成员权限、Dataset mount、运行锁、Run manifest、日志、Artifact、预览、导出 | Dataset 原始文件副本 |
| Pipeline | 工作流定义、节点参数、选择规则、版本状态 | 具体数据文件和输出文件 |
| Run | 一次执行事实：输入快照、定义快照、参数、任务事件、输出索引、依赖关系 | 动态读取“当前数据”作为历史事实源 |

目标文件管理原则：

1. 用户不直接操作服务器目录，前端只拿 `dataset_file_id`、`artifact_id` 或 selector。
2. `raw_bids/` 是 Dataset 的标准原始数据入口，可以是逻辑视图，不一定复制大文件。
3. `sourcedata/original_uploads/` 是上传证据源，原则上永久保留。
4. `derivatives/elys-canonical-fif/` 是 MNE-ready 工作副本，可重建、可缓存。
5. Study 不复制 Dataset 原始文件，只挂载 Dataset，并在 Run 创建时冻结输入。
6. Artifact 输出按 `retention_status` 和依赖关系清理，不能靠目录盲删。
7. 业务层逐步使用 `elys://datasets/...`、`elys://studies/...`，由 StorageService 映射到本地文件或对象存储。

## 3. 当前实现摘要

### 3.1 当前文件根目录

当前配置仍然只有：

```python
PROJECTS_DIR = "/mnt/elys_data/projects"
```

对应代码位置：`elys_version1/backend/app/config.py:33`。

创建 Study/Project 时，后端会把 `projects.bids_root` 设置为：

```python
project.bids_root = os.path.join(settings.PROJECTS_DIR, project.id)
```

对应代码位置：`elys_version1/backend/app/routers/projects.py:546`。

并创建这些目录：

```text
source_uploads/
fifdata/
upload_staging/
validation/
bids_exports/
derivatives/preprocessing/
pipeline/
```

对应代码位置：`elys_version1/backend/app/routers/projects.py:71-83`。

这说明当前系统仍把 Study/Project 目录当成原始上传、canonical FIF、临时文件、Pipeline 输出的统一根。

### 3.2 当前 Dataset 文件写入

对应代码位置：`elys_version1/backend/app/routers/datasets.py:1134-1225`。

对应代码位置：`elys_version1/backend/app/routers/datasets.py:870-930`。

### 3.3 当前数据库语义

数据库已经有新旧两套语义并存：

| 当前表/视图 | 当前语义 | 与目标方案的关系 |
| --- | --- | --- |
| `dataset_assets` | 平台级 Dataset 资产目录 | 方向正确，但没有 Dataset Version |
| `study_dataset_mounts` | Study 挂载 Dataset Asset | 方向正确，但挂载仍指向没有物理目录的 Asset |
| `subjects` | Project 内 subject 索引 | 仍是 Study/Project 作用域 |
| `datasets` | 实际上是 recording / 采集记录 | 已通过 `recordings_view` 兼容新命名 |
| `dataset_uploads` | 实际上是 recording version | 已通过 `recording_versions_view` 兼容新命名 |
| `dataset_files` | 文件索引 | 方向正确，但强绑定 `project_id + dataset_id + dataset_upload_id` |
| `pipeline_runs` | Run 主记录 | 有 definition snapshot，但无 `manifest_json` |
| `pipeline_run_inputs` | Run 输入快照 | 方向正确，但上游 Artifact 依赖尚未自动写入 |
| `pipeline_artifacts` | Run 输出索引 | 方向正确，但物理文件仍写在 Project 根目录 |

关键数据库注释也明确了当前兼容状态：

- `datasets.source_path` 是 `source_uploads/` 中的主原始文件路径。
- `datasets.fif_path` 是 `fifdata/` 中由系统生成的 FIF 工作数据路径。
- `dataset_files.storage_uri` 当前使用 `project://{project_id}/{relative_path}`。
- `dataset_files.relative_path` 是相对于项目 `bids_root` 的路径。

对应位置：`elys_version1/database/schema/00_current_schema.sql:255-299`。

## 4. 冲突清单

优先级说明：

- P0：会直接影响 Dataset / Study / Run 的边界、追溯事实源或结果安全。
- P1：MVP 可以短期兼容，但要尽快改，否则会阻碍数据选择器、协作和文件治理。
- P2：不阻塞 MVP，但会影响长期一致性、迁移和维护。

| 编号 | 优先级 | 区域 | 目标方案 | 当前实现 | 影响 | 需要更改 |
| --- | --- | --- | --- | --- | --- | --- |
| FM-ROOT-01 | P0 | 存储根目录 | `/storage/datasets` 和 `/storage/studies` 分开 | 只有 `/projects/{project_id}` | Dataset 文件和 Study 输出物理混在一起 | 新增 `ELYS_STORAGE_ROOT`、`DATASETS_STORAGE_ROOT`、`STUDIES_STORAGE_ROOT`，保留旧 `PROJECTS_DIR` 兼容 |
| FM-ROOT-02 | P1 | 路径抽象 | 业务层使用 `elys://`，StorageService 映射真实路径 | 业务层大量直接使用 `Path(project.bids_root)` | 后续迁移 MinIO/S3 或标准目录会牵一发动全身 | 新增 `app/services/storage.py`，统一解析 `project://`、`elys://`、`file://` |
| FM-DS-01 | P0 | Dataset 边界 | Dataset 拥有原始上传、Raw BIDS、canonical FIF | Study/Project 目录拥有 `source_uploads` 和 `fifdata` | Study 看起来拥有 Dataset 文件，跨 Study 引用会变成复制或混乱 | 上传新数据时写入 `storage/datasets/{asset}/versions/{version}`，旧字段双写兼容 |
| FM-DS-02 | P0 | Raw BIDS | `raw_bids/` 是权威原始数据入口 | 没有真正 Raw BIDS 目录，只有 `source_uploads` 和 `fifdata` | 无法标准导出、验证、分享，也无法从 Raw BIDS 重建 canonical FIF | 实现 Raw BIDS 逻辑视图，至少登记 `raw_bids_data`、`raw_bids_events`、`raw_bids_channels` |
| FM-DS-03 | P0 | 文件索引 | `dataset_files.relative_path/logical_path` 表示 Dataset 内逻辑路径 | `relative_path` 是相对 Project `bids_root` 的路径 | 文件索引无法表达 Dataset 版本内的标准 BIDS 路径 | 新增或迁移到 `logical_path`，`storage_uri` 指真实物理位置 |
| FM-DS-04 | P1 | 文件角色 | `original_upload`、`raw_bids_data`、`raw_bids_events`、`canonical_fif` 等细分角色 | 只有 `raw_source`、`canonical_fif`、`sidecar` | 选择器无法区分 Raw BIDS sidecar、canonical provenance、上传证据 | 标准化 `dataset_files.file_role`，旧角色兼容读取 |
| FM-DS-05 | P1 | Dataset 版本 | Dataset Asset 下有 version，Study mount 引用固定版本 | 只有 `dataset_assets`，没有 `dataset_versions` | 增量上传和未来发布/冻结版本难以清晰表达 | MVP 可先 working 不发布，但应设计 `dataset_versions` 或在 metadata 中预留 |
| FM-DS-06 | P2 | 零复制 | `raw_bids` 可用硬链接/reflink/`storage_objects` 表示逻辑视图 | 没有 `storage_objects`，一个逻辑文件一个物理路径 | 大规模数据下重复存储和跨视图引用不清晰 | 正式阶段新增 `storage_objects`，MVP 先用 `storage_uri + sha256` |
| FM-DS-07 | P1 | canonical FIF | FIF 是从 Raw BIDS 生成的工作副本，sidecar 只保留轻量 provenance | 当前 FIF 生成同时产出完整 `*_eeg.json/channels.tsv/events.tsv` 放在 `fifdata` | Raw BIDS sidecar 和 canonical sidecar 语义混淆 | Raw BIDS sidecar 放 `raw_bids`，canonical FIF 只保留 provenance JSON |
| FM-DS-08 | P1 | 导入任务 | 上传、识别、Raw BIDS 构建、FIF 转换应进入任务系统 | 当前 `/datasets/import` 在 HTTP 请求内同步完成 | 大文件导入不可取消、不可重试、进度不可追踪 | 新增 `dataset_import` / `dataset_convert` async task |
| FM-DS-09 | P1 | 唯一约束 | Recording 唯一性应考虑 Dataset Asset 或 Dataset Version | 当前 `uq_datasets_bids_entities` 是 Project 范围 | 同一 Study 挂载多个 Dataset Asset 时，同名 subject/session/task/run 可能冲突 | 评估改为 `(project_id, dataset_asset_id, subject_id, session, task, run)` 或引入 Asset 内 recording |
| FM-DS-10 | P1 | provenance | canonical FIF 应记录来源 Raw BIDS 文件、sha、转换参数和转换器版本 | 当前 provenance 主要在 `*_import.json` 和 `metadata_json` 中松散保存 | 删除 canonical FIF 后无法严格自动重建 | 新增 `dataset_file_derivations` 或规范 `metadata_json` 结构 |
| FM-SELECT-01 | P1 | 数据选择器 | 选择器按数据库摘要筛选，不读目录 | 当前主要按 `datasets` 字段和 `fif_path` 筛选 | 4000 被试、多 session/run、多 marker 时筛选维度不足 | 新增 `recording_event_summaries`、`recording_channel_summaries` |
| FM-SELECT-02 | P1 | 文件选择 | 前端应传 `dataset_file_id` 或 selector，不传路径 | 当前 `LoadDataDataInfo` 中仍大量包含 `source_path`、`fif_path`、`fif_abs_path` | 运行链路继续依赖路径，迁移存储时风险大 | LoadData 输出以 `dataset_file_id + storage_uri + sha256` 为主，路径只作兼容 |
| FM-ST-01 | P1 | Study 设置 | `storage_policy`、`run_policy`、`artifact_retention_policy` 应被运行时消费 | 目前 `default_dataset_filter` 已消费，其他策略基本未消费 | 设置能写但不生效，协作规则不稳定 | Run 创建、ArtifactStore、清理服务读取 Study Settings |
| FM-ST-02 | P0 | 删除治理 | 普通业务不能物理删除影响追溯的目录和记录 | Project purge 虽已做 blocking check，但底层外键仍有大量 cascade | 一旦误用硬删，会破坏 Run 和 Dataset 追溯 | purge 继续作为管理员治理能力；增加更严格依赖检查和 trash 流程 |
| FM-ST-03 | P1 | 运行锁 | 可按 Study 策略限制单个或多个活跃 Run | 当前只对 `resource_kind=pipeline` 加 run lock | 多个 Pipeline 同时跑时，仍可能争用同一批数据或输出 | 根据 `study_settings.run_policy` 决定锁粒度：study / pipeline / dataset mount |
| FM-ST-04 | P1 | 文件归属 | Study 不拥有 Dataset 原始文件 | 当前 `projects.bids_root` 既是 Study 根也是数据根 | 跨 Study 引用 Dataset 时没有自然路径 | 新建 Study 目录只创建 `runs/artifacts/previews/temp/exports` |
| FM-PL-01 | P2 | Pipeline 定义 | Pipeline 不关心 `fifdata` 目录 | Node spec 文案仍写“项目 fifdata 工作数据集” | 产品语义与文档不一致 | 更新节点说明为“Study 挂载 Dataset 中的 canonical FIF / Raw BIDS” |
| FM-PL-02 | P1 | 协作编辑 | 多人编辑 Pipeline 应有 edit lock 或强制版本检查 | 只有可选 `expected_version`，运行锁只保护 run | 仍可能覆盖别人编辑习惯 | 使用 `study_locks(lock_type='edit')` 或强制 `expected_version` |
| FM-RUN-01 | P0 | Artifact 存储 | Run 输出进入 `storage/studies/{study_id}/artifacts/{hash_prefix}/{content_hash}` | 输出进入 `{project_root}/pipeline_runs/{run_id}/nodes/{node_id}` | 输出和 Run 临时目录混在一起，难以去重和清理 | 改造 ArtifactStore，先兼容旧目录，新增 content-addressed 写入 |
| FM-RUN-02 | P0 | Run Manifest | 每个 Run 有 `run_manifest.json` 和 DB 摘要 | 目前无 manifest 文件，`pipeline_runs` 也无 `manifest_json` | 对外解释、导出复现、审计不够直接 | 新增 manifest 生成服务，Run 完成/失败时写入并登记 Artifact |
| FM-RUN-03 | P0 | Run 依赖 | 下游 Run 使用上游 Artifact 时必须写依赖 | 有 `pipeline_run_dependencies` 表，但运行时尚未自动写入 | run3 依赖 run2 时，清理 run2 输出可能污染结果 | 在节点输入解析层写 `pipeline_run_dependencies` 和 `pipeline_run_inputs.upstream_*` |
| FM-RUN-04 | P1 | retention 状态 | 需要 `temporary/current/pinned/cached/deleted/quarantined` | DB CHECK 只有 `current/pinned/cached/deleted`，API 更新只允许 `current/pinned/deleted` | 临时文件、隔离文件和缓存治理表达不足 | 扩展状态枚举，清理服务按状态执行 |
| FM-RUN-05 | P1 | 预览和缓存 | Preview/Cache 通过 StorageService 读取 Artifact | 直接用 `project.bids_root + storage_path` | 迁移 `storage/studies` 或对象存储后容易断 | Preview、Cache、Engine IO 改为从 `storage_uri` 解析 |
| FM-RUN-06 | P1 | 清理服务 | 只清理未被依赖、可重建、非 pinned/current 的文件 | 目前只有 retention 标记 API，没有后台清理闭环 | 数据会持续增长，或人工清理会破坏依赖 | 新增 cleanup task，先只扫描 `cached/temporary` |
| FM-API-01 | P1 | 文件访问 API | API 以 file/artifact id 为入口，不暴露路径 | 响应仍返回 `relative_path`、`storage_path`、`bids_root` | 前端可能继续依赖目录结构 | 新增 browse/download/preview API，前端逐步少用路径字段 |
| FM-API-02 | P1 | Raw BIDS API | 应支持 Raw BIDS 浏览、验证、导出、重建 canonical FIF | 当前无 raw_bids 视图 API | 用户无法确认 Dataset 是否标准化 | 增加 `/dataset-assets/{id}/files`、BIDS tree、validation、canonical rebuild |
| FM-API-03 | P2 | Study 命名 | 产品语义是 Study | API 仍是 `/projects`，DB 仍是 `projects` | 文档和代码长期会混淆 | 短期文档说明 Project=Study；中期增加 `/studies` alias |
| FM-GOV-01 | P1 | 治理隔离 | Dataset、Artifact、文件都需要可隔离 | Dataset Asset 有 `quarantined`，Artifact retention 无 `quarantined` | 伦理下架只能资产级粗粒度处理 | 扩展 Artifact/File 级治理状态和访问拦截 |

## 5. Study / Pipeline / Run 重点冲突

### 5.1 Study 当前最大冲突

目标中的 Study 是“协作空间 + Dataset 引用 + Run 输出空间”。当前 Project 实际还是“协作空间 + 数据根目录 + 输出根目录”。

当前 Study/Project 创建时会创建 `source_uploads` 和 `fifdata`，这与目标边界冲突。未来 Study 目录应该只创建：

```text
study.json
runs/
artifacts/
previews/
temp/
exports/
pipeline_snapshots/
```

不应该创建 Dataset 的原始上传目录。

短期可以保留旧目录，但新写入不应继续扩大旧结构。推荐做法：

1. 保持已有 `projects.bids_root` 不搬。
2. 新增 `projects.storage_uri` 或 `study_storage_uri` 作为标准 Study 根。
3. 新上传 Dataset 时写入 Dataset 根，而不是 Study 根。
4. Artifact 新写入 Study 根，旧 `pipeline_runs` 只读兼容。

### 5.2 Pipeline 当前最大冲突

Pipeline 的数据库边界基本正确：`pipeline_definitions` 只保存定义，Run 会保存 `definition_snapshot`。这部分与目标方案冲突不大。

真正冲突在于 Pipeline 节点和 LoadData 的数据语义：

1. 节点说明仍然把输入叫做 `fifdata`。
2. `LoadDataDataInfo` 仍然以 `fif_path` / `fif_abs_path` 作为运行时核心字段。
3. Run input snapshot 会匹配 `dataset_files`，但匹配逻辑仍先找 `canonical_fif` 的相对路径。

目标方案里，Pipeline 可以保存“选择规则”，但不应该暗含“从项目 fifdata 目录取数据”。推荐改为：

```text
LoadData selector
  -> Study mount
  -> Dataset Asset / Dataset Version
  -> Recording / Recording Version
  -> dataset_file_id(file_role=canonical_fif 或 raw_bids_data)
```

### 5.3 Run 当前最大冲突

Run 已经有 `pipeline_run_inputs`、`async_tasks`、`task_events`、`pipeline_artifacts`，方向是对的。但文件层还有三个关键缺口：

1. 没有 `run_manifest.json`。
2. Artifact 文件不在标准 Study artifacts 目录，也不是内容寻址。
3. 上游 Artifact 作为下游输入时，没有系统自动写依赖。

这三个问题会直接影响你之前最担心的“run3 依赖 run2，run2 输出被删或变了怎么办”。现在 DB 有一部分结构，但运行时还没完全闭环。

## 6. 数据库需要改造的地方

### 6.1 建议优先新增或调整

| 建议对象 | 类型 | 目的 | MVP 是否必须 |
| --- | --- | --- | --- |
| `dataset_versions` | 新表 | 表达 Dataset Asset 的 working version / future publish version | 可先弱化，但建议预留 |
| `dataset_files.logical_path` | 新字段或语义迁移 | 区分 Dataset 内逻辑路径和真实存储位置 | 是 |
| `dataset_files.storage_uri` 标准化 | 字段语义升级 | 从 `project://` 迁到 `elys://datasets/...` | 是 |
| `dataset_file_derivations` | 新表 | 记录 canonical FIF 来源 Raw BIDS 和转换参数 | 建议 |
| `storage_objects` | 新表 | 零复制、多逻辑文件引用同一物理对象 | 后续 |
| `recording_event_summaries` | 新表 | 大规模 marker / event 快速筛选 | 建议 |
| `recording_channel_summaries` | 新表 | 通道、坏通道、定位状态摘要 | 建议 |
| `pipeline_runs.manifest_json` | 新字段 | 保存 Run manifest 摘要 | 是 |
| `pipeline_artifacts.retention_status` 扩展 | 字段约束调整 | 支持 `temporary`、`quarantined` | 建议 |
| `pipeline_run_dependencies` 自动写入 | 业务逻辑，不只是表 | 保护下游依赖 | 是 |

### 6.2 `dataset_files` 当前设计的限制

当前 `dataset_files` 必须有：

```text
project_id
dataset_id
dataset_upload_id
relative_path
storage_uri
```

这对现在的 legacy upload 很好，因为每个文件都能落回一个上传版本。但它对目标方案有三个限制：

1. 不能自然表达 Dataset Asset Version 下的文件。
2. 不能自然表达 `raw_bids` 逻辑路径和物理对象路径不同的情况。
3. 不能自然表达跨 Study 引用同一个 Dataset 文件。

短期不建议破坏式改表。推荐做兼容升级：

1. 保留 `relative_path`，但新写入把它当 `logical_path` 使用。
2. 新增 `storage_scope` 或通过 `storage_uri` 前缀区分 `dataset` / `study`。
3. 新增可空 `dataset_version_id`。
4. 新增 `source_file_id` 或引入 `dataset_file_derivations`。

### 6.3 `pipeline_artifacts` 当前设计的限制

当前 `pipeline_artifacts` 已经有正确字段：

```text
storage_path
storage_uri
checksum
sha256
retention_status
deleted_at
deleted_by
last_accessed_at
content_hash
```

但物理存储和服务逻辑还没跟上：

1. `content_hash` 没有决定物理路径。
2. `storage_uri` 仍是 `project://`。
3. `storage_path` 仍相对 `project.bids_root`。
4. `retention_status` 没有完整清理服务。

推荐下一步不是先继续加字段，而是改 `ArtifactStore` 写入策略。

## 9. 推荐实施路线

### 第 0 阶段：先加兼容层，不搬旧数据

目标：停止扩大旧路径依赖。

建议任务：

1. 新增 `ELYS_STORAGE_ROOT=/mnt/elys_data/storage`。
2. 新增 StorageService，先支持现有 `project://`。
3. 所有新代码只通过 StorageService 解析路径。
4. 更新 NodeSpec 文案，去掉“项目 fifdata 工作数据集”的表述。
5. 在文档和代码注释中明确 `Project=Study` 是兼容命名。

验收标准：

- 旧上传和旧 Run 不受影响。
- 新读写服务不再直接散落 `Path(project.bids_root)`。

### 第 1 阶段：Dataset 新写入标准化

目标：让 Dataset 真正拥有原始数据和 canonical FIF。

建议任务：

1. 上传保存到 `storage/datasets/{asset}/versions/working/sourcedata/original_uploads`。
2. 生成或登记 `raw_bids` 逻辑视图。
3. canonical FIF 写到 `derivatives/elys-canonical-fif`。
4. `dataset_files.file_role` 改为标准角色。
5. `dataset_files.relative_path` 新写入使用 Dataset 内逻辑路径。
6. 旧 `datasets.source_path/fif_path` 继续双写兼容。

验收标准：

- 新上传能在 Dataset 文件树中看到 `sourcedata/raw_bids/derivatives`。
- LoadData 能从 `dataset_files` 解析 canonical FIF。
- 旧 `/datasets/{id}` API 仍能返回兼容字段。

### 第 2 阶段：Run 输出标准化

目标：让 Study 只拥有运行输出，Run 可导出、可复现、可清理。

建议任务：

1. `ArtifactStore` 写到 `storage/studies/{study_id}/artifacts/{hash_prefix}/{content_hash}`。
2. Run 临时目录写到 `storage/studies/{study_id}/temp/{run_id}`。
3. Run 完成后生成 `runs/{run_id}/run_manifest.json`。
4. DB 保存 `pipeline_runs.manifest_json` 摘要，或登记 manifest artifact。
5. 写入 `pipeline_run_dependencies`。

验收标准：

- Run detail 能返回 manifest、inputs、outputs、dependencies。
- Artifact preview 只通过 `artifact_id/storage_uri` 工作。
- 下游依赖存在时，清理上游 Artifact 被阻止。

### 第 3 阶段：数据选择器和大规模索引

目标：让用户不用理解目录，也能快速选择 4000 被试规模的数据。

建议任务：

1. 增加 event/channel summary 表。
2. 导入时抽取 marker/event 摘要。
3. API 支持按 marker、event count、channel type、duration、missing channel 筛选。
4. 前端选择器只使用 DB 索引和 selector，不暴露目录。

验收标准：

- 可按 Dataset mount、subject、session、run、marker 快速筛选。
- 选择结果可保存为 Pipeline LoadData 规则。
- Run 创建时冻结实际命中的文件列表。

### 第 4 阶段：治理和对象存储准备

目标：支持清理、隔离、未来 MinIO/S3。

建议任务：

1. 增加 cleanup task。
2. 增加 Artifact / Dataset File 级 quarantine。
3. 增加 `storage_objects`，支持零复制和对象存储。
4. 下载 API 生成短期 URL 或流式响应。
5. MinIO/S3 只影响 StorageService，不影响业务 API。

## 11. 对 MVP 的建议

不建议立刻做大搬迁。直接把旧 `/mnt/elys_data/projects/{project_id}` 全部迁走，会带来很高风险。

更稳妥的 MVP 策略：

1. 旧数据旧路径继续可读。
2. 新代码新增 StorageService。
3. 新上传开始按标准 Dataset 目录写。
4. 新 Run 输出开始按标准 Study artifacts 写。
5. `dataset_files`、`pipeline_run_inputs`、`pipeline_artifacts` 作为事实源逐步强化。
6. `source_path/fif_path/storage_path` 继续返回，但标记为兼容字段。
7. 前端逐步改为 file id / artifact id / selector 驱动。

这样既不会打断现有 MVP，又能把未来平台的边界立住。

## 13. 最终判断

现在的代码和目标文件管理方案确实有明显出入，而且出入集中在“物理文件归属”和“路径解析方式”上：

- 数据库新概念已经比较接近目标。
- API 已经有一部分新入口。
- 但文件仍然主要写在 Project 根目录。
- `raw_bids` 还没有真正落地。
- `storage_uri` 还没有成为运行时事实源。
- Artifact 还没有进入标准 Study artifacts/content-addressed 存储。
- Run Manifest 和 Run dependency 还没有形成闭环。

如果只做 MVP，当前方案还能继续跑；如果要实现你想要的协作分享平台，下一阶段应该把重点从继续加表，转到“统一存储服务 + 新写入标准化 + Run 输出追溯闭环”。
