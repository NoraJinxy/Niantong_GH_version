本轮目标：根据前一份系统分析中的 `DB-DS-* / DB-ST-* / DB-PL-* / DB-RUN-* / DB-SQL-*` 问题清单，优先修复低风险、能直接增强 MVP 数据追溯能力的内容；对暂不适合立即改的内容说明原因和后续建议。

## 1. 本轮已完成的修复

### DB-DS-01：Dataset Asset 和实际上传数据未打通

状态：部分修复，MVP 主链路已接上。

已改内容：

1. `datasets` 增加 `dataset_asset_id` 字段，指向 `dataset_assets`。
2. ORM `Dataset` 增加 `dataset_asset_id` 和 `dataset_asset` 关系。
3. `DatasetResponse` 和 `RecordingResponse` 返回 `dataset_asset_id`。
4. 上传 EEG 时自动创建或复用 Study 的默认 working Dataset Asset。
5. 上传 EEG 时自动创建或复用默认 `working` Study Mount。
6. 历史兼容迁移会为已有 Project 创建默认 working Dataset Asset，并回填已有 `datasets.dataset_asset_id`。

涉及文件：

- `elys_version1/database/schema/00_current_schema.sql`
- `elys_version1/database/migrations/20260521_0001_compat_v1_to_current.sql`
- `elys_version1/backend/app/models/project.py`
- `elys_version1/backend/app/services/dataset_assets.py`
- `elys_version1/backend/app/routers/datasets.py`
- `elys_version1/backend/app/schemas/dataset.py`

遗留问题：

- 这仍然是 MVP 的“每个 Study 默认 working Dataset Asset”方案。
- 还没有实现 Dataset Asset 版本、发布、跨机构共享和 Dataset ACL。

### DB-DS-02 / DB-PL-05：LoadData 不认 Study Mount / Pipeline 输入没有 Dataset Mount 契约

状态：部分修复，后端解析能力已具备。

已改内容：

1. `LoadData.dataset_filter` 支持 `mount_id`。
2. `LoadData.dataset_filter` 支持 `mount_name`。
3. `LoadData.dataset_filter` 支持 `dataset_asset_id` 或 `dataset_asset_ids`。
4. 如果使用 mount，后端会读取 `study_dataset_mounts.selection_json`，并把 mount 对应的 `dataset_asset_id` 合并进实际过滤条件。
5. `LoadDataDataInfo` 增加 `dataset_asset_id`。
6. `pipeline_run_inputs` 增加 `dataset_asset_id`，Run 输入快照能记录 Dataset Asset。

涉及文件：

- `elys_version1/backend/app/pipeline/load_data.py`
- `elys_version1/backend/app/pipeline/executor.py`
- `elys_version1/backend/app/schemas/pipeline.py`
- `elys_version1/backend/app/routers/pipelines.py`
- `elys_version1/database/schema/00_current_schema.sql`
- `elys_version1/database/migrations/20260521_0001_compat_v1_to_current.sql`

遗留问题：

- 前端数据选择器还没有接入 mount-based selector。
- 目前只完成 LoadData 后端解析，不等于已经完成完整数据选择 UI。

## 2. 本轮暂未修复的问题

### DB-DS-03：dataset_files 仍强绑定 legacy datasets / dataset_uploads

暂不修原因：

- 当前 MVP 正需要文件明确归属到某次上传版本。
- 直接放松 `dataset_id`、`dataset_upload_id` 非空约束，会影响现有上传和 Run 快照逻辑。

后续建议：

- 等 Derived Dataset 真正进入主链路后，再设计 `recording_version_files` 或 asset-level file link。

### DB-DS-04：没有 Dataset Asset Version

暂不修原因：

- 当前已经决定 MVP 暂不做发布。
- Dataset Version 会牵涉发布、下架、引用冻结、伦理治理，不能只加表。

后续建议：

- 做共享发布前，再新增 `dataset_asset_versions`。

### DB-DS-05：Dataset ACL / 成员权限不足

暂不修原因：

- 当前所有 Dataset 仍是 working/private 为主。
- 细粒度 ACL 需要配合分享产品策略。

后续建议：

- 后续统一做 `dataset_members` 或通用 resource ACL。

### DB-DS-06：缺少 event / marker / segment 索引

暂不修原因：

- 这需要先确定 marker 分割、事件抽取、epoch 管理的产品模型。
- 不能只加空表，否则很快会返工。

后续建议：

- 设计友好数据选择器时一并定义 `recording_events`、`recording_segments` 或物化索引。

### DB-DS-07：Dataset import / convert 没有 async task 化

暂不修原因：

- 现有上传流程是同步接口，改异步会影响前端交互、临时文件保留、错误恢复。

后续建议：

- 复用 `async_tasks`，新增 `dataset_import`、`dataset_convert` task_type。

### DB-DS-09：dataset_files 历史回填

暂不修原因：

- 当前没有真实 PostgreSQL 和历史文件样本可验证。

后续建议：

- 另做 backfill 脚本，扫描 `datasets.source_path`、`datasets.fif_path`、`dataset_uploads.sidecar_paths` 补齐。

### DB-ST-01：Project / Study 命名未完全统一

暂不修原因：

- API 和前端目前大量使用 `/projects`。
- 立即新增 `/studies` 双路由会增加维护面。

后续建议：

- 产品文档先统一称 Study，后端保留 projects 表；等前端准备好后增加 `/studies` alias。

### DB-ST-04：硬删除级联风险

暂不修原因：

- 当前已有软删除和 admin purge 流程。
- 彻底改外键级联会影响大量表和旧数据。

后续建议：

- 先在产品权限上限制 purge。
- 再给 purge 增加 Run / Artifact / Dataset 依赖检查。
- 最后才考虑修改外键策略。

### DB-ST-05：audit_events 和 project_audit_events 并存

暂不修原因：

- `project_audit_events` 当前用于项目硬删除后的保底审计。
- 直接合并会影响 purge 的可追溯性。

后续建议：

- 先统一新行为全部写 `audit_events`，后续再做兼容视图或迁移。

### DB-PL-01：没有不可变 pipeline_versions

暂不修原因：

- 现在 Run 已有 `definition_snapshot`，MVP 可追溯性基本够用。
- 新增 pipeline_versions 后，需要同步修改保存、运行、比较、回滚逻辑。

后续建议：

- 下一阶段做 Pipeline 协作编辑时一起补。

### DB-PL-02：expected_version 仍是可选

暂不修原因：

- 强制 required 可能立刻破坏现有前端调用。

后续建议：

- 先让前端保存 Pipeline 时必传，再逐步让后端强制。

### DB-PL-03：Pipeline 编辑锁未实现

暂不修原因：

- 已有 `study_locks` 可承载，但前端还没有“正在编辑者”的交互。

后续建议：

- 做多人编辑 UI 时，使用 `study_locks(resource_kind='pipeline', lock_type='edit')`。

### DB-RUN-02：Run Manifest 未实现

暂不修原因：

- Run Manifest 应该在 Run 完成时生成，涉及 executor 生命周期和 artifact 写入策略。

后续建议：

- 由 Pipeline 完成回调生成 `run_manifest.json`，作为 `pipeline_artifacts.artifact_type='run_manifest'` 保存。

### DB-RUN-05：Run status 和 Task status 映射文档不足

暂不修原因：

- 本轮主要做后端结构和 API。

后续建议：

- 在 docs_v2 API 或任务队列章节补状态机表。

### DB-RUN-06：缺少真实 PostgreSQL + FastAPI + Celery 回归

暂不修原因：

- 当前本地环境没有完整 PostgreSQL/FastAPI/Celery 端到端验证条件。

后续建议：

- 增加 docker compose 集成测试环境。

## 5. 当前建议

下一步如果继续做数据库相关功能，我建议优先做两件事：

1. 完成 Dataset 选择器前后端闭环，让 UI 可以选择 `mount_name` / `dataset_asset_id`，并批量过滤 subject/session/run/marker。
2. 完成 Run dependency 写入逻辑，让任何使用上游 Artifact 的 Run 都自动写 `pipeline_run_dependencies`。

这两件事会直接降低你担心的“多人处理导致数据依赖污染”的风险。
