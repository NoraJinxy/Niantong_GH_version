## 1. 总体实施原则

本次改造不要一次性搬迁旧数据，也不要一次性删除旧字段。正确方式是：

1. 先加兼容层，再改新写入。
2. 先让新代码统一走 StorageService，再逐步迁移旧路径。
3. 先保留 `project://` 兼容，再引入 `elys://datasets/...` 和 `elys://studies/...`。
4. 先让新上传和新 Run 走标准目录，再做旧数据回填。
5. 先把事实源写入数据库，再考虑文件旁 JSON。
6. 先保证旧 API 不断，再逐步新增标准 API。
7. 先保护 Run 依赖，再做清理服务。

实际发现：

1. 目标文件管理方案的核心标准已经在 `docs_v2` 中比较明确：Dataset 目录负责表达“数据是什么”，Study 目录负责表达“做了什么”，数据库负责身份、索引、版本、来源、权限和依赖关系，文件系统只保存大文件和可导出的结构。目标根目录是 `/mnt/elys_data/storage/datasets/{dataset_asset_id}/versions/{version}/...` 与 `/mnt/elys_data/storage/studies/{study_id}/...`。
2. 当前代码仍以旧 Project 根目录为唯一物理根。`backend/app/config.py` 只有 `PROJECTS_DIR=/mnt/elys_data/projects`；`routers/projects.py` 创建 Project 时把 `projects.bids_root` 设置为 `/mnt/elys_data/projects/{project_id}`，并创建 `source_uploads`、`fifdata`、`upload_staging`、`validation`、`bids_exports`、`derivatives/preprocessing`、`pipeline` 和 `.elys_project.json`。
3. 当前上传写入位置集中在 `routers/datasets.py`：原始上传归档到 `source_uploads/{subject}/{session}/{task}/{run}/upload-{seq}/files`，同时写入 `source_uploads/.../manifest.json`；FIF 转换先写入 `upload_staging/fif-*` 临时目录，成功后移动到 `fifdata/{subject}/{session}/{task}/{run}/upload-{seq}`，并写 `_raw.fif`、`_eeg.json`、`_channels.tsv`、`_events.tsv`、`_import.json`。
4. 当前 `fifdata` 还会写入兼容性数据集说明文件，包括 `fifdata/dataset_description.json`、`participants.json`、`participants.tsv`。代码注释已经说明这不是官方 EEG-BIDS raw dataset，官方导出预期在 `bids_exports/` 下生成。
5. 当前 Dataset 文件索引已经具备雏形。`dataset_files` 会登记 `raw_source`、`canonical_fif`、`sidecar`，并保存 `relative_path`、`storage_uri`、`sha256`、`size_bytes`、BIDS 实体等。问题是 `relative_path` 仍是相对 `project.bids_root`，`storage_uri` 仍是 `project://{project_id}/{relative_path}`，还不是目标方案中的 Dataset/Study URI。
6. 当前文件读取位置仍大量依赖 `Path(project.bids_root)` 和 `storage_path`。`routers/datasets.py` 用 `resolve_project_relative_path` 读取旧相对路径；`pipeline/load_data.py` 用 `project.bids_root + path_value` 解析 LoadData；`pipeline/previews.py` 用 `pipeline_artifacts.storage_path + project root` 预览；`pipeline/dispatcher.py` 把上游 artifact 的 `storage_path` 拼回绝对 FIF 路径；`engine/io.py` 直接读取 `fif_abs_path`、`fif_path`、`storage_path`、`artifact_storage_path`。
7. 当前 Pipeline Artifact 写入位置由 `pipeline/artifacts.py` 控制。`ArtifactStore` 在 `project.bids_root/pipeline_runs/{run_id}/nodes/{node_id}` 下写 JSON、复制文件、复制目录或保存 MNE 对象；`storage_path` 是相对 `project.bids_root` 的路径；`storage_uri` 由 `_storage_uri` 生成 `project://{project_id}/{storage_path}`；新 artifact 默认写 `retention_status=current`，兼容写 `checksum` 和 `sha256`。
8. 当前缓存复用由 `pipeline/cache.py` 以 `storage_path` 和 `content_hash` 为核心。复用 artifact 时会复制数据库记录，但物理文件仍指向同一个旧 `storage_path`，并把新记录标为 `retention_status=cached`。这对后续清理策略有风险，需要第 11 步依赖保护和第 9 步 ArtifactStore 改造一起处理。
9. 当前 `storage_uri` 的使用更像展示字段和未来兼容字段，不是统一解析入口。`dataset_files.storage_uri` 与 `pipeline_artifacts.storage_uri` 会通过 schema/API 返回，也有索引，但读取、预览、LoadData、dispatcher 仍主要认 `storage_path`、`relative_path` 或绝对路径。
10. 当前数据库已经包含一些新概念，但语义尚未完全落地。`dataset_assets` 和 `study_dataset_mounts` 已存在；`datasets` 仍承担 recording 语义；`dataset_uploads` 接近 recording version；`pipeline_run_inputs` 已能保存 `dataset_id`、`dataset_upload_id`、`dataset_file_id`、`upstream_run_id`、`upstream_artifact_id`，但没有直接保存 `storage_uri`、`logical_path`、`sha256` 快照字段；`pipeline_runs` 还没有明确的 `manifest_json` 字段。
11. 当前 schema 和 ORM 中与文件最相关的字段包括：`projects.bids_root`，`datasets.source_path`，`datasets.fif_path`，`dataset_uploads.fif_path`，`dataset_uploads.sidecar_paths`，`dataset_files.storage_uri`，`dataset_files.relative_path`，`pipeline_artifacts.storage_path`，`pipeline_artifacts.storage_uri`，`pipeline_artifacts.sha256`，`pipeline_artifacts.retention_status`，`pipeline_artifacts.deleted_at/deleted_by/last_accessed_at`。
12. 当前 API 入口分为四组：Project/Study 管理在 `/api/v1/projects`；Dataset 资产在 `/api/v1/dataset-assets`；旧 Dataset/Recording 与上传、QA、文件列表在 `/api/v1/projects/{project_id}/datasets` 和 `/api/v1/projects/{project_id}/recordings`；Pipeline/Run/Task/Artifact/Preview 在 `/api/v1/projects/{project_id}/pipelines`、`/api/v1/projects/{project_id}/pipeline-runs`、`/api/v1/projects/{project_id}/tasks` 等入口。
13. 与目标方案的主要冲突是：当前文件系统按 Project 根目录组织，而目标方案要求 Dataset 文件根与 Study 输出根分离；当前 `raw_bids` 尚未作为正式视图/标准入口落地；当前 canonical FIF 存在于 `fifdata`，但未放入 `derivatives/elys-canonical-fif`；当前 Run 输出落在 `pipeline_runs`，而目标方案希望进入 Study 下的 `artifacts/runs/previews/temp/exports` 体系。

6. 文档已经统一到当前实现口径，但部分旧章节仍保留 `projects/project_id` 的兼容命名，这是为了不破坏现有 API，不代表产品语义仍叫 Project。

最终结论：

第 15 步可以收口。文件管理改造已经形成一条可运行、可测试、可追溯的 MVP 闭环：


后续不建议继续在 `init.sql` 或文件路径上做大拆大改，而应进入部署验证和产品化阶段：先在 staging 上跑真实上传和真实 Run，再补 SSE、cancel/retry、staged upload、BIDS validator、BrainVision 引用重写和物理清理治理。

## 4. 建议优先级

如果时间有限，优先做这 6 步：

1. 第 2 步：StorageService。
2. 第 5 步：Dataset 新上传标准目录。
3. 第 6 步：Raw BIDS 逻辑视图。
4. 第 8 步：LoadData 和 Run 输入快照改为文件索引驱动。
5. 第 9 步：ArtifactStore 标准 Study 输出目录。
6. 第 10 步和第 11 步：Run Manifest 与 Run 依赖保护。

这 6 步能先解决最关键的边界问题：

- Dataset 文件不再被 Study 物理拥有。
- Pipeline Run 不再依赖“当前数据”。
- Artifact 输出可以被追溯和治理。
- 下游依赖不会因为上游清理被破坏。

## 5. 风险控制

| 风险 | 控制方式 |
| --- | --- |
| 旧上传断裂 | 所有旧字段和旧目录先保留 |
| 旧 Run 预览断裂 | StorageService 必须兼容 `project://` 和 `storage_path` |
| 迁移误删文件 | 前 14 步都不做物理删除，清理只走第 13 步任务 |
| 数据重复占空间 | MVP 可接受，后续用 hardlink/reflink/storage_objects 优化 |
| DB migration 风险 | 每一步都先兼容新增，不做破坏式改表 |
| 前端路径依赖 | API 保留路径字段，但新增 id/URI 驱动字段，引导前端逐步切换 |
| 大文件导入超时 | 第 13 步异步化前，先控制同步入口文件大小和超时提示 |

## 7. 当前结论

这套改造不建议当成一次“大迁移”，而应该当成一条兼容演进路线：

```text
旧 Project 根目录可读
  -> StorageService 统一路径
  -> 新 Dataset 上传标准化
  -> Raw BIDS / canonical FIF 标准化
  -> LoadData 文件索引驱动
  -> Study Artifact 标准化
  -> Run Manifest / Dependency 闭环
  -> 异步任务和清理治理
  -> 旧数据回填
  -> 全链路验证与文档收口
```

做到第 15 步后，平台的核心数据安全边界已经在 MVP 层面立住：Dataset 是可共享、可追溯的数据资产；Study 是协作与输出空间；Pipeline 是流程定义；Run 是不可篡改的执行事实。下一阶段重点不再是继续堆表和目录，而是在 staging/生产相似环境中验证真实上传、真实任务队列、真实大文件转换和治理策略。
