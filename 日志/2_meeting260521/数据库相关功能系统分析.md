## 1. 总体结论

当前数据库已经能支撑 MVP 的核心链路：

1. 用户创建 Study/Project。
2. 在 Study/Project 内上传 EEG 数据。
3. 上传时记录 legacy `datasets`、`dataset_uploads`，并兼容写入 `dataset_files`。
4. 创建 Pipeline。
5. 创建 Run 时冻结 `definition_snapshot` 和 `pipeline_run_inputs`。
6. Run 通过 `async_tasks` 和 `task_events` 记录异步任务状态。
7. 输出通过 `pipeline_artifacts` 记录，并带有 `storage_uri`、`sha256`、`retention_status` 等字段。

但是，如果按你最终想要的协作分享平台来衡量，目前还不能说已经“较好支持” Dataset / Study / Pipeline / Run 的完整语义。更准确的判断是：

| 对象 | 当前支持度 | 判断 |
| --- | --- | --- |
| Dataset | 中等偏弱 | 数据资产表、挂载表、文件索引已经有了，但上传数据和 Dataset Asset 还没有真正打通，LoadData 也还没有从 Study Mount 解析数据。 |
| Study | 中等偏强 | Project 已经基本承担 Study 职责，有成员权限、can_run、运行锁、审计和 Dataset Mount，但命名、设置、挂载管理和软删除策略还需要统一。 |
| Pipeline | 中等 | 有定义表、版本号、更新冲突检查和 Run 快照，但没有不可变 Pipeline Version 表，Pipeline 本体仍是可变对象。 |
| Run | 较好但未闭环 | Run 输入快照、异步任务、事件、Artifact 保留策略都有基础，但缺少 Run Manifest 一等对象、依赖保护、任务 API、取消重试和清理服务。 |

工程建议：不要推翻当前改造。当前结构已经有了正确方向，下一步重点不是继续大改 `init.sql`，而是把“已经建好的表”真正接入业务链路，尤其是 Dataset Asset、Study Mount、LoadData、Run dependency 和 Artifact retention。

## 2. 当前数据库对象分层

当前数据库可以理解为五层：

| 层级 | 当前表/视图 | 职责 |
| --- | --- | --- |
| 用户权限层 | `users`, `roles`, `permissions`, `user_roles`, `role_permissions` | 账号、角色和系统权限。 |
| Study 层 | `projects`, `project_members`, `study_locks`, `audit_events`, `project_audit_events` | 当前仍用 Project 表承担 Study 语义，管理研究空间、协作者权限、运行锁和审计。 |
| Dataset 层 | `dataset_assets`, `study_dataset_mounts`, `subjects`, `datasets`, `dataset_uploads`, `dataset_files`, `recordings_view`, `recording_versions_view` | 同时存在新 Dataset Asset 语义和旧 recording/import 语义。 |
| Pipeline 层 | `pipeline_definitions` | 保存工作流定义、当前版本号、节点数量和模板标记。 |
| Run 层 | `pipeline_runs`, `pipeline_node_runs`, `pipeline_run_inputs`, `pipeline_artifacts`, `async_tasks`, `task_events`, `dataset_derivatives`, `analysis_results` | 保存执行记录、节点状态、输入快照、输出文件、任务事件和部分分析结果。 |

推荐的长期语义应该是：

```text
Dataset Asset
  └─ Recording / Recording Version / Dataset File
        └─ mounted by Study
              └─ used by Pipeline Run
                    ├─ Pipeline Run Inputs
                    ├─ Pipeline Artifacts
                    └─ Async Tasks / Task Events
```

但当前实际语义更接近：

```text
Project
  └─ subjects / datasets / dataset_uploads
        ├─ dataset_files
        └─ LoadData
              └─ Pipeline Run

Dataset Asset
  └─ Study Mount
        └─ 暂时没有深度接入 LoadData 和导入流程
```

这就是当前最大的结构性问题：新的 Dataset Asset 框架已经建好，但旧导入链路仍然是事实主链路。

## 3. Dataset 支持情况

### 已经支持

当前已经有以下能力：

1. `dataset_assets` 表作为真正的数据资产表，包含 `name`、`code`、`owner_id`、`status`、`visibility`、`metadata`。
2. `study_dataset_mounts` 表表达 Study 对 Dataset Asset 的引用关系。
3. `subjects`、`datasets`、`dataset_uploads` 继续承担上传记录、采集记录、上传版本语义。
4. `recordings_view` 和 `recording_versions_view` 提供 Recording 命名的兼容视图。
5. `dataset_files` 统一索引 `raw_source`、`canonical_fif`、`sidecar` 等文件。
6. 上传流程已经兼容写入 `dataset_files`。
7. Dataset Asset 有基础创建、列表和 Study Mount API。

### 主要不足

1. Dataset Asset 没有和实际上传进来的 `datasets` / `dataset_uploads` 建立明确关系。
   当前用户创建了一个 Dataset Asset，但上传 EEG 时，数据仍主要进入 Project 下的 legacy `datasets` 表。

2. Study Mount 还没有真正参与 LoadData。
   `LoadData` 当前仍然按 `project_id` 查询 legacy `datasets`，通过 subject/session/task/run/qa_status 过滤，而不是从某个挂载 Dataset Asset 中解析数据。

3. `dataset_files` 仍绑定 legacy `datasets` 和 `dataset_uploads`，两个字段都是非空。
   这对 MVP 有利，因为能保证文件属于明确的上传版本；但对未来“Dataset Asset 文件”“Derived Dataset 文件”“跨 Study 引用文件”会比较僵硬。

4. Dataset Asset 没有版本模型。
   当前有 `status` 和 `visibility`，但没有 `dataset_asset_versions` 或类似表。MVP 不做发布可以接受，但如果后续要支持共享、下架、伦理冻结、版本引用，就需要补。

5. Dataset 权限偏粗。
   当前主要靠 owner、created_by、visibility 判断可见性，没有 Dataset 成员、Dataset ACL、分享链接、引用许可等细粒度模型。

6. 大规模选择支持不足。
   对 4000 被试、2 session、12 run、多 marker 分割这种规模，目前只有 subject/session/task/run/qa_status 级别过滤，不足以支撑友好的批量选择器。缺少 recording/event/marker/segment 的可查询索引。

7. 上传和转换不是统一异步任务。
   Pipeline Run 已有 `async_tasks`，但 Dataset import/convert 还没有同等任务化。大数据上传、FIF 转换、元信息扫描、事件提取都应该走任务体系。

8. QC 可选的产品语义和当前默认 LoadData 策略略有冲突。
   `LoadData` 默认 `qa_status` 是 `converted` 和 `checked`，这会自然排除 `pending`。如果你坚持 QC 不是必要项，默认选择器需要调整，或者 UI 明确提供“包含未检查数据”。

### Dataset 判断

Dataset 的表结构已经具备雏形，但还没有成为真正的数据入口和选择入口。现在它更像是“平台级数据资产目录”，而不是实际数据处理链路的唯一事实源。

MVP 中可以接受这种过渡，但下一轮必须把上传数据接到 Dataset Asset，否则 Dataset 这个概念会变成“有表、有 API，但用户实际用不上”。

## 4. Study 支持情况

### 已经支持

当前 `projects` 基本承担 Study 语义：

1. Study/Project 有 owner、状态、存储根目录和配额字段。
2. `project_members` 支持成员角色和 `can_read`、`can_write`、`can_delete`、`can_export`、`can_run`。
3. `study_locks` 支持运行锁，有 `expires_at`，可以避免异常后永久占用。
4. `audit_events` 记录上传、运行、挂载等关键事件。
5. Study 可以挂载 Dataset Asset。
6. Router 层已经有项目创建、成员管理、项目恢复、项目删除等基础能力。

### 主要不足

1. 命名仍然是 Project。
   代码、API、DB 主表仍叫 `projects`。如果产品上确定叫 Study，可以先保持底层兼容，但 API 和文档需要逐步暴露 `/studies` 别名。

2. Study Mount 管理不完整。
   目前有创建和列表，缺少更新、禁用、删除、重命名、调整 selection_json 的接口。

3. Study 设置缺失。
   没有 `study_settings` 表保存运行并发策略、默认数据选择策略、Artifact 保留策略、默认 QC 策略、存储策略等。

4. 运行锁只接在 Pipeline Run 上。
   目前有 run lock，但 Pipeline 编辑、Dataset 重传、Artifact 清理、挂载修改等操作是否互斥，还没有统一策略。

5. 物理级联删除风险较高。
   多个关键表对 `projects`、`pipeline_runs` 使用 `ON DELETE CASCADE`。如果未来误触发硬删除，会破坏可追溯性。产品上应尽量只软删除，硬删除只能走后台治理流程。

6. 审计体系有分裂。
   目前同时有 `audit_events` 和 `project_audit_events`。建议长期统一到 `audit_events`，把 `event_scope`、`resource_kind`、`metadata` 作为通用审计模型。

### Study 判断

Study 对 MVP 支持是比较够的。主要问题不是缺少基础能力，而是命名和治理边界还没有完全统一。短期可以继续用 `projects` 表，但产品语义和 API 文档应该统一叫 Study。

## 5. Pipeline 支持情况

### 已经支持

1. `pipeline_definitions` 保存 Pipeline 当前定义。
2. Pipeline 有 `version` 字段，每次更新递增。
3. 更新接口支持可选 `expected_version`，可用于前端处理并发编辑冲突。
4. Run 创建时会写入 `pipeline_version` 和 `definition_snapshot`，使历史 Run 不依赖 Pipeline 的当前定义。
5. Pipeline delete 是逻辑删除，将 `status` 设为 `deleted`。
6. Pipeline validate 可以解析 LoadData 等节点，提前发现部分输入问题。

### 主要不足

1. 没有不可变 Pipeline Version 表。
   当前 Run 靠 `definition_snapshot` 保留历史定义，这对 MVP 足够，但如果后续要比较版本、回滚版本、引用某个固定 Pipeline 版本、多人协作审计，就应该新增 `pipeline_versions`。

2. `expected_version` 是可选的。
   如果前端不传，后端仍会接受更新。多人编辑时，建议前端强制传，后端也可以对关键更新强制要求。

3. 没有 Pipeline 编辑锁。
   目前只对运行加锁。多人同时编辑同一个 Pipeline 时，主要靠版本冲突，不够直观。建议增加 edit lock 或至少记录 active editor。

4. Pipeline status 约束不够严格。
   代码中使用 `deleted`，创建时使用 `active`，文档中可能还会出现 draft/archived 等语义。数据库没有明确 CHECK 约束，长期应统一枚举。

5. Pipeline 与 Dataset Mount 的输入契约还没有建立。
   Pipeline 定义中 LoadData 节点可以选数据，但它不知道自己来自哪个 Dataset Asset 或哪个 Mount。后续应该让 LoadData 支持 `mount_id`、`mount_name`、`dataset_asset_id` 或 selection snapshot。

### Pipeline 判断

Pipeline 对单人或轻协作 MVP 是可用的。它已经通过 Run 的 `definition_snapshot` 避免了“当前 Pipeline 改了导致历史 Run 失真”的问题。下一步重点是不可变版本和编辑协作，而不是立即重写 Pipeline 表。

## 6. Run 支持情况

### 已经支持

1. `pipeline_runs` 保存一次执行的主体信息。
2. `pipeline_node_runs` 保存节点级执行状态、输入输出、错误、trace_code。
3. `pipeline_run_inputs` 在 Run 创建或 prepare 阶段冻结 LoadData 解析结果。
4. `pipeline_artifacts` 保存输出文件，支持 `storage_uri`、`sha256`、`retention_status`、`deleted_at`、`last_accessed_at`。
5. `async_tasks` 记录 Celery 任务，`task_events` 记录任务状态变化。
6. Run detail API 已经能返回 inputs、tasks、node_runs、artifacts。
7. Pipeline Run 派发失败时会记录失败事件并释放运行锁。

### 主要不足

1. 没有 Run Manifest 一等对象。
   目前 Run 信息分散在 `pipeline_runs.definition_snapshot`、`pipeline_run_inputs`、`pipeline_artifacts`、`async_tasks` 中。技术上可追溯，但缺少一个明确的 manifest JSON 或 manifest artifact，方便导出、复现和对外解释。

2. Run 依赖保护不足。
   如果 pipeline2 的 run2 输出被 pipeline3 的 run3 使用，目前可以通过 `pipeline_run_inputs.upstream_run_id` 和 `upstream_artifact_id` 表达，但业务链路还没有系统写入和检查。删除 run2 或清理 artifact 时，缺少下游依赖保护。

3. 没有统一任务 API。
   Run detail 会带出 tasks，但还没有通用的 `/tasks/{task_id}`、取消、重试、事件列表等接口。

4. Artifact retention 字段已经有了，但服务还没闭环。
   还缺少 pin/unpin、标记删除、后台清理、访问更新时间策略、按 Study 配置保留策略等。

5. 物理删除仍可能破坏 Run 追溯。
   `pipeline_runs`、`pipeline_node_runs`、`pipeline_artifacts`、`pipeline_run_inputs` 等存在级联关系。产品层必须避免普通用户硬删除 Run。

6. Task 状态和 Run 状态之间还需要标准化映射。
   例如 `completed` 映射为 task `succeeded`，`waiting_user_input` 当前也算 task `succeeded`。这可以接受，但需要在 API 文档中明确。

### Run 判断

Run 是目前四个对象中最接近 MVP 闭环的部分。输入快照、任务事件、Artifact 记录都已经有正确方向。主要风险集中在“Run 之间的依赖”和“输出清理策略”。

## 7. 逐项问题汇总

优先级说明：

- P0：会直接影响协作追溯、数据安全或 Run 依赖正确性。
- P1：MVP 重要缺口，短期应该补。
- P2：不一定阻塞 MVP，但会影响长期一致性、维护性或体验。

| 编号 | 优先级 | 对象 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- | --- | --- |
| DB-DS-01 | P0 | Dataset | `dataset_assets` 没有和实际上传的 `datasets` / `dataset_uploads` 建立关系。 | Dataset 概念容易变成目录壳，实际处理仍绕过 Dataset。 | MVP 可先给 `datasets` 增加 `dataset_asset_id`，或新增 `dataset_asset_recordings` 关系表。上传时自动关联一个 working Dataset Asset。 |
| DB-DS-02 | P0 | Dataset | `LoadData` 不从 Study Mount / Dataset Asset 解析数据。 | Study 挂载 Dataset 后，Pipeline 仍不能自然使用挂载数据。 | LoadData 增加 `mount_id`、`mount_name`、`dataset_asset_id` 选择入口，再解析到 recording/dataset/file。 |
| DB-DS-03 | P1 | Dataset | `dataset_files.dataset_id` 和 `dataset_upload_id` 都是非空，强绑定 legacy 上传版本。 | 未来 Derived Dataset、Asset 级文件、跨 Study 文件引用不够灵活。 | 保持 MVP 不动；下一阶段设计 `recording_version_files` 或允许 `dataset_files` 支持 asset/file link。 |
| DB-DS-04 | P1 | Dataset | 没有 Dataset Asset Version。 | 发布、下架、引用固定版本、伦理冻结无法完整表达。 | MVP 暂缓发布可以不做；表设计预留 `dataset_asset_versions`。 |
| DB-DS-05 | P1 | Dataset | Dataset 权限只有 owner/created_by/visibility。 | 共享、协作、授权撤销、机构内访问规则不足。 | 后续增加 `dataset_members`、`dataset_shares` 或统一 resource ACL。 |
| DB-DS-06 | P1 | Dataset | 大规模 EEG 选择缺少事件、marker、segment 索引。 | 4000 被试、多 session/run、多 marker 分割后，前端选择器难以高效工作。 | 增加 `recording_events`、`recording_segments` 或 `recording_index` 物化索引。 |
| DB-DS-07 | P1 | Dataset | 上传、扫描、FIF 转换没有进入 `async_tasks` 体系。 | 大文件上传和转换难以追踪、重试和审计。 | 增加 `dataset_import` / `dataset_convert` 任务类型，复用 `async_tasks` 和 `task_events`。 |
| DB-DS-08 | P2 | Dataset | QC 可选，但 LoadData 默认只选 `converted`、`checked`。 | 未检查但可用的数据默认不会进入分析，和产品语义略冲突。 | 默认改为不过滤 QA，或在 UI 明确提供“仅已转换/已检查”和“包含未检查”。 |
| DB-DS-09 | P2 | Dataset | 历史数据是否完整回填 `dataset_files` 还不确定。 | 旧数据的 Run 输入快照可能只能记录 dataset，不能记录精确 file。 | 做一次 backfill 脚本和统计检查。 |
| DB-ST-01 | P1 | Study | 底层仍叫 `projects`，产品语义叫 Study。 | API、文档、代码命名容易混乱。 | 短期保持 DB 表不改，新增 `/studies` API 别名和文档统一；长期再迁移命名。 |
| DB-ST-02 | P1 | Study | Study Mount 只有创建和列表。 | 挂载错误、重命名、禁用、调整选择范围不方便。 | 增加更新、禁用、删除、审计接口。 |
| DB-ST-03 | P1 | Study | 缺少 Study 设置表。 | 默认 QC、运行并发、保留策略、存储策略只能散落在代码或前端。 | 增加 `study_settings`，保存运行策略、数据选择默认值、Artifact retention policy。 |
| DB-ST-04 | P0 | Study | 多个关键表存在 `ON DELETE CASCADE`，硬删除会破坏追踪链。 | 用户或管理操作误删可能导致 Run 历史消失。 | 普通业务只允许软删除；硬删除仅平台治理后台执行，并先检查依赖。 |
| DB-ST-05 | P2 | Study | `audit_events` 和 `project_audit_events` 并存。 | 审计查询和行为分析会分裂。 | 统一到 `audit_events`，保留兼容视图或迁移旧表数据。 |
| DB-PL-01 | P1 | Pipeline | 没有不可变 `pipeline_versions`。 | 历史比较、回滚、版本发布、多人协作审计不足。 | 新增 `pipeline_versions`，Run 引用 `pipeline_version_id`；保留当前 `definition_snapshot`。 |
| DB-PL-02 | P2 | Pipeline | `expected_version` 不是强制。 | 前端漏传时仍可能覆盖别人编辑。 | 对 Pipeline 更新强制要求 `expected_version`，或引入 edit lock。 |
| DB-PL-03 | P1 | Pipeline | 没有 Pipeline 编辑锁。 | 多人同时编辑体验不清晰。 | `study_locks` 支持 `resource_kind=pipeline`、`lock_type=edit`，前端显示谁正在编辑。 |
| DB-PL-04 | P2 | Pipeline | Pipeline status 枚举没有数据库约束。 | `active`、`deleted`、`draft`、`archived` 等状态可能漂移。 | 增加 CHECK 约束，统一 schema 和 API 枚举。 |
| DB-PL-05 | P1 | Pipeline | Pipeline 定义中没有明确 Dataset Mount 输入契约。 | 工作流无法稳定表达“使用 Study 挂载的哪个 Dataset”。 | LoadData 节点参数支持 mount-based selector，并在 Run input snapshot 中保存。 |
| DB-RUN-01 | P1 | Run | 没有通用 Task API。 | 前端难以独立展示任务进度、取消、重试和事件流。 | 增加 `/api/v1/projects/{study_id}/tasks`、`/tasks/{task_id}`、cancel、retry。 |
| DB-RUN-02 | P1 | Run | 没有 Run Manifest 一等对象。 | 对外解释、导出复现、问题排查不够直接。 | Run 完成后生成 `run_manifest.json`，同时写 artifact 或 `pipeline_runs.manifest_json`。 |
| DB-RUN-03 | P0 | Run | Run 与 Run、Artifact 与 Artifact 的下游依赖没有系统保护。 | run3 依赖 run2 时，run2 输出被清理会污染结果。 | 新增 `pipeline_run_dependencies` 或强化 `pipeline_run_inputs.upstream_*` 写入，并在删除/清理前检查。 |
| DB-RUN-04 | P1 | Run | Artifact retention 字段有了，但没有服务闭环。 | 数据量增长后无法安全清理，也无法保护重要输出。 | 增加 pin/unpin、mark deleted、cleanup job、last_accessed_at 更新策略。 |
| DB-RUN-05 | P2 | Run | Run status 和 Task status 映射需要文档化。 | UI 显示可能混乱，尤其是 `waiting_user_input`。 | 在 API 文档中定义状态机和映射规则。 |
| DB-RUN-06 | P1 | Run | 缺少 PostgreSQL + FastAPI + Celery 的真实集成回归。 | 目前编译和单测通过，但不能完全证明真实数据库约束和异步链路。 | 增加 docker compose 或测试数据库集成测试。 |
| DB-SQL-01 | P2 | Schema | baseline schema 末尾仍有 `ALTER TABLE datasets ALTER COLUMN fif_path DROP NOT NULL;`。 | 不是功能错误，但 baseline 和 migration 职责混杂。 | 将此类兼容 ALTER 移到 migration 文件，baseline 只保留目标态 schema。 |

## 8. 对“是否较好支持”的直接回答

### Dataset

还不能算较好支持。它已经有正确的数据库雏形，但还没有接管实际上传、选择和使用链路。

判断理由：

- 有 `dataset_assets`、`study_dataset_mounts`、`dataset_files`。
- 但上传主链路仍是 `projects -> subjects -> datasets -> dataset_uploads`。
- LoadData 仍从 Project 内 legacy datasets 查询，不认 Dataset Mount。

建议下一步先做“最小接线”：

1. 每个 Study 可以有一个默认 working Dataset Asset。
2. 上传 Recording 时必须关联一个 Dataset Asset。
3. Study Mount 的 Dataset Asset 能被 LoadData 使用。

### Study

MVP 基本支持。当前 Project 已经承担 Study，大体够用。

判断理由：

- 有成员表、权限字段、can_run、运行锁、审计、软删除/恢复能力。
- 有 Dataset Mount。

短板是：

- 产品名和底层名不统一。
- Study 设置缺失。
- 挂载管理不完整。
- 硬删除级联风险要从产品层禁掉。

### Pipeline

MVP 可以支持，但协作版本管理还不够强。

判断理由：

- 有 Pipeline 定义、版本号、Run 快照。
- 历史 Run 不依赖当前 Pipeline，这点是正确的。

短板是：

- Pipeline 本体可变，没有不可变版本表。
- 多人编辑主要靠可选 expected_version，没有锁和强制版本校验。
- LoadData 输入还没有绑定 Dataset Mount。

### Run

四者里 Run 支持最好，但还没到完整治理。

判断理由：

- 有 Run、Node Run、Input Snapshot、Artifact、Async Task、Task Event。
- 创建 Run 时会保存 LoadData 实际解析结果，方向正确。

短板是：

- 没有 Run Manifest。
- 没有下游依赖保护。
- 没有任务取消/重试 API。
- Artifact retention 还只是字段，不是完整服务。

## 9. 推荐的下一步实施顺序

### 第一阶段：让 Dataset 真正可用

目标：让 Dataset Asset 不再只是目录，而是真正成为数据入口。

建议任务：

1. 新增 `datasets.dataset_asset_id` 或 `dataset_asset_recordings` 关系表。
2. 上传时自动创建或选择一个 working Dataset Asset。
3. LoadData 支持从 `study_dataset_mounts` 解析数据。
4. `pipeline_run_inputs` 保存 mount、asset、recording、upload、file 的完整快照。
5. 给 Dataset 文件索引增加查询 API，方便前端做数据选择器。

### 第二阶段：保护 Run 依赖和输出

目标：避免“run3 依赖 run2，但 run2 被删或输出被清理”的问题。

建议任务：

1. 新增 `pipeline_run_dependencies`，或系统化写入 `pipeline_run_inputs.upstream_run_id/upstream_artifact_id`。
2. 删除 Run、清理 Artifact 前检查下游依赖。
3. Artifact 增加 pin/unpin/cleanup API。
4. 生成 `run_manifest.json`。

### 第三阶段：补齐任务系统

目标：把长耗时动作都纳入 async task。

建议任务：

1. 增加通用 Task 查询 API。
2. 支持 task events 分页查询。
3. Pipeline Run 支持 cancel/retry。
4. Dataset import/convert 也纳入 `async_tasks`。

### 第四阶段：增强协作和版本

目标：支持多人协作、版本回溯和稳定复现。

建议任务：

1. 新增 `pipeline_versions`。
2. Pipeline 更新强制 `expected_version`。
3. 使用 `study_locks` 支持 Pipeline edit lock。
4. 新增 `study_settings`。
5. 增加 `/studies` API 别名。

### 第五阶段：为共享发布预留治理

目标：未来支持数据分享、伦理下架和版本冻结。

建议任务：

1. 新增 `dataset_asset_versions`。
2. 新增 Dataset ACL 或 Dataset members。
3. 支持下架、隔离、冻结引用。
4. 引入平台治理审计和管理员复核流程。

## 10. MVP 建议边界

如果当前仍然是 MVP，我建议先不要把 Dataset 发布、不可变版本、外部共享一次性做完。

MVP 的合理边界可以是：

1. 所有 Dataset 都是 working 状态。
2. 不做公开发布。
3. 不做外部共享。
4. Study 内可以挂载 Dataset Asset。
5. Pipeline Run 必须记录输入快照。
6. Run 元数据永久保留，Artifact 可按保留策略清理。
7. 普通用户不能物理删除会影响追溯的 Run 和 Artifact。
8. Dataset 上传、Pipeline Run、Artifact 清理都写审计。

这样既不会过度设计，又能把你最担心的“多人协作污染数据结果”和“Run 依赖断裂”先管住。

## 11. 最小数据库改造建议

如果只选最小的一组数据库改动，建议优先级如下：

1. `datasets` 增加 `dataset_asset_id UUID REFERENCES dataset_assets(id) ON DELETE RESTRICT`。
2. 新增 `study_settings`。
3. 新增 `pipeline_run_dependencies`。
4. 新增 `pipeline_versions`，但可以先只写不强制用。
5. 新增或强化 `run_manifest_json` 字段，或者把 manifest 写成 `pipeline_artifacts.artifact_type='run_manifest'`。

其中第 1 和第 3 最关键：

- 第 1 个解决 Dataset Asset 和实际数据脱节。
- 第 3 个解决 Run 链式依赖和删除清理风险。

## 12. 最终判断

当前数据库设计已经从“项目内上传文件并运行 Pipeline”升级到了“有 Dataset Asset、Study Mount、Run Input Snapshot、Async Task、Artifact Retention 的平台雏形”。

但真正的系统边界还需要继续收紧：

- Dataset 要成为数据资产事实源。
- Study 要成为协作和挂载边界。
- Pipeline 要成为可版本化的工作流定义。
- Run 要成为不可篡改、可追溯、可复现的执行事实。

当前最值得投入的不是重命名或大拆表，而是补上 Dataset Asset 到 Recording、Study Mount 到 LoadData、Run 到 Artifact Dependency 这三条关键连接。
