# 工作流图示页面规划

> 目标：把工作流专题中复杂的架构、执行、缓存、调度和人工交互机制拆成一组可插入文档的技术图。每张图只讲一个问题，便于前端、后端、算法和运维人员快速对齐。

## 1. 生成策略

本组图采用“确定性技术图优先，image2 美化版可选”的方式。

- 主交付：可控 PNG 技术图，保证中文标签、状态名、表名和箭头关系准确。
- 可选补充：如果后续要做汇报封面或宣传版，可再用 image2 生成更强视觉风格的插画版。
- 当前图片目录：`images/workflow/`
- 正式 wiki 复用目录：`wiki/docs/assets/workflow/`

## 2. 建议设计 9 张图

| 序号 | 图片文件名 | 图名 | 解决的问题 | 建议插入文档 |
|---:|---|---|---|---|
| 01 | `workflow-01-overview.png` | 工作流整体架构图 | 前端、API、数据库、Redis/Celery、执行器、算法引擎、文件系统之间怎么协作 | `05-工作流程序架构与实施方案.md` |
| 02 | `workflow-02-definition-contract.png` | 工作流定义与 NodeSpec 契约 | NodeSpec 如何变成前端节点，PipelineDefinition 如何保存，Validator 校验什么 | `03-工作流节点规范与数据结构.md` |
| 03 | `workflow-03-editor-save-validate.png` | 编辑器保存与校验流程 | 用户编辑画布后，前端如何保存 definition，后端如何做静态校验和 LoadData 解析 | `02-工作流编辑器交互与用户行为定义.md` |
| 04 | `workflow-04-run-lifecycle.png` | 一次 PipelineRun 生命周期 | 点击运行后，pipeline_runs、pipeline_node_runs、状态流转和前端进度如何串起来 | `08-工作流当前进度与开发路线.md` |
| 05 | `workflow-05-executor-internals.png` | PipelineExecutor 内部执行逻辑 | 拓扑排序、输入解析、hash、缓存、dispatch、artifact 写入的真实顺序 | `04-工作流执行缓存与增量运行设计.md` |
| 06 | `workflow-06-redis-celery-scheduler.png` | Redis/Celery 后台调度架构 | API、Redis 队列、Scheduler、Worker、进度推送、DB 事实源的边界 | `10-Redis后台任务与工作流调度架构.md` |
| 07 | `workflow-07-cache-incremental.png` | 缓存与增量运行机制 | node_hash / traceCode / input hash 如何决定缓存命中，哪些下游需要重跑 | `04-工作流执行缓存与增量运行设计.md` |
| 08 | `workflow-08-artifact-lineage.png` | Artifact 与结果追溯链路 | 从上传版本到 pipeline_artifacts、derivatives、analysis_results、观察/统计/作图/ML 的追溯关系 | `06-FIF数据导入校正规则.md` |

## 3. 建议阅读顺序

1. 先看 `workflow-01-overview.png`，建立全局架构。
2. 再看 `workflow-04-run-lifecycle.png`、`workflow-05-executor-internals.png`、`workflow-06-redis-celery-scheduler.png`，理解运行闭环。
3. 然后看 `workflow-02-definition-contract.png`、`workflow-03-editor-save-validate.png`，理解编辑器和 NodeSpec 契约。
4. 最后看 `workflow-07-cache-incremental.png`、`workflow-08-artifact-lineage.png`、`workflow-09-human-node-and-recovery.png`，补齐缓存、结果追溯和人工节点细节。

## 5. image2 美化版提示词

如果后续需要用 image2 生成汇报版或封面版，建议每张图使用统一约束：

```text
Use case: scientific-educational infographic-diagram
Asset type: technical architecture diagram for software engineers
Style: clean vector-like technical diagram, white background, precise boxes and arrows, no decorative clutter
Language: Simplified Chinese labels, short exact technical terms only
Layout: landscape 16:9, clear sections, consistent color coding
Color coding: frontend blue, API green, database purple, queue orange, executor teal, filesystem gray, error red
Constraints: no fake code, no tiny unreadable paragraphs, no watermark, no extra icons unless they clarify the architecture
```

注意：image2 对中文小字和精确表名不一定稳定。当前这 9 张技术主图优先保证研发沟通的准确性。
