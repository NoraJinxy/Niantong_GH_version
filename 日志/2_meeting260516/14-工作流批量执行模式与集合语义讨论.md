# 工作流批量执行模式与集合语义讨论

> 文档性质：工作流专题讨论稿。本文记录关于 Pipeline 节点批量执行、集合输入输出、N->N / N->1 等语义的讨论，用于后续回写 NodeSpec、执行器、缓存和前端交互设计。
>
> 讨论背景：当前 `elys_version1` 代码里已经在 NodeSpec 的端口上写了 `cardinality`，例如 `one_or_many`、`same_as_input`、`many`。但目前它更多是描述性字段，后端校验还没有真正理解批量执行、分组、配对、集合级建模和统计设计。

## 1. 核心结论

Pipeline 节点不能只按表面输入输出数量分类。

例如：

- `FIR Filter` 看起来是 N -> N。
- `公共 ICA` 也可能看起来是 N -> N。

但二者本质不同：

- `FIR Filter` 是单个数据集独立计算，N -> N 只是 1 -> 1 重复 N 次。
- `公共 ICA` 是 N 个数据集共同参与一次模型拟合，再把公共模型应用回每个数据集。

因此，真正需要进入程序模型的不是单纯的 `N->N`、`N->1`，而是：

1. 端口类型：能不能连接。
2. 输入输出形状：整体看是 1->1、1->N、N->1、N->N。
3. 执行作用域：一次计算吃一个 item、一个 pair、一个 group，还是整个 collection。
4. 输入组织规则：是否需要 `group_by`、`match_by`、实验设计矩阵。
5. 缓存粒度：按 item、pair、group、collection，还是 model + applied item 分开缓存。

建议最终 NodeSpec 里保留 `cardinality` 作为展示层，同时新增 `execution` 契约作为执行层事实。

## 2. 当前代码中的不足

当前 NodeSpec 里已有类似：

```json
{
  "inputs": [
    {"name": "input", "type": "eeg_data", "cardinality": "one_or_many"}
  ],
  "outputs": [
    {"name": "output", "type": "eeg_data", "cardinality": "same_as_input"}
  ]
}
```

这能表达“这个节点可以接收多个输入，并返回对应输出”，但还不能回答：

- 是每个输入独立处理，还是所有输入一起处理？
- 输入集合顺序是否影响结果？
- 一个输入是否会拆成多个输出？
- 多个输入如何配对？
- 多个条件如何组成统计设计？
- 缓存命中时按单个输入恢复，还是整个集合一起恢复？
- 某个输入失败时，是否允许其它输入继续？
- 输出里的 `condition`、`group`、`subject` 等 key 如何生成和继承？

这些问题不解决，后续做缓存、增量运行、人工节点、统计、作图和 ML 时会不断返工。

## 3. 两个维度：shape 与 execution scope

建议把节点语义拆成两个维度。

### 3.1 输入输出形状 shape

shape 用于描述整体数量关系，适合前端展示和用户理解。

| shape | 含义 | 例子 |
| --- | --- | --- |
| `1 -> 1` | 一个输入产生一个输出 | 单文件滤波、重采样 |
| `1 -> N` | 一个输入拆出多个输出 | 一个 raw 按 marker 拆成多个 condition epochs |
| `N -> 1` | 多个输入汇总成一个输出 | Merge、GrandAverage、统计表 |
| `N -> N` | 多个输入产生对应多个输出 | 批量滤波、公共模型应用回每个数据集 |
| `N -> M` | 多个输入产生多个非一一对应输出 | 跨被试聚类、微状态模板 + 回填结果、多条件统计 |

### 3.2 执行作用域 scope

scope 决定执行器如何调用节点函数。

| scope | 一次计算吃什么 | 程序含义 |
| --- | --- | --- |
| `item` | 单个 `data_info` / artifact | 可以逐个并行、逐个缓存、逐个失败 |
| `pair` | 配对后的两个或多个 item | 需要先按 key 匹配 |
| `group` | 同一 group 内的一组 item | 需要先 group_by |
| `collection` | 整个输入集合 | 需要整体 hash，通常不能随意拆开 |
| `design` | 带实验设计矩阵的集合 | 统计/ML 需要 subject、condition、group 等设计变量 |

同样是 `N -> N`，scope 不同，程序实现完全不同。

## 4. 建议的执行模式

建议把最初的 6 类模式进一步细化为下面 6 类。

| 执行模式 | shape | scope | 含义 | 典型节点 |
| --- | --- | --- | --- | --- |
| `item_map` | N -> N | item | 1->1 重复 N 次 | FIR、Resample、Re-reference |
| `item_expand` | N -> M | item | 每个输入可拆成多个输出 | Epoch、按 condition 切分 |
| `collection_reduce` | N -> 1 或 N -> G | group/collection | 多个输入共同汇总 | Merge、GrandAverage |
| `collection_transform` | N -> N 或 N -> M | collection | 整组共同拟合模型，再回写/转换每个 item | 公共 ICA、公共空间模型、跨被试聚类标签回填 |
| `join_map` | 多路 N -> N 或 N -> M | pair/group | 多路输入按 key 配对后逐对计算 | 差异波、A-B、配对 T 检验前处理 |
| `design_reduce` | N -> stats | design | 按实验设计汇总统计 | ANOVA、组间比较、重复测量统计 |

其中：

- `group_reduce` 可以看成带 `group_by` 的 `collection_reduce`。
- `pairwise` 可以看成带 `match_by` 的 `join_map`。
- `multi_input_reduce` 可以看成带多个输入角色和设计矩阵的 `design_reduce`。

## 5. 为什么不能只用 N->N / N->1

### 5.1 N->N 的两种完全不同情况

#### 情况 A：1->1 重复 N 次

```text
sub-001 raw -> sub-001 filtered
sub-002 raw -> sub-002 filtered
sub-003 raw -> sub-003 filtered
```

特点：

- 每个输入彼此独立。
- 可以并行。
- 可以单个输入缓存命中。
- 一个 subject 失败时，其它 subject 可能继续。
- 缓存粒度是 item。

适合：

- FIR Filter
- Butterworth Filter
- Resample
- Re-reference
- 单被试 ICA Compute

#### 情况 B：N 个输入共同拟合一次模型，再输出 N 个结果

```text
sub-001 raw \
sub-002 raw  -> fit shared model -> shared model -> apply to sub-001 cleaned
sub-003 raw /                                      -> apply to sub-002 cleaned
                                                   -> apply to sub-003 cleaned
```

特点：

- 输入集合整体影响模型。
- 不可简单逐个并行 fit。
- 新增一个 subject 可能导致整个模型变化。
- 缓存粒度至少包括 collection-level model hash。
- 输出虽然是 N 个，但每个输出都依赖整个输入集合。

适合：

- 公共 ICA
- 公共空间模型
- 统一模板拟合
- 跨被试聚类后给每个 subject 回填 label

这两种都可以显示成 N->N，但执行器必须区分。

### 5.2 N->1 也不是一个概念

以下都可能是 N->1，但含义不同：

| 场景 | 关键差异 |
| --- | --- |
| Merge | 主要是数据拼接或集合登记 |
| GrandAverage | 需要同一数据类型、同一 condition、同一时间轴/通道空间 |
| ANOVA | 需要实验设计矩阵、subject 配对、condition/group 因子 |
| 训练 ML 模型 | 需要训练/验证切分、防止数据泄漏 |
| 公共模板拟合 | 输出模板，还可能要回填每个输入 |

所以 N->1 只能作为 shape，不能作为执行模式。

## 6. 建议的 NodeSpec execution 契约

建议在 NodeSpec 中新增：

```json
"execution": {
  "operator": "item_map",
  "scope": "item",
  "input_policy": "one_or_many",
  "output_policy": "same_as_input",
  "cache_grain": "item"
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `operator` | 执行模式：`item_map`、`item_expand`、`collection_reduce`、`collection_transform`、`join_map`、`design_reduce` |
| `scope` | 一次调用的输入范围：`item`、`pair`、`group`、`collection`、`design` |
| `input_policy` | 接收一个还是多个输入 |
| `output_policy` | 输出数量与输入数量的关系 |
| `group_by` | 分组聚合使用的 key |
| `match_by` | 配对计算使用的 key |
| `design` | 统计模型或 ML 模型使用的实验设计 |
| `cache_grain` | 缓存粒度 |
| `failure_policy` | 部分失败时是否继续 |
| `ordering` | 输入集合是否需要稳定排序 |

## 7. 典型节点建议

### 7.1 FIR Filter：`item_map`

```json
"execution": {
  "operator": "item_map",
  "scope": "item",
  "input_policy": "one_or_many",
  "output_policy": "same_as_input",
  "cache_grain": "item",
  "failure_policy": "per_item"
}
```

执行含义：

```text
for item in input.items:
  output_item = run_fir_filter(item, params)
```

### 7.2 Epoch：`item_expand`

```json
"execution": {
  "operator": "item_expand",
  "scope": "item",
  "input_policy": "one_or_many",
  "output_policy": "one_to_many",
  "split_by": "event_id",
  "output_keys": ["subject", "session", "task", "run", "condition"],
  "cache_grain": "item"
}
```

执行含义：

```text
sub-001 raw
  -> sub-001 target epochs
  -> sub-001 standard epochs
  -> sub-001 deviant epochs
```

注意：

- `condition` 必须进入 `data_infos`。
- 同一个 raw 输出多个 epochs 时，每个输出都应有独立 `artifact_id`。
- `event_id`、`tmin/tmax`、baseline 都参与 hash。

### 7.3 Merge：`collection_reduce`

```json
"execution": {
  "operator": "collection_reduce",
  "scope": "collection",
  "input_policy": "many",
  "output_policy": "one",
  "cache_grain": "collection",
  "ordering": "stable_by_keys"
}
```

注意：

- 输入集合必须稳定排序，否则同一组数据可能产生不同 hash。
- 需要明确合并维度：time、subject、condition、run，还是只登记为 collection。
- 合并不是简单连线聚合，要明确输出 artifact 的真实语义。

### 7.4 差异波：`join_map`

```json
"execution": {
  "operator": "join_map",
  "scope": "pair",
  "input_policy": "two_collections",
  "match_by": ["subject", "session", "task", "run"],
  "operation": "left_minus_right",
  "output_policy": "same_as_pairs",
  "cache_grain": "pair"
}
```

执行含义：

```text
target[sub-001] - standard[sub-001] -> diff[sub-001]
target[sub-002] - standard[sub-002] -> diff[sub-002]
```

注意：

- 它不应该简单理解为 N->1。
- 关键是 `match_by`。
- 缺失配对时需要策略：报错、跳过、还是产生 warning。

### 7.5 ANOVA：`design_reduce`

```json
"execution": {
  "operator": "design_reduce",
  "scope": "design",
  "input_policy": "many",
  "design": {
    "subject_key": "subject",
    "within": ["condition"],
    "between": ["group"]
  },
  "output_policy": "stats_table",
  "cache_grain": "collection"
}
```

注意：

- ANOVA 的重点不是 N->1，而是实验设计。
- 需要 subject 配对、condition、group、缺失值策略、多重比较校正。
- 输出也不一定只是一个表，可能还包括 effect map、p-value map、cluster mask、posthoc contrasts。

## 8. 复杂场景展开

下面几个场景表面上经常被写成 N->M 或 N->1，但真实执行逻辑更复杂。

## 8.1 跨被试聚类

### 8.1.1 场景说明

跨被试聚类是把多个被试的特征放到同一个特征空间里，统一做聚类。

输入可能是：

- 每个被试的 ERP 特征。
- 每个被试的 PSD 频段特征。
- 每个被试的 TFR 时间频率特征。
- 每个被试的连接矩阵。
- 每个被试的微状态 map。
- 每个被试的源空间特征。

输出可能是：

- 全局 cluster centers。
- 每个 subject / condition 的 cluster label。
- 每个 cluster 的统计摘要。
- 聚类质量指标，例如 silhouette、inertia、stability。
- 用于作图的二维嵌入，例如 UMAP/t-SNE 坐标。

### 8.1.2 为什么不是简单 N->1

如果只把它理解为 N->1，会丢掉很多必要输出。

真实结构更像：

```text
N 个 subject feature
  -> fit clustering model once
  -> K 个 cluster centers
  -> N 个 subject labels
  -> cluster summary table
  -> optional embedding / quality metrics
```

所以它更适合：

```text
operator = collection_transform
scope = collection
output_policy = model_plus_item_annotations
```

### 8.1.3 程序实现要点

输入集合必须先标准化：

- 所有 item 是否有相同 channel 空间。
- 是否有相同 time/frequency 维度。
- 是否需要 baseline normalize。
- 是否需要 z-score。
- 是否按 subject 内标准化，还是全体一起标准化。
- 是否允许缺失 channel / condition。

需要明确聚类对象：

| 聚类对象 | item 粒度 |
| --- | --- |
| subject-level feature | 每个 subject 一个向量 |
| subject-condition feature | 每个 subject + condition 一个向量 |
| time point / map | 每个 subject 的多个 map 参与聚类 |
| connectivity matrix | 每个矩阵拉平成一个特征向量 |

缓存建议：

- 聚类模型缓存按整个 input collection。
- 如果输入集合新增或删除一个 item，模型一般失效。
- 如果只改可视化参数，不应重算聚类模型。
- 如果改 `n_clusters`、distance metric、normalization，必须重算。

输出建议：

```json
{
  "type": "cluster_result",
  "items": [
    {
      "artifact_id": "cluster_model",
      "artifact_kind": "model",
      "n_clusters": 4,
      "feature_space": "erp_time_window"
    },
    {
      "artifact_id": "sub001_label",
      "subject": "sub-001",
      "condition": "target",
      "cluster_label": 2
    }
  ]
}
```

### 8.1.4 NodeSpec 草案

```json
{
  "type": "eeg/ml/cross_subject_clustering",
  "inputs": [
    {"name": "features", "type": "analysis_result", "cardinality": "many"}
  ],
  "outputs": [
    {"name": "model", "type": "ml_model"},
    {"name": "labels", "type": "cluster_result"},
    {"name": "summary", "type": "stats_table"}
  ],
  "execution": {
    "operator": "collection_transform",
    "scope": "collection",
    "input_policy": "many",
    "output_policy": "model_plus_annotations",
    "group_by": ["condition"],
    "cache_grain": "collection"
  }
}
```

## 8.2 微状态模板

### 8.2.1 场景说明

EEG 微状态通常需要从每个被试的 EEG 中提取空间拓扑图，再聚类得到若干典型 microstate maps。

常见流程：

```text
每个 subject raw/cleaned EEG
  -> 选取 GFP peaks 或候选 topographies
  -> 个体层面聚类得到 individual maps
  -> 跨被试汇总 maps
  -> 聚类得到 group-level microstate templates
  -> 把模板 backfit 回每个 subject
  -> 输出每个 subject 的 time labels 和统计指标
```

### 8.2.2 为什么不是简单 N->1

微状态模板不是“多个输入合成一个结果”这么简单。

它至少有三类输出：

1. 群体模板：K 个 microstate maps。
2. 个体回填结果：每个 subject 的时间点 label 序列。
3. 统计指标：duration、coverage、occurrence、transition matrix、GEV。

所以它更像：

```text
N EEG -> fit group template -> template K maps + N fitted label sequences + stats
```

执行模式建议：

```text
operator = collection_transform
scope = collection
output_policy = template_plus_fitted_items
```

### 8.2.3 程序实现要点

必须定义一致性要求：

- 通道集合一致。
- 通道顺序一致。
- 参考方式一致。
- montage 一致。
- 采样率和滤波范围尽量一致。
- 极性处理策略一致：是否 polarity invariant。
- topography normalization 策略一致。

关键参数：

| 参数 | 含义 |
| --- | --- |
| `n_states` | 微状态类别数 K |
| `peak_selection` | GFP peak、全时点、随机采样 |
| `clustering_method` | k-means、AAHC 等 |
| `polarity_invariant` | 是否忽略极性 |
| `random_state` | 随机种子 |
| `backfit_smoothing` | 回填平滑策略 |
| `min_segment_length` | 最短片段长度 |

输出 key 建议：

- `template_id`
- `microstate_class`
- `subject`
- `condition`
- `duration_mean`
- `coverage`
- `occurrence`
- `transition_matrix_path`
- `gev`

缓存建议：

- group template 的 hash 按输入集合 + K + clustering 参数。
- backfit 结果可以按 `template_hash + subject_item_hash` 单独缓存。
- 如果只是新增一个 subject，group template 是否重算需要由策略决定：
  - `fixed_template`：不重算模板，只给新 subject backfit。
  - `refit_template`：重新拟合 group template，全部 backfit 失效。

### 8.2.4 NodeSpec 草案

```json
{
  "type": "eeg/microstate/group_template",
  "inputs": [
    {"name": "input", "type": "eeg_data", "cardinality": "many"}
  ],
  "outputs": [
    {"name": "template", "type": "microstate_template"},
    {"name": "labels", "type": "microstate_labels", "cardinality": "same_as_input"},
    {"name": "metrics", "type": "stats_table"}
  ],
  "execution": {
    "operator": "collection_transform",
    "scope": "collection",
    "input_policy": "many",
    "output_policy": "template_plus_fitted_items",
    "cache_grain": "model_and_item",
    "compatibility_keys": ["channels", "montage", "reference"]
  }
}
```

## 8.3 公共空间模型

### 8.3.1 场景说明

公共空间模型指多个数据集共同拟合一个空间变换或空间基，然后应用到每个数据集。

可能包括：

- 公共 ICA 矩阵。
- 公共 PCA 空间。
- Common Spatial Pattern。
- 跨被试共享空间滤波器。
- source space common basis。
- 统一模板空间下的投影模型。

### 8.3.2 为什么不是简单 N->N

公共空间模型通常分两步：

```text
fit shared spatial model:
  N 个输入 -> shared model

apply shared spatial model:
  shared model + 每个输入 item -> 每个输出 item
```

整体看是 N->N，但执行器应理解为：

```text
collection fit once + item apply N times
```

这和 FIR 这种 item_map 的 N->N 完全不同。

### 8.3.3 程序实现要点

必须做输入兼容性检查：

- channel names 是否一致。
- channel order 是否一致。
- montage 是否一致。
- bad channels 是否如何处理。
- reference 是否一致。
- sfreq 是否一致或是否允许 resample。
- 数据长度差异如何处理。
- 是否按 subject/condition 分组拟合多个模型。

要避免数据泄漏：

- 如果公共空间模型用于机器学习，fit 阶段不能把测试集信息泄漏进训练模型。
- 需要明确 train/test split 或 cross-validation fold。
- NodeSpec 里应支持 `fit_scope=train_only`。

缓存建议：

| 部分 | 缓存粒度 |
| --- | --- |
| shared model | collection |
| applied output | model_hash + item_hash |
| preview / metrics | model_hash |

输出建议：

- `spatial_model`：公共模型 artifact。
- `transformed_data`：每个输入对应的转换后数据。
- `model_metrics`：解释方差、成分质量、滤波器矩阵摘要。

### 8.3.4 NodeSpec 草案

```json
{
  "type": "eeg/spatial/common_model",
  "inputs": [
    {"name": "input", "type": "eeg_data", "cardinality": "many"}
  ],
  "outputs": [
    {"name": "model", "type": "spatial_model"},
    {"name": "output", "type": "eeg_data", "cardinality": "same_as_input"},
    {"name": "metrics", "type": "stats_table"}
  ],
  "execution": {
    "operator": "collection_transform",
    "scope": "collection",
    "fit": "once",
    "apply": "broadcast_to_items",
    "output_policy": "model_plus_same_as_input",
    "cache_grain": "model_and_item",
    "compatibility_keys": ["channel_names", "channel_order", "reference", "sfreq"],
    "leakage_control": "required_if_ml"
  }
}
```

## 8.4 多条件统计输出

### 8.4.1 场景说明

多条件统计不是简单把多个结果合成一个表，而是要按照实验设计解释输入集合。

常见场景：

- 同一 subject 的 target vs standard。
- 多个 condition 的 repeated-measures ANOVA。
- control vs patient 的组间比较。
- group x condition 混合设计 ANOVA。
- channel x time 的 cluster permutation。
- frequency band x region x group 的多因素统计。

### 8.4.2 为什么不是简单 N->1

多条件统计需要明确：

- 哪个字段是 subject。
- 哪些是组内因素，例如 condition、time_window、frequency_band。
- 哪些是组间因素，例如 group。
- 是否配对。
- 缺失 condition 如何处理。
- 统计输出的空间维度是什么。

输出也不只是一个单表，可能包括：

- 主效应表。
- 交互效应表。
- posthoc contrasts。
- corrected p-value。
- effect size。
- significant mask。
- cluster table。
- 可视化 preview。

所以它更适合：

```text
operator = design_reduce
scope = design
```

### 8.4.3 程序实现要点

输入 `data_infos` 必须包含标准实验变量：

- `subject`
- `session`
- `task`
- `run`
- `condition`
- `group`
- `time_window`
- `frequency_band`
- `channel`
- `region`

统计节点必须先生成 design matrix：

```text
subject | group | condition | artifact_id | value_ref
sub-001 | control | target   | art_001     | ...
sub-001 | control | standard | art_002     | ...
sub-002 | patient | target   | art_003     | ...
sub-002 | patient | standard | art_004     | ...
```

需要明确缺失策略：

| 策略 | 含义 |
| --- | --- |
| `strict_complete_cases` | 只保留所有 condition 完整的 subject |
| `allow_missing_with_warning` | 允许缺失但给 warning |
| `impute` | 进行插补，需明确算法 |
| `fail_on_missing` | 有缺失就失败 |

多重比较校正：

- FDR
- Bonferroni
- cluster permutation
- TFCE
- none

输出类型建议：

- `stats_table`
- `effect_map`
- `pvalue_map`
- `cluster_mask`
- `contrast_result`
- `figure_spec`

### 8.4.4 NodeSpec 草案

```json
{
  "type": "eeg/stats/anova",
  "inputs": [
    {"name": "input", "type": "analysis_result", "cardinality": "many"}
  ],
  "outputs": [
    {"name": "table", "type": "stats_table"},
    {"name": "effect_map", "type": "analysis_result"},
    {"name": "posthoc", "type": "stats_table"}
  ],

    "output_policy": "stats_bundle",

  }
}
```

## 9. 执行器建议

建议执行器不要把所有节点都当成简单函数调用，而是分层。

```text
PipelineExecutor
  -> 读取 NodeSpec.execution
  -> 组织输入集合
  -> 生成 item / pair / group / collection execution units
  -> 计算 hash
  -> 检查缓存
  -> 调用节点函数
  -> 规范化输出 data_infos
  -> 写入 artifact 和 node_run
```

节点函数只处理最小计算单元：

```text
item_map:
  run_node(item, params) -> item

item_expand:
  run_node(item, params) -> items[]

collection_reduce:
  run_node(items[], params) -> item 或 items[]

collection_transform:
  fit(items[], params) -> model
  apply(model, item) -> item

join_map:
  run_node(left_item, right_item, params) -> item

design_reduce:
  run_node(design_matrix, items[], params) -> stats_bundle
```

## 10. 缓存建议

不同执行模式的缓存粒度必须不同。

| 执行模式 | 推荐缓存粒度 |
| --- | --- |
| `item_map` | item |
| `item_expand` | item |
| `collection_reduce` | group 或 collection |
| `collection_transform` | model + item |
| `join_map` | pair |
| `design_reduce` | collection / design |

### 10.1 collection hash

集合级 hash 需要稳定排序：

```text
collection_hash = sha256(sort(item_hashes).join("|") + params_hash + spec_version)
```

如果输入顺序本身有意义，则必须写明：

```json
"ordering": "user_defined"
```

否则默认：

```json
"ordering": "stable_by_keys"
```

### 10.2 model + item 两级缓存

公共模型类节点建议拆成两级：

```text
model_hash = hash(collection + fit_params)
applied_hash = hash(model_hash + item_hash + apply_params)
```

这样当模型不变、只新增一个 item 且策略允许时，可以只对新增 item apply。

## 12. 建议落地顺序

建议不要一口气实现所有复杂模式。

### Phase 1A：把集合输出打牢

目标：

- 所有节点输出统一为 `NodeOutput.items[]`。
- `data_infos` 标准化。
- 每个 item 都有可追溯 key。

### Phase 1B：实现 `item_map`

先跑通：

- LoadData
- FIR Filter
- Resample
- Re-reference

### Phase 1C：实现 `item_expand`

跑通：

- Epoch
- ERP 按 condition 输出时也可使用类似逻辑。

### Phase 1D：实现 `collection_reduce`

跑通：

- Merge
- GrandAverage
- 简单 group mean。

### Phase 1E：实现 `join_map`

跑通：

- Difference Wave。
- Pairwise contrast。

### Phase 2：实现 `collection_transform`

跑通：

- 公共 ICA。
- 微状态群体模板。
- 公共空间模型。

### Phase 2/3：实现 `design_reduce`

跑通：

- ANOVA。
- Group comparison。
- Cluster permutation。
- ML model training。

## 13. 需要进一步讨论的问题

1. 是否在 NodeSpec 中把 `execution.operator` 设为必填？
2. `cardinality` 是否只保留给端口展示，不参与执行判断？
3. `data_infos` 的标准 key 是否必须包含 `subject/session/task/run/condition/group`？
4. Epoch 输出多个 condition 时，是一个 artifact 包含多个 condition，还是每个 condition 一个 artifact？
5. 公共模型类节点是否拆成两个节点：`FitModel` 和 `ApplyModel`，还是一个节点内完成 fit + apply？
6. 公共 ICA 新增 subject 时，是否允许固定旧模型只 apply 新 subject？
7. ANOVA 等统计节点的设计矩阵由用户手工配置，还是从 metadata 自动推断后让用户确认？
8. 差异波节点是用两个输入端口 `left/right`，还是一个输入端口内部按 condition 选择 A/B？
9. `collection_transform` 的失败策略如何定义：一个 item apply 失败是否导致整个模型节点失败？
10. 缓存 UI 是否显示 item cache、pair cache、collection cache 的不同命中情况？

## 14. 暂定推荐

暂定采用以下方向：

```text
端口类型负责“能不能连”
cardinality 负责“看起来几个进几个出”
execution.operator 负责“执行器怎么组织输入”
execution.scope 负责“一次计算吃什么”
group_by / match_by / design 负责“集合如何被组织”
cache_grain 负责“缓存按什么粒度计算”
```

这套设计比单纯 `N->N`、`N->1` 更复杂，但更贴近 EEG 工作流的真实需求，也更利于后续实现缓存、增量运行、统计、作图、ML 和人工交互节点。
