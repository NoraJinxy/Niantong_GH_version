## 0. 文档定位与权威口径

| --- | --- | --- | --- |

## 2. 结论摘要

本项目工作流模块建议采用如下路线:

1. 前端使用 Vue 3 + TypeScript 承载 LiteGraph 画布。
2. 节点定义采用 JSON/NodeSpec 驱动,前端自动注册节点并生成属性面板。
3. 工作流定义保存到 PostgreSQL `pipeline_definitions.definition_json`,同时可在项目目录生成镜像 JSON 便于导出和审计。
4. 节点执行不沿用旧项目“前端逐节点直接调用多个后端 endpoint”的方式,改为后端 `PipelineExecutor` 统一调度。
5. 工作流运行建议接入 Redis/Celery 后台任务系统；数据库保存事实，Redis 负责排队、临时进度和事件通知，文件系统保存 EEG 中间产物。
6. 借鉴旧项目 `traceCode + data_infos + node_output_registry` 的思想,但将执行记录、缓存索引、输出文件索引转移到后端数据库和项目数据目录。
7. Phase 1 工作流只覆盖: 数据选择、预处理、ICA、Epoch、ERP/PSD/TFR 基础分析、保存结果、发送到观察/统计入口。
8. Phase 2 再启用: 发送到作图编辑器、微状态、脑网络、溯源、高级统计与高级图表。

## 3. 旧版 Niantong 可直接借鉴的部分

旧项目中最有价值的部分不是数据上传规范,而是工作流编辑器和节点执行协议:

| 旧项目机制 | 价值 | 新项目处理 |
|------------|------|------------|
| LiteGraph 画布 | 已验证节点拖拽、连线、拓扑执行可行 | 继续使用,嵌入 Vue 组件 |
| `frontend/js/nodes/*.json` | 节点配置外置,便于扩展 | 升级为后端可校验的 NodeSpec |
| `ProcessNode.js` | 统一构造端口、属性、后端请求 payload | 前端只保留 UI 节点行为,执行交给后端 |
| `data_infos` | 统一描述节点输出,可用于绘图、恢复、下游传递 | 作为 ELYS 的节点输出元数据标准 |
| `traceCode` | 解决跨 session 缓存与可追溯问题 | 后端生成,纳入 `pipeline_node_runs` |
| 节点状态颜色 | 用户能直观看到 idle/running/success/restored/error | 保留并细化为正式状态机 |
| 节点双击打开预览 | 分析体验好 | 保留,但预览走观察模块或节点预览 API |

## 4. 旧版 Niantong 不建议照搬的部分

| 旧项目做法 | 问题 | 新项目方案 |
|------------|------|------------|
| 前端执行拓扑排序并逐节点请求 REST endpoint | 逻辑过重,难审计,难恢复,难排队 | 后端统一 `PipelineExecutor`;前端只发 run request |
| 每个节点一个 `/api/process/*` endpoint | endpoint 泛滥,参数契约分散 | 统一节点 dispatch,可保留少量调试 endpoint |
| localStorage 保存核心缓存 | 换浏览器/清缓存会丢,且不适合多人协作 | localStorage 只保存 UI 临时状态;核心状态在后端 |
| `/tmp/eeg_pipeline_cache` | 重启或清理后丢失 | 项目数据目录下持久化缓存 |
| BIDS 与 FIF 混用 | 旧项目把 FIF 当 BIDS raw 的倾向不符合本项目策略 | `source_uploads/` 保留原始上传,`fifdata/` 作为工作数据集 |
| `modu_process.py` 单文件堆积 | 难维护、难测试 | 拆分 `engine/preprocess`, `engine/analysis`, `engine/ica` |

## 6. 命名约定

| 名称 | 定义 |
|------|------|
| 工作流 / Pipeline | 一个由节点和连线组成的 DAG,描述从数据选择到分析结果保存的处理流程 |
| 节点 / Node | 一个处理步骤,例如 Filter、Resample、ICA、Epoch、ERP |
| NodeSpec | 节点定义 JSON,描述端口、参数、UI、后端函数、缓存策略 |
| PipelineDefinition | 保存到数据库的工作流定义 |
| PipelineRun | 一次运行记录,可以是全量运行、从某节点运行、单节点运行 |
| NodeRun | 某次 PipelineRun 中单个节点的执行记录 |
| Artifact | 节点输出文件或结果对象,例如 FIF、HDF5、JSON、PNG preview |
| Import Correction | 导入校正,只修正原始数据在系统中的解释方式和必要元数据,允许发生在 `fifdata/` |
| Preprocessing | 预处理,会改变信号处理状态或产生分析就绪派生数据,必须写入 `derivatives/` |
| Phase 1/2/3 | 产品落地阶段,不要缩写为 P1/P2/P3 |
| P0/P1/P2 | 实现优先级,只用于任务优先级,不要表示阶段 |
| `data_infos` | 节点输出元数据数组,用于描述数据 ID、文件路径、subject/session/run、类型和可视化入口 |
| traceCode | 由数据、节点类型、参数、上游输入共同决定的可追溯编码 |

### 2. 旧版路线的取舍

- 可以吸收：traceCode、node_hash、`data_infos`、节点输出注册表、缓存恢复、绘图联动、页面刷新后恢复。
- 不建议照搬：前端逐节点直接调用多个 `/api/process/*` 接口、依赖 session 内存变量、用 localStorage 判断缓存命中。
- 新版原则：前端只负责编辑、配置、发起运行和展示状态；后端 `PipelineExecutor` 负责拓扑排序、输入解析、节点调度、缓存命中、产物写入和审计记录。
