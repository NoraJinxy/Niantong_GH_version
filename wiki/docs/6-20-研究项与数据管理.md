## 涵盖路由

研究项是**两层结构**：第一层 `/studies` 列表页（master-detail：左列表 + 右概览卡 +「进入工作区」，点选不跳页），第二层 `/studies/:studyId` 工作区（Overleaf 式操作界面，默认落**工作流**，次级导航切 数据 / 工作流 / 结果）。顶层只有 工作台 / 数据集库 / 研究项三个 live 入口。

| 路由 | 组件 | 说明 |
|---|---|---|
| `/dashboard` | `Dashboard.vue` | 登录默认落点、导航中枢 |
| `/datasets`（alias `/import`） | `DatasetsPage.vue` | 数据集库（跨研究项资产，Dataset-first 导入） |
| `/studies` | `StudiesPage.vue` | **研究项列表（master-detail）**：左列表 + 右选中项概览卡（`StudyOverviewTab`）+「进入工作区」；点选走 `?study=id` 不跳页 |
| `/studies/:studyId` | `StudyLayout.vue` | **研究项工作区**：研究项标识 +「← 研究项列表」+ 3-tab bar + `<router-view>`；默认重定向到 **workflow** |
| `/studies/:studyId/data` | `StudyDetailPage.vue` | 数据：挂载数据集 + 采集记录宽表（只读） |
| `/studies/:studyId/workflow` | `PipelinePage.vue` | 工作流·运行：工作流编辑 + 运行 |
| `/studies/:studyId/results` | `ResultsPage.vue` | 结果：结果管理 |
| `/admin/withdrawals` | `AdminWithdrawalsPage.vue` | 数据集撤回审核（admin 从数据集页进入） |

> 旧的顶层 `/pipeline`、`/results` 路由已改为**兼容重定向**：从 query 解析 `studyId` 落到对应子 tab，无 study 上下文的裸链兜底回 `/studies`。兜历史书签与未改全的深链，前端代码不再产生这类链接。

## 一、仪表盘 `/dashboard`（Dashboard）

### 1.1 设计定位

仪表盘是**登录后的默认落点**，也是工作台的导航中枢。它不执行任何分析，只呈现概况、提供快速入口。

设计原则：
- **概况而非细节**——让用户在 3 秒内知道"我有多少数据、多少研究项"。
- **快速行动**——新建研究项、导入数据、进入工作流，三步以内可达。
- **角色感知**——只有 admin / pi 角色看到"新建研究项"按钮，普通协作成员看不到。

### 1.2 主要功能

#### 统计卡（4 项，四对象模型）

`Dashboard.vue` 的四张统计卡对应 ELYS 四个核心对象，数据来自 `GET /api/v1/dashboard/summary`（`dashboardApi`）的 `counts`：

| 卡片 | 来源说明 | 跳转 |
|---|---|---|
| 数据集 | `counts.datasets` | `/datasets` |
| 研究项 | `counts.studies` | `/studies` |
| 工作流 | `counts.pipelines` | `/studies`（工作流在研究项工作区内，先选研究项） |
| 运行记录 | `counts.executions` | `/studies` |

#### 快速操作区

| 操作 | 行为 | 权限 |
|---|---|---|
| 新建研究项 | 弹出创建模态框 | admin / pi |
| 进入研究项列表 | 跳 `/studies` | 全部已登录用户 |
| 进入数据集管理 | 跳 `/datasets` | 全部已登录用户 |
| 进入研究项 | 跳 `/studies`（工作流 / 运行 / 结果 都在研究项工作区内） | 全部已登录用户 |

#### 近期研究项（最多 5 个）

展示最近有活动的研究项卡片，每张卡片含研究项名、code、数据集数量和快捷操作入口。

#### 快速上传

复用 `BidsUploadPanel` 组件：先选择研究项，然后直接拖拽上传 EEG 文件，无需离开仪表盘页面。

### 1.3 数据加载策略

当前实现：`onMounted` 时调 `dashboardApi`（`GET /api/v1/dashboard/summary`）一次性拿 `counts` / `states` / `recent_activity`，统计卡和近期活动都来自这个聚合摘要；近期研究项卡片再用 `studyApi` 补列表。聚合端点避免了早期"逐研究项拉数据集"的 N+1。

## 二、研究项列表 `/studies`（StudiesPage）

### 2.1 设计定位

研究项的**入口列表 + 概览**，采用 **master-detail 左右栏**（参考 DatasetsPage）：左侧研究项目录（搜索 / 状态筛选 / 每行 名·code·状态·角色·挂载预览·数据·工作流·运行信号），**点选一项右栏即时铺开它的概览卡**（`StudyOverviewTab`：研究进度 / 已挂载数据集 / 建议下一步 / 工作流·运行 / 结果摘要）+ 顶部「进入工作区」按钮——点选不跳页、选中态走 URL `?study=id`（刷新可恢复）。这层只管"**选和看**"，真要干活点「进入工作区」切到第二层。

> 历史沿革：`/studies` 先后做过 master-detail（右栏摘要）→ 容器化纯列表（点进去全屏 4-tab）→ 现回到 master-detail，但右栏换成更清爽的概览卡、且把"干活"分到第二层工作区。中间那版"点进去先看概览 tab、再点一下才到工作流"被用户判为绕，遂改（参考 DatasetsPage 左右栏 + Overleaf"点进项目即操作界面"）。

科研研究项的生命周期包含创建、使用、归档、删除，页面设计**遵从这个生命周期**：

- 正常状态和垃圾箱分 tab 展示，职责清晰。
- 删除默认是软删除（移入垃圾箱），数据暂时保留。
- 永久删除（purge）是高危操作，需要二次确认——这是不可逆的，数据目录会被清除。

### 2.2 主要功能

#### Tabs 两视图

| Tab | 显示内容 | 过滤条件 |
|---|---|---|
| 正常研究项 | active / archived 研究项 | `status IN ('active', 'archived')` |
| 垃圾箱 | 已软删除研究项 | `status = 'trashed'` |

两个 tab 分别调用不同接口（`GET /studies` 和 `GET /studies/trash`），保持数据隔离清晰。

#### 研究项列表项操作

**正常视图**：列表项是 RouterLink，**点击进入容器**（`/studies/:studyId`，默认落概览 tab）；行内「移入回收站」按钮做软删除（输入理由，可恢复）。

**垃圾箱视图**：列表项不导航，行内「恢复」/「永久删除」按钮做治理；永久删除**不可逆**，需输入研究项 ID 或 code 确认。

#### 永久删除二次确认设计

不使用简单的"确定/取消"弹窗，而是要求用户主动输入研究项 ID，原因：
- 强制用户停下来思考，而不是惯性点击。
- 明确告知后果（数据目录清除、审计记录写入）。
- 输入匹配才启用删除按钮，技术上防止误触。

### 2.3 权限边界

| 操作 | 角色要求 |
|---|---|
| 新建研究项 | admin 或 pi |
| 移入垃圾箱 | admin 或研究项 owner |
| 永久删除 | admin 或研究项 owner |
| 查看研究项 | 研究项成员 |

权限在前端控制按钮可见性，后端仍执行实际权限校验。

## 三、研究项工作区 `/studies/:studyId`（StudyLayout，Overleaf 式，3 tab）

### 3.1 设计定位

研究项的**工作区**（Overleaf 式：点进项目就是操作界面）。一个研究项把 数据 / 工作流 / 结果 组织在一起，**进入后默认落「工作流」操作界面**（节点库 + 画布 + 参数，干活的主场），顶部次级导航切 数据 / 工作流 / 结果。**studyId 由 URL 路径承载**（`route.params.studyId`），刷新 / 深链 / 前进后退都稳定。容器（`StudyLayout.vue`）独占外壳（顶栏 + 研究项标识 +「← 研究项列表」+ 3-tab bar），3 个 tab 是它的子路由。

> 设计要点：子页面一律从 `route.params.studyId` 读"当前是哪个研究项"，不再各自带下拉；`stores/study.ts` 只缓存当前研究项详情对象供顶栏复用。**概览不在工作区里**——它在第一层 `/studies` 列表页右栏（见二节），工作区专注"干活"。

### 3.2 三个 tab

#### 数据（StudyDetailPage）

只读展示本研究项 active 挂载的数据集（mount 列表，`studyDatasetMountApi.list`）+ 采集记录宽表（被试 / 会话 / 任务 / 轮次 / 格式 / 标准化 FIF 状态 / 通道·事件 / 质量 / 导入时间，`recordingApi.list`）。导入数据集跳顶层数据集库（`/datasets?study_id=`，数据集是跨研究项资产，不被某个研究项拥有）。

#### 工作流·运行（PipelinePage）

工作流编辑（LiteGraph 画布）+ 运行发起 / 追踪一体。容器对本 tab 启用 `keep-alive`（画布重建成本高、编辑态值得保活），切走 / 切回时重算画布尺寸、停 / 续运行轮询、flush 草稿。深链参数 `pipeline_id` / `execution_id` 仍走 query（如 `/studies/:studyId/workflow?pipeline_id=..`）。

#### 结果（ResultsPage）

结果管理：按数据类型 / 被试 / 标签筛选，改名、加标签、改保留策略、下载、清理缓存。

### 3.3 研究项状态与容器行为

| 研究项 status | 容器表现 |
|---|---|
| active | 正常，所有 tab 可用 |
| archived | 显示归档徽章，导入提示已归档 |
| trashed | 后端返回 409；提示"先恢复" |
| 不存在 / 无权限 | 404 / 403；跳回研究项列表 |

## 四、数据集管理 `/datasets`（DatasetsPage + BidsUploadPanel）

### 4.1 设计定位

数据导入是科研流程的起点，设计上强调：

- **BIDS 兼容**：自动按 BIDS 实体（被试/任务/Session/Run）分组，降低手工填写的错误。
- **格式宽容**：支持 BrainVision（三件套）、EDF、BDF，自动识别并校验文件完整性。
- **进度透明**：上传过程中实时显示进度（上传阶段 0-95%）和服务器处理阶段（MNE 转换）。
- **错误可恢复**：单组失败不影响其它组，每组有独立重试入口。

当前口径是 **Dataset-first**：用户先确定 Dataset 目标，系统自动创建配套 Study 和 mount，然后再提交文件。

### 4.2 两层职责拆分

`DatasetsPage.vue`（数据集管理主页）做：
- 数据集列表 + 新建/选择 Dataset Asset（`datasetAssetApi.bootstrap()`），admin 可见「撤回审核」入口跳 `/admin/withdrawals`
- 拉研究项列表（支持 `?study_id=` query 自动选中）
- 渲染 `BidsUploadPanel`，传入研究项 / Dataset 上下文

`BidsUploadPanel.vue`（核心逻辑）负责：
- 文件选择和拖拽接收（支持文件夹拖拽）
- BIDS 实体自动分组
- 逐组上传和重传确认
- 进度展示和错误处理

这种拆分让 `BidsUploadPanel` 可以在 Dashboard 等其他页面复用。

### 4.3 BIDS 自动分组规则

| 输入场景 | 分组行为 |
|---|---|
| 拖入文件夹 | 递归扫描，按目录和文件名匹配 BIDS 实体 |
| 选择多个文件 | 按文件名匹配，同名三件套（.vhdr/.eeg/.vmrk）归为一组 |
| 单 EDF / BDF | 自动归为独立组 |
| 无 BIDS 实体的文件名 | 使用默认 task / subject，用户可手动修改 |
| 不支持的格式（.fif/.set 等） | 标为 invalid 组，展示拒绝原因 |

这一设计减少了用户手动填写 subject/task/session 的工作量，同时保留了手动覆盖的能力。

### 4.4 重传（版本管理）

收到 409 `DATASET_EXISTS` 响应时，弹出确认对话框：

```
该数据位 sub-093 / task-rest 已存在版本 v1。
是否作为新版本导入？
旧 FIF 在替换前会保留在 source_uploads/upload-001/，可用于回滚或对比。
[取消]  [确认替换]
```

确认后立即用 `replace_existing=true` 重提，不需要用户重新选文件。这保证了数据版本可追溯，而不是悄悄覆盖。

### 4.5 上传状态机

| 状态 | 显示 | 颜色 |
|---|---|---|
| `pending` | 待上传 | 灰色 |
| `uploading` | 进度条 0-95% | 蓝色 |
| `processing` | 服务器转换中 | 黄色 |
| `done` | 完成 + upload_seq | 绿色 |
| `error` | 错误信息 + 重试按钮 | 红色 |

95% 后的"服务器转换中"是因为 MNE 转换在后端同步执行，XHR progress 事件在此阶段不更新。未来接入 Celery 异步后可用 SSE 替换这个假进度。

### 4.6 错误处理覆盖

| 错误 | 展示方式 |
|---|---|
| 422 不支持的扩展名 | 该组 error + 拒绝原因 |
| 422 BrainVision 三件套不完整 | error + 缺哪个文件 |
| 409 `DATASET_EXISTS` | 重传确认弹窗 |
| 409 checksum 重复（已导入其它位） | error + 提示 |
| 422 MNE 读取失败 | error + 详细错误 + 重试 |
| 500 / 网络错误 | error + 通用提示 + 重试 |
