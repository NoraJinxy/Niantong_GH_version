## 1. 事实源优先级

| 级别 | 来源 | 用途 |
|---|---|---|
| **P0** | `elys_project/` 当前代码 | 判断已实现能力、接口、表结构、文件路径和页面状态 |
| **P1** | `wiki/docs/` | 当前维护中的正式文档 |

冲突时按 **P0 → P1** 顺序判断。当前代码最适合确认"是否已经实现"；产品文档最适合确认"是否应该实现"。

## 2. 冲突分类与处理

| 类型 | 表现 | 处理方式 |
|---|---|---|
| 文档问题 | wiki 写成已实现，但代码中找不到对应能力 | 修正文档状态，列入规划或待开发 |
| 代码问题 | 代码行为违背已确认产品约束 | 保留文档目标，提出开发任务 |
| 设计冲突 | 两份 wiki 页面互相不一致 | 先查 `0-10`，无约束时先决策再回写 |
| 待讨论 | 业务、科研方法或合规边界未定 | 标注待确认，不写成已实现 |

## 3. 多页面冲突判断顺序

1. 是否违背 [0-10 术语与统一约束](0-10-术语与统一约束.md)？
2. 是否影响 [1-00 需求分析](1-00-需求分析总览.md)、[3-00 数据库设计](3-00-数据库设计总览.md)、[4-00 文件管理](4-00-文件管理总览.md)、[5-00 研究管理](5-00-研究管理总览.md)？
3. 哪个页面离代码更近？数据库页对齐 SQL，前端页对齐 router 和 view，文件页对齐导入与目录逻辑。
4. 如果仍无法判断，查看变更记录，并补一次明确决策。

## 4. 冲突修复后必做

- [ ] 修改相关 wiki 页面。
- [ ] 必要时追加 [9-00 更新日志](9-00-更新日志.md)。
- [ ] 检查 nav 是否需要同步。
- [ ] 运行 `mkdocs build --clean`，确认没有构建错误。

## 5. 真实案例

| 场景 | 处理 |
|---|---|
| 前端有 ML 页面，但后端没有 ML 接口 | 页面可写"仅前端预览"，模块能力仍是规划 |
| 数据库字段和文档名称不同 | 以当前 schema SQL 为准，文档同步修正 |
| 工作流页面能保存节点，但大多数节点不能真实执行 | M3 标为"部分接入"，不能写成完整分析能力 |
