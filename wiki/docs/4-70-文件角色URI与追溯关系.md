## 1. 数据库是平台事实源

文件旁边的 JSON 是为了导出和离线复现；平台内的事实源应是数据库。

| 事实 | 数据库位置 |
|---|---|
| 文件属于哪个 Dataset/Study | `dataset_files` / `study_outputs` |
| 文件角色 | `file_role` / `data_type` |
| 逻辑路径 | `logical_path`，`relative_path` 保留旧兼容 |
| 真实读取位置 | `storage_uri` |
| 内容校验 | `sha256` |
| 转换来源 | `produced_by_params` / `dataset_file_derivations` |
| Execution 输入 | `pipeline_execution_inputs` |
| Execution 输出 | `study_outputs` |

## 2. Dataset 文件角色

建议标准化 `dataset_files.file_role`：

`dataset_files.file_role`（2026-06-11 两层重构后精简）：

| file_role | 含义 | 物理层 |
|---|---|---|
| `original_upload` | 用户上传原始文件 | `sourcedata/original_uploads/` |
| `fif` | MNE-ready canonical FIF（`_eeg.fif`） | `BIDSdata/` |
| `fif_eeg_json` | canonical FIF 同目录 `*_eeg.json` | `BIDSdata/` |
| `fif_channels` | canonical FIF 同目录 `*_channels.tsv` | `BIDSdata/` |
| `fif_events` | canonical FIF 同目录 `*_events.tsv` | `BIDSdata/` |
| `fif_provenance` | canonical FIF 旁边的轻量溯源 JSON | `BIDSdata/` |
| `qc_report` | 导入或基础 QC 报告 | —— |
| `event_summary` | marker/event 摘要 | —— |
| `channel_summary` | 通道摘要 | —— |

两层重构**退役**的角色：`raw_bids_data` / `raw_bids_eeg_json` / `raw_bids_channels` / `raw_bids_events` / `raw_bids_electrodes` / `raw_bids_coordsystem`（raw_bids 降纯逻辑，不再单独登记）、`raw_source` / `sidecar`（旧兼容角色）、`canonical_fif` / `canonical_fif_provenance`（改名为 `fif` / `fif_provenance`）。**raw_bids 的 BIDS 实体映射现由 `recordings` 表（sub/ses/task/run 四元组）回答，原始文件位置由 `original_upload` 行的 `storage_uri` 回答。**

## 3. StudyOutput 文件角色

建议标准化 `study_outputs.file_role`：

| 角色 | 含义 |
|---|---|
| `clean_raw` | 清洗后的连续数据 |
| `epochs` | epoch 数据 |
| `ica_solution` | ICA 模型或分量信息 |
| `evoked` | ERP/evoked 结果 |
| `spectrum` | PSD/TFR 等频域结果 |
| `table` | 统计表、特征表 |
| `figure` | 图片 |
| `report` | HTML/PDF/Markdown 报告 |
| `cache` | 可重算缓存 |

StudyOutput 是否可清理不由角色单独决定，而由 `retention_status`、依赖关系和报告引用共同决定。

## 4. URI 规则

建议业务层统一使用逻辑 URI：

```text
elys://datasets/ds-000001/BIDSdata/sub-001/ses-01/eeg/...        # working 版 canonical FIF
elys://datasets/ds-000001/sourcedata/original_uploads/upload-001/...  # 原始上传
elys://datasets/ds-000001/ver1.0.0/sub-001/ses-01/eeg/...        # 发布版本快照（P3）
elys://studies/202605000001/outputs/ab/abcdef...
```

2026-06-11 两层重构：dataset URI 形如 `elys://datasets/{asset_id}/{logical_path}`，**不再含 `versions/{label}` 段**。`{logical_path}` 第一段即物理层（`sourcedata/` / `BIDSdata/` / `ver{label}/`）。

StorageService 负责把它映射成：

```text
file:///mnt/elys_data/storage/datasets/...
s3://elys-storage/datasets/...
```

legacy scheme：`resolve_uri` 解析的 legacy 前缀是 `study://{study_id}/...`，映射到研究项 `data_root`（= `STUDIES_DIR/{study_id}`，即旧上传 / canonical FIF 实际落盘处）；`datasets.py` / `studies.py` / `cache.py` 写入端产出的就是这一形态（见 [4-10](4-10-存储原则与后端选择.md)）。

```text
study://202605000001/fifdata/sub-001/...
```

前端不接触 `file://`、`s3://` 或服务器绝对路径，只拿 `dataset_file_id` / `study_output_id`。

## 5. canonical FIF provenance

canonical FIF 的轻量 JSON 可以由数据库自动生成：

```json
{
  "Description": "Canonical FIF generated from the original upload for MNE processing.",
  "SourceBIDSEntities": {"subject": "sub-001", "session": "ses-01", "task": "task-rest", "run": "run-01"},
  "SourceOriginalUpload": {"logical_path": "sourcedata/original_uploads/upload-001/raw.vhdr", "storage_uri": "elys://datasets/ds-000001/sourcedata/original_uploads/upload-001/raw.vhdr"},
  "SourceSHA256": "…",
  "GeneratedBy": {
    "Name": "ELYS import pipeline",
    "Step": "generate_canonical_fif"
  },
  "GeneratedAt": "2026-06-11 17:59:13 +08:00"
}
```

2026-06-11 两层重构：原合成的 `SourceRawBIDS` / `SourceEvents` / `SourceChannels`（假 raw_bids 路径）退役，溯源改记真实 BIDS 实体 + 原始上传位置。数据库对应关系：

| JSON 字段 | 数据库位置 |
|---|---|
| `SourceBIDSEntities` | `recordings`（sub/ses/task/run 四元组） |
| `SourceOriginalUpload` | `dataset_files.file_role='original_upload'` |
| `CanonicalFIF` | `dataset_files.file_role='fif'` |
| `GeneratedBy` | `dataset_files.metadata_json` |
| `GeneratedAt` | `dataset_files.created_at` |
| `SourceSHA256` | source 文件的 `sha256` |
| `ConversionParams` | `metadata_json` |

## 6. 派生关系表

当前已新增 `dataset_file_derivations`，用于记录 Raw BIDS、sidecar、canonical FIF 和 provenance 之间的来源关系。标准字段可继续演进为：

```text
dataset_file_derivations
  id
  study_id
  source_file_id
  derived_file_id
  execution_id
  study_output_id
  derivation_kind
  transform_name
  transform_version
  parameters_json
  metadata_json
  created_at
```

示例关系：

```text
fif generated_from original_upload          # derivation_kind=canonical_fif
fif_provenance generated_from original_upload   # derivation_kind=canonical_fif_provenance
```

两层重构后只保留 `fif` / `fif_provenance` 两条派生（均溯源到主 `original_upload`）；旧的从 `raw_bids_*` 派生的关系随 raw_bids 降逻辑撤销。`derivation_kind` 仍叫 `canonical_fif` / `canonical_fif_provenance`（描述转换动作，非 file_role）。这样 canonical FIF 删除后也能知道如何从原始上传重建。

## 7. Execution 输入与输出追溯

Execution 创建时冻结输入：

```text
pipeline_execution_inputs
  execution_id
  dataset_asset_id
  recording_id
  recording_version_id
  dataset_file_id
  file_role
  storage_uri
  sha256
  selector_json
  resolved_metadata_json
```

Execution 完成后登记输出：

```text
study_outputs
  produced_by_execution_id
  produced_by_job_id
  produced_by_node_type
  data_type
  upstream_dataset_ids
  upstream_recording_ids
  storage_uri
  sha256
  retention_status
  display_name
  tags
```

历史 Execution 不依赖“当前数据”，只依赖它自己的输入快照。
