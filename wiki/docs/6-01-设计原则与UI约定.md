## 一句话

念析（ELYS）是面向脑电科研的专业工作台，不是通用 SaaS 仪表盘。UI 决策的第一问：**科研人员在实际分析场景下这是否有效**，而不是"界面好不好看"。

> **配色基线（2026-06-05 起）**：生产默认主题为 **Steel 钢蓝**（降饱和、去装饰渐变 / 光晕的冷静方向）。所有具体色值 / 间距 / 字阶以 `frontend/elys-web/src/style.css` 的 CSS 令牌为准；本卷及 6-05 中若出现写死的十六进制色（如旧版 `#2E6BFF` / `#17233c`）均为示意，**以代码令牌为唯一事实源**。

## 设计纲领：受众与“渐进披露”三层

> 本节是 6-01 所有具体 UI 规则的上位框架——先定「给谁看、露多少」，再谈每条交互细则。（2026-06-13 拍板）

### 受众与一句话纲领

ELYS 的最终用户是**医生 + 心理学家 / 神经科学家**，不是工程师 / 程序员。设计纲领一句话：**让用户觉得「脑电数据处理是一件简单、fancy 的事」，而不是一件复杂的事。**

这与「ELYS 是专业工作台」并不矛盾——专业能力在底层（厚），但默认呈现要薄。把厚做到薄的手段不是砍功能，而是**「渐进披露」**（progressive disclosure：默认只露最少信息，想深入再逐层展开），把复杂度收进抽屉、按需拉出。

### 三层界面，同一套后端

同一套节点图、同一个后端，按用户深度提供三种「皮」：

| 层 | 面向谁 | 看到什么 | 看不到什么 |
|---|---|---|---|
| **薄** | 临床医生 / 不懂细节者 | 上传数据 → 答几个问题 → 看结果 / 报告 | 节点、参数、MNE |
| **中** | 会做分析的科研人员 | pipeline 节点图，能改关键参数 | 底层实现细节 |
| **厚** | 专家 / 想抠细节者 | 每个节点全参数，可下钻到接近底层 MNE | —— |

两条纪律：

- **概念先行、自上而下设计**：先定「薄」层用的词（被试 / 任务 / 范式 / 结果），「厚」层是这些概念的展开，而不是另起一套工程词汇。**别先按工程师习惯堆「厚」层、最后贴一张「薄」皮**——那样复杂度会从缝里漏出来。
- **领域语言，不用文件系统语言**：用「被试 / 采集记录 / 任务 / 范式」，不用「路径 / 扩展名 / sha256 / logical_path」；ID·DOI·校验值一律折叠进「技术信息 / 高级」。（与 §1.1 数据可追溯不冲突：可追溯是「能追问来源」，不是「默认把来源糊在脸上」。）

### Overleaf 原则

ELYS 与 MNE 的差别不只是「多了图形界面」。参照 Overleaf：

- **底层源码永远可达**：Overleaf 再傻瓜的模板，都能点开看底层 LaTeX。⇒ ELYS 最深一层要让专家**能下钻到接近 MNE 的程度**（全参数、甚至看生成的调用），「懂了有细节」是有下限承诺的。
- **协作是内建的**：⇒ ELYS 的**文件管理 + 远程协作（数据集 / 研究项 / 权限 / 追溯）不是附属增强，而是区别于 MNE 的「另一半护城河」**，与分析模块同等重要。

### 节点粒度判据：按「科研决策边界」拆

工作流节点拆多细，**按用户（科研人员）要做几个决策来切，不按 MNE 函数边界切**。设计或评审任一新节点，先问两题：

1. 这是**用户决策**还是**实现细节**？决策 → 暴露；实现细节 → 藏进节点内部。
2. 这个操作**跨多种分析类型复用**吗？复用 → 独立节点；只在本类型内有意义 → 做成该节点的参数。

| 情形 | 做法 | 例 |
|---|---|---|
| 改变数据语义类型、且只在本类型内有意义 | 节点的**参数** | TFR 的 `average=on/off`（Epochs→AverageTFR） |
| 跨分析类型复用、且是用户的实验设计决策 | **独立节点** | baseline 校正可接在 ERP / TFR / PSD 之后 |
| 用户不关心的计算中间步 | **藏进节点内部** | —— |

裁决示例：**时频分析 = TFR 节点（average 作参数） + 独立 Baseline 节点 = 2 个节点**，不是 1 也不是 3。（MNE 把 average 塞进 `tfr_morlet` 是省内存的工程便利，不是科学决策边界，不照搬成节点划分。）

为什么这个判据可靠——三层收敛：

- 「科研人员做决策」的粒度 = 「未来 LLM 编排 pipeline」的粒度（LLM 就是在替用户做这些决策）；
- **节点图 ≈ 结构化的论文 Methods 段**（Methods 即论文「方法」段，本就是「滤波 → 分段 → 基线校正 → 时频」的散文化流水线）。

> <span class="elys-badge elys-badge--planned">规划 · 北极星</span> 「对话生成 pipeline + 自动起草论文 Method/Results」是远期愿景，落地冻结待用户访谈。但它有一条**现在就该兑现的便宜约束**：每个节点都应携带足够的 **provenance（来历溯源：用什么方法 / 什么参数 / 引哪篇文献）元数据**——将来自动成文才能退化成「模板填充 + 润色」。现在留位几乎零成本，事后补昂贵。

## 1. 核心设计原则

### 1.1 数据可追溯优先

科研工作的核心要求是**复现性**。页面上每一条结果，用户都应能追问"这从哪来"。

- 结果列表（Results 页）展示来源链（upstream_dataset_ids → upstream_recording_ids）。
- 工作流运行记录（Execution detail）保存 manifest 和 lineage，而不只是最终结果。
- 上传组件显示 `upload_seq`，文件版本可溯源。
- **不允许**在没有来源上下文的情况下展示分析结果。

### 1.2 状态清晰，避免误导

"已接后端"和"静态预览"是两种本质不同的状态。UI 必须始终区分这两者，不能让用户误以为点进去就能真正运行某个功能。

- 导航项未接入后端时必须显示"预览"灰色徽章（`is-preview` 类 + tooltip）。
- 静态预览页面不展示假数据作为"样例"，仅展示 UI 骨架和功能说明。
- 按钮在不满足条件时禁用（disabled），并给出原因，而不是静默失败。

### 1.3 角色权限在 UI 层可见

权限由后端执行，但 UI 不做"能提交但会 403"的设计——相关按钮根据角色直接隐藏或禁用。

- 新建研究项仅 admin / pi 角色可见。
- 永久删除（purge）仅 admin / 研究项 owner 可见入口。
- 管理后台项仅 admin 可完整访问。

### 1.4 操作可逆，高危操作二次确认

- 软删除（移入垃圾箱）优先于硬删除——用户有机会恢复。
- 不可逆操作（purge、清理 cached 结果）必须有二次确认，并明确说明后果。
- 删除研究项时要求输入研究项 ID 或 code 确认，不只是弹"确定/取消"。

### 1.5 布局稳定，信息分层

页面布局遵循固定模式：顶部导航栏（56 px） → 可选侧栏 → 主内容区。用户不需要猜测操作入口在哪里。

- 全局导航在顶部（9 项主入口：工作台 / 数据集 / 研究项 / 工作流 / 结果 / 观察 / 统计 / 作图 / 机器学习）。
- 工具栏和细分导航在侧栏（3 组 16 项：四对象主线 4 + 预处理与分析预览 4 + 观察与出图 8）。
- 主内容区不被导航遮挡——Pipeline 页例外，只保留节点库/工作流选择侧栏，关闭全局侧栏，避免双左栏。
- 面包屑导航用于多层级页面（详情页需显示"研究项列表 > 研究项名"）。

### 1.6 加载 / 空 / 错误三态必须处理

任何异步数据区域都要有三态：

| 状态 | 表现 |
|---|---|
| 加载中 | skeleton 或 spinner + 文字"加载中..." |
| 空数据 | empty 状态 + 引导动作（"去创建研究项"/"去导入数据"） |
| 错误 | 红色 alert + 错误信息 + 重试入口 |

静默失败是不可接受的设计。

### 1.7 科研场景的键鼠友好性

目标用户是科研人员，主要用鼠标 + 键盘在桌面浏览器操作。

- 核心表单支持 Enter 提交。
- 工作流画布支持快捷键（右键菜单、居中视图、100% 缩放）。
- 表格行支持键盘导航（规划）。
- 移动端响应式是辅助需求，不是主需求——登录页做了响应式，工作台不做强制适配。

### 1.8 版心宽度统一（内容容器最大宽度）

列表 / 总览类页面的内容**不铺满整屏**，而是限制在一个居中的最大宽度。这个宽度业内叫「内容容器最大宽度」（content max-width），中文设计里叫「**版心**」——就是不管屏多宽，正文只占中间这么宽、两边留白。

全站由一个 CSS 令牌统一控制：`--content-w`（在 `style.css` 的 `:root`），**当前值 1600px**。改这一处即全站生效。

- **套用方式**：页面用 `<WorkbenchShell :narrow="true">` 套上 `.page--narrow`（= `max-width: var(--content-w); margin: 0 auto`）。
- **统一套用**：工作台 / 数据集 / 研究项 / 研究项详情 / 结果 五个 live 页。
- **例外**：工作流页（`/pipeline`，画布要尽量铺满）和未接后端的预览页**不套版心**。
- **多屏**：典型工作屏 1920 下左右各留约 160px；2K / 4K 屏内容固定不再拉宽，自动两侧留更多白。
- **别和段落宽度混淆**：页面内部某些段落自己的 `max-width`（如副标题 760、研究项描述 980）是**阅读行宽**，目的是文字不要太长难读，和版心是两回事，各自保留。

## 2. 技术栈约定

| 层 | 选型 | 原因 |
|---|---|---|
| 框架 | Vue 3 Composition API | 组件逻辑集中，TypeScript 友好 |
| 路由 | Vue Router 4 | 支持 `meta.requiresAuth`；路由守卫在 `router/index.ts` 统一处理 |
| 状态 | Pinia | store 轻量，TypeScript 类型推导好；全局 auth store 持久化到 localStorage |
| HTTP | Axios + `api/client.ts` | 401 自动 refresh 拦截集中处理，业务代码不处理 token 刷新 |
| 可视化 | LiteGraph.js | 工作流画布节点连线 |
| 样式 | 自定义 CSS（style.css） + BEM 命名 | 无外部组件库，保持科研工具的简洁风格 |

TypeScript 类型定义集中在 `src/types/index.ts`；API 响应类型直接在 `api/*.ts` 中内联或引用。

## 3. 组件复用规范

| 组件 | 职责 | 使用场景 |
|---|---|---|
| `WorkbenchShell` | 包裹所有已登录业务页；含顶栏 + 可选侧栏 | 除 `Login.vue`、`Index.vue` 外的全部页面 |
| `BidsUploadPanel` | 文件选择 → BIDS 实体分组 → 逐组上传；含进度和错误处理 | `DatasetsPage`（`/datasets`）、Dashboard 快速上传 |
| `ObserveTabs` | 在 6 个 `/observe/*` 子页之间切换的 tab 组件 | 所有观察子页 |
| `AppIcon` | 全站 SVG 图标封装 | 全站 |

新页面**优先**使用以上组件，不重写功能重复的逻辑。

## 4. CSS 命名约定（BEM）

| 块 | 内容 |
|---|---|
| `.topbar` | 顶部导航栏 |
| `.sidebar` / `.nav-item` | 侧栏与导航项 |
| `.page` / `.page__header` / `.page__title` | 主内容区及其标题 |
| `.card` / `.stat` | 信息卡与统计卡 |
| `.alert` / `.badge` | 提示与状态徽章 |
| `.btn` / `.input` | 通用按钮与输入框 |
| `.workbench-*` | 工作台专用样式 |
| `.elys-badge--done` / `--wip` / `--planned` | 接入状态徽章（绿/黄/灰） |

状态徽章语义：
- `--done`（绿）= 后端已接通，功能可用
- `--wip`（黄）= 核心链路接入中，部分功能可用
- `--planned`（灰）= 仅前端预览，后端未接

## 5. 路由守卫约定

```
未登录访问需 auth 路由 → /login
已登录访问 /login       → /dashboard
其余                     → 正常放行
```

- 守卫在每次 `router.beforeEach` 中执行 `auth.init()`（从 localStorage 恢复 token）。
- `meta.requiresAuth = true` 的路由全部需要登录。
- 首页 `/` 和 `/login` 不需要登录。
