## 1. 基本原则

前端数据选择器不读取文件夹，只读数据库索引。

可筛选维度：

- Dataset Asset、Dataset Version、Study mount。
- subject、session、task、run。
- group、sex、age、handedness 等被试元数据。
- sampling rate、channel count、duration。
- marker/event label、event count。
- QC 状态。
- 是否已有 `original_upload`（上传格式）、是否已有 `fif`（canonical FIF）。
- 是否已有某类 Execution 输出。

文件系统只在用户真正预览、运行或下载时被后端访问。

## 2. 大规模数据场景

即使有：

```text
4000 subjects * 2 sessions * 12 runs * 多种 marker
```

用户也不应该通过目录选择文件。推荐交互方式：

- 表格筛选。
- 批量选择。
- 保存选择规则。
- 按 subject/session/task/run 分组预览。
- 按 marker/event 快速分层。
- 显示预计命中数量和缺失数据。
- 一键选择“当前 Study 挂载的 working Dataset”。

## 2.1 StudyOutput 跨 Execution 浏览复用同一筛选模型

`/results` 跨 Execution 浏览页（详见 [3-45](3-45-StudyOutput.md) 和 [6-00](6-00-前端页面总览.md)）使用与 LoadData 一致的 chip 多维筛选交互：

- 维度直接复用 BIDS（`bids_subject_id` / `session` / `task` / `condition`）。
- 额外维度有 `data_type` 枚举、`node_types`、`tags[]`、`retention_status`、`run_ids`。
- 选择 chip 后立即调 `GET /studies/{id}/outputs?...` 刷新列表。
- 选择规则不写回任何"派生选择器表"，只作为前端 URL query 参数；保存选择请走 Study `default_dataset_filter` 或 Pipeline LoadData。

也就是说"结果浏览"不引入额外索引表 —— `study_outputs` 行本身就承载了筛选所需字段，前端 chip 直接映射后端查询参数。

## 3. 文件索引模型

数据选择器看到的是逻辑文件，不是服务器路径。

| 字段 | 说明 |
|---|---|
| `dataset_file_id` | 文件索引 ID，前端传这个而不是路径 |
| `file_role` | `original_upload`、`fif`、`fif_eeg_json` / `fif_channels` / `fif_events` / `fif_provenance`（2026-06-11 两层重构精简，见 [4-70](4-70-文件角色URI与追溯关系.md)） |
| `logical_path` / `relative_path` | BIDS 或兼容相对路径 |
| `storage_uri` | 后端读取文件的位置，可为 `elys://`、`file://`、`s3://` |
| `sha256` | 内容校验 |
| `metadata_json` | provenance、转换参数、BIDS entities、显示摘要 |

当前代码已有 `dataset_files.logical_path` 和 `dataset_files.storage_uri`；`relative_path` 继续作为旧 API 兼容字段。

## 4. 摘要索引（规划，未落地）

建议维护两个轻量索引表（**当前 schema / ORM 中均无此两表**，属后续目标）：

| 表 | 用途 |
|---|---|
| `recording_event_summaries` | 每个 recording version 中各 marker/event 的数量、首末时间、标签别名 |
| `recording_channel_summaries` | 通道类型、坏通道候选、缺失通道、定位状态摘要 |

详细事件仍可保存在 Raw BIDS 的 `events.tsv` 中；选择器只需要摘要即可。

## 5. LoadData 解析

### 5.1 选择器双模式（2026-06-11 P4）

LoadData selector 支持两种持久化模式，由节点 `selection_mode` 区分：

| 模式 | 存什么 | 行为 | 用途 |
|---|---|---|---|
| `filter`（默认） | 规则：`dataset_filter` 的 subjects / sessions / tasks / runs 四维（各「全部」或多选） | 执行时后端按规则**实时匹配** `recordings`，数据集后续新增被试自动纳入 | 跟随数据集的动态分析 |
| `explicit` | 固定 `dataset_ids`（recording id 列表） | 锁死当前匹配集，之后数据集变化不影响 | 复现某次分析 |

> **修了一个真 bug**：旧前端 `LoadDataPanel` 无论用户怎么筛，保存时一律塌缩成 `selection_mode='explicit'` + 固定 `dataset_ids`，导致数据集后续加被试不会自动纳入已配置的 pipeline。P4 重写后 filter 模式按所选规则持久化、不再塌缩；`ensureLoadDataParams` 也不再强制 explicit。

前端面板（`LoadDataPanel.vue`）按四维提供「全部 / 多选」控件 + **实时匹配预览**（边选边显示「匹配 N 条」+ 前 20 条 + 「及另 M 条」，预览在客户端基于已加载的 recordings 即时计算，无需额外请求）+ 快捷场景按钮 + filter/explicit 模式切换。执行粒度（逐条 / 整批）不在此暴露，由引擎按节点类型自动判定。

### 5.2 执行时冻结

无论哪种模式，Execution 启动时都把选择**冻结成静态输入**（filter 模式此刻才展开为具体 recording + 文件）：

```text
sub-001 ses-01 task-rest run-01 version=v0002 file=fif sha256=...
sub-002 ses-01 task-rest run-01 version=v0001 file=fif sha256=...
```

冻结结果写入 `pipeline_execution_inputs`，后续 Dataset 继续上传不会改变旧 Execution。

## 6. 原始上传与 canonical FIF 的选择

默认策略（2026-06-11 两层重构后，raw_bids 降为纯逻辑索引，不再是物理层）：

| 场景 | 优先文件 |
|---|---|
| 长期存档、导出、伦理审查、重导追溯 | `original_upload`（sourcedata 原件） |
| MNE 预览和 Pipeline 运算 | `fif`（BIDSdata canonical FIF） |
| canonical FIF 缺失但原始上传在 | 自动生成或提示生成 canonical FIF |
| canonical FIF 已被清理 | 按 provenance 从 `original_upload` 重建 |

LoadData 优先级：`fif` → `original_upload`（见 `load_data.py` `CANONICAL_LOAD_FILE_ROLE` / `SOURCE_LOAD_FILE_ROLES`）。数据选择器可同时显示「上传格式可用」和「FIF 可用」两个状态，而不是让用户理解目录。

## 7. 文件索引与预览

| 操作 | 后端动作 |
|---|---|
| 波形预览 | API 鉴权后根据 `dataset_file_id` 读取 canonical FIF；缺失时触发生成 |
| marker 分割 | API 读取事件摘要或 Raw BIDS `events.tsv` |
| 批量运行 | Execution 创建时解析选择规则，写 `pipeline_execution_inputs` |
| 下载 | API 生成下载响应或短期下载 URL |
| 导出 BIDS | 按需从 `sourcedata` 原件 + sidecar 临时组装标准 BIDS 导出包（raw_bids 为逻辑索引，不常驻磁盘） |
