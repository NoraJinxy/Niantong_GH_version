## 2026-06-05 · 找茬收尾：4 个未深验候选逐个核实（3 个坐实并修、1 个确认非 bug）

**背景**：上一条「代码逻辑找茬」留了 4 个"看着可疑但没逐行坐实"的候选。本次逐个 Read 代码核实，是真 bug 才改、不误报。

**核实结论 + 处理**：

- ✅ **修 · 异步导入 worker 不复检 asset/mount 状态**（`tasks/file_tasks.py::run_dataset_import`）：同步导入在请求内由 `resolve_upload_dataset_asset` 校验"asset 状态可上传 + asset 已 active 挂载到本 Study"，但异步 worker 从 payload 直接按 id 取 asset、没复检——请求受理到 worker 执行有时间窗，期间 asset 被归档/隔离/删除、或 mount 被停用，worker 仍照写。已在 materialize 前补 `ensure_dataset_asset_uploadable` + `ensure_dataset_asset_active_mounted`，与同步路径对齐（不合规则任务 failed、带原因）。
- ✅ **修 · canonical FIF legacy 镜像复制失败留孤儿目录**（`routers/datasets.py::generate_canonical_fif`）：转完 FIF 先 `shutil.move` 到 canonical 目录并置 `committed=True`，再逐个复制镜像到 legacy 兼容目录。若镜像复制中途失败（磁盘满/权限），原 `except` 因 `committed=True` 不清理 → canonical 目录留盘、但上层 `db.rollback()` 致 DB 查无 → 孤儿目录（且会以 409 挡住后续同 seq 重试）。已把 legacy 镜像包进 try，失败时回滚 canonical + legacy 两个目录再 raise，做成 all-or-nothing。
- ✅ **修 · 紧急下架后遗留"永远 pending"的撤回申请**（`services/dataset_lifecycle.py::emergency_takedown_version`）：对 `withdraw_requested` 版本紧急下架时，新建一条 `decision='emergency'` 申请、但原来那条等审批的 `decision=NULL` 申请不动 → 它永远留在管理员 `/pending` 列表、点 review 又因版本状态已变而 409。已在下架时把同版本的 pending 申请一并标 `decision='emergency'` + reviewed 字段关闭（`emergency` 是 CHECK 允许值）。
- ❌ **非 bug · `get_next_upload_seq` 探测目录硬编码 `working` label**：探测用 `build_canonical_fif_base_path_for_asset`（默认 `version_label="working"`）、落盘用 `build_canonical_fif_base_path(target_version,...)`（取真实 label）——两者确实取不同字段。但核实导入链路：`_build_import_context` 里 `target_version = get_or_create_working_dataset_version(...)`（`datasets.py:3170`），即导入**永远**针对 working 版本，`target_version.version_label` 恒为 `"working"`，探测与落盘一致、当前根本触发不到（且有 409 兜底）。属"发布-rename 真启用后才可能冒头"的潜伏点，且现行 import 路径写死 get-or-create-working、不会走到，故**不改工作代码**，记此备查。

**验证**：3 个改动文件 `python -m py_compile` 通过。无本地运行环境，真实跑通待部署云端。

**Why**：把上一条留的尾巴收干净——异步/同步导入校验对齐、FIF 落盘原子化、紧急下架不留脏 pending；同时坐实第 4 个是不可达的潜伏点、避免为它改动工作代码（不误报、不过度修）。

## 2026-06-05 · 代码逻辑找茬：修 8 处后端/前端真实 bug（锁恢复 / retention / superadmin / 缓存 / 乐观锁 / 单活跃 / batch 事务 / refresh 单飞）

**背景**：延续 wiki 全章核对的思路，反过来拿 wiki 描述的"应有行为"当规格去读代码找**逻辑错误**（不是文档措辞）。5 个子代理按子系统并行深挖，再逐条亲自 Read 代码复验（子代理有误报前科，下文标了两处被纠正的高估）。共坐实并修复 8 处。

> 黑话铺垫：**乐观锁**指保存时带上"我看到的版本号"，服务端发现版本对不上就拒绝(409)、防止后写覆盖先写；**单飞(single-flight)** 指同一时刻多个请求要做同一件事(刷 token)时只真正做一次、其余共享结果；**CHECK 约束**是数据库给某列限定的合法取值集合，写了集合外的值会直接报错拒绝写入。

**改了什么（按严重度）**：

- 🔴 **锁恢复分支 500 + 运行锁泄漏**（`routers/pipelines.py`）：创建 Execution 抢运行锁失败后的"清理 stale 锁再重试"分支里，重试调用没接收返回值——若并发窗口里别的运行刚好结束、这次重试**成功**，`execution_lock` 变量未赋值会在后面 `str(execution_lock.id)` 抛 `UnboundLocalError`(500)，且刚拿到的锁引用丢失、泄漏到 10 分钟 TTL（期间该 Pipeline 全部 409）。改成赋值写法，三条路径都正确收敛。
- 🔴 **`retention_status='none'` 撞数据库 CHECK**（`pipeline/save_settings.py`）：用户给节点设 `retention: none`（或旧 NodeSpec 的 `temporary`/`trash`）时返回 `"none"`，但 `derived_datasets.retention_status` 的 CHECK 六值里没有 `none` → 写库报错、整个节点产物登记失败、execution 挂掉。改成映射到合法的 `temporary`（expires 为空 → 下次 cleanup 立即可回收，语义一致）。
- 🔴 **`superadmin` 角色不存在致紧急下架永远 403**（`services/dataset_lifecycle.py`）：`_ensure_superadmin` 要求 `has_role("superadmin")`，但 seed 只建 `admin`/`pi`（还主动删了 researcher/reviewer）。从零自建的环境里没人能持有 superadmin → 紧急下架对所有人 403、整条路径在实测里是死的。改成一并放行 `admin`（seed 里 admin 拥有全部权限）。
- 🟠 **缓存命中复用已删派生数据**（`pipeline/cache.py`）：cleanup 把过期 cached 数据标 `deleted` 但**保留物理文件**，而缓存查找只按 job_id 取、只校验"文件在 + sha256 对"，没排除 deleted → 重跑会把用户视角已删除的派生数据当命中复用。加 `deleted_at IS NULL` 过滤，与 content-addressed dedup 路径口径对齐。
- 🟡 **保存遇 409 乐观锁冲突死循环**（前端 `PipelinePage.vue`）：保存版本冲突后只显示报错、不刷新本地版本号 → 再点保存仍发旧 `expected_version`、永远 409，直到手动重载才逃。改成 409 时拉最新版本号刷新（保留画布改动），提示用户确认后可重新保存。
- 🟡 **`single_active_pipeline_run` 形同虚设**（`routers/pipelines.py`）：策略默认 `true`、能存能改，但创建 execution 时从没读过它，并发控制只有 per-pipeline 运行锁（挡不住同 Study 不同 Pipeline 并发）。补上按 `run_policy` 的 Study 级前置检查（已有活跃运行则 409）。**这是行为变化，见下**。
- 🟡 **batch 改 retention 部分提交无回滚**（`routers/pipelines.py`）：批量删除时，单条 helper 命中依赖 blocker 会"先 commit 再抛 409"，导致前几条改动已落库、后面抛错且无回滚。改成删除前全量预检 blocker、命中就在动数据之前一次性 409。
- 🟡 **前端 401 refresh 无单飞**（前端 `api/client.ts`）：并发 401 各自发一次 `/auth/refresh`。当前后端 refresh 无状态、不吊销旧 token，所以**不会**把人踢下线（子代理"几乎必现被踢"的判断已纠正），只是多刷几次；但将来若加 refresh token 轮换/黑名单就会踩雷。加模块级单飞 Promise，两个 client + 并发请求共享一次刷新。

**⚠️ 行为变化（single_active）**：修复后默认"同一研究项同一时刻只允许一个运行"（之前默认 true 但没强制，所以可能一直在并发跑多个）。经用户确认**目前保持此限制**，将来要并行并发时再放开（去研究项设置把 `run_policy.single_active_pipeline_run` 改 false）。做法是前置查询 + 409（同 Pipeline 仍由运行锁兜底）；跨 Pipeline 硬互斥需引 Study 级锁，留待后续。

**验证**：后端 4 个改动文件 `python -m py_compile` 全通过；前端 `npm run typecheck`（vue-tsc）退出 0。无本地运行环境，真实跑通待部署云端。

**未做 / 留待**：① 两个设计问题待定语义后再改——BIDS 四元组唯一性是"Study 级"还是"Asset 级"（唯一索引 + 去重查询都不含 `dataset_asset_id`，致同 Study 第二个数据集无法导入同名被试同任务）、`workspace` 可见性现等同 `public`（全平台登录可见，工作区概念未实现）。② 四个未深验候选待逐个核实再决定修否：`get_next_upload_seq` 探测目录硬编码 `working` label（发布-rename 启用后才冒头）、异步导入 worker 不复检 asset/mount 状态、canonical FIF legacy 镜像复制失败留孤儿目录、紧急下架后遗留"永远 pending"的撤回申请。

**Why**：调试期最怕"层间不一致"（retention 枚举、缓存 vs dedup 的 deleted 过滤、seed vs 代码的 superadmin）和"并发边界"（锁恢复、单飞、batch 事务）这类隐性 bug——平时不显、真用起来才崩。借这次找茬一次性收掉能站住的 8 处。

## 2026-06-05 · 修复 storage.py `study://` URI 解析 bug（dispatch 误写成 `project://`）

**背景**：上一条 wiki 核对中发现的代码真 bug——`services/storage.py` 的 `resolve_uri` 解析端没有 `study://` 分支，而生成端（`studies.py` / `datasets.py` / `cache.py`）大量产出 `study://{study_id}/...`。本次核实并修复。

> 黑话铺垫：**storage URI / scheme** 指给文件一个抽象地址（`scheme://netloc/path`，如 `study://202605000001/fifdata/x.fif`），由 `StorageService` 翻译成真实磁盘路径，业务层不直接拼物理路径；**dispatch** 指 `resolve_uri` 按 scheme 分流到不同解析函数。

**根因**：`resolve_uri` 的 dispatch 把 legacy 分支的 scheme 写成了 `project`（line 58），但**全后端没有任何地方生成 `project://`**（仅存在于 `_old/` 旧版与 wiki/会议日志）——是一次改名只改了 dispatch、漏改回 `study`。佐证：`_resolve_legacy_study_uri` 的 docstring（line 124）、生成端、`tests/test_storage_service.py`（line 48/62/104/105 直接 `resolve_uri("study://…")` 并断言成功）用的全是 `study://`，即这些测试此前必然 FAIL。

**为什么不按 DDL 注释统一到 `elys://studies/`**（纠正上一条的设想）：核实发现两者解析到**不同物理根**——`study://` 走 legacy resolver → `STUDIES_DIR/{id}`（= `study.data_root`，`studies.py:247` 设定，也是数据集导入 `resolve_study_relative_path` 实际写文件的地方）；`elys://studies/` 走新根 → `STUDIES_STORAGE_ROOT/{id}`（另一个目录）。把生成端改成 `elys://studies/` 等于把读取目标从有数据的 data_root 挪到空目录，是一次物理迁移而非 bug 修复。命名上 `legacy_*` / `_resolve_legacy_study_uri` 也表明 `elys://studies/`（新 Study 存储）是迁移目标、`study://`（data_root）是仍在用的现状。故采用最小正解：让解析端重新认 `study://`。

**改了什么**：
- `services/storage.py`：dispatch（line 58）`project` → `study`；`resolve_path` 的 scheme 白名单（line 81）`{"project","elys"}` → `{"study","elys"}`（否则 `study://` 会被当裸文件路径）；`_resolve_legacy_study_uri` 返回的 `scheme="project"` → `"study"`。死 scheme `project://` 直接删除不留兼容（调试期、零产出）。
- `database/schema/03_datasets.sql:197`：`dataset_files.storage_uri` 的 COMMENT 原写"例如 `elys://studies/...`"与现状不符，改为如实说明——当前导入写 legacy `study://{study_id}/{relative_path}`（解析到 data_root）、新 Study 存储用 `elys://studies/{study_id}/{relative_path}`（解析到 STUDIES_STORAGE_ROOT）。

**验证**：`py_compile` 通过；本地无 pytest/依赖，用桩掉 `app.config` 的内联脚本复刻测试断言——`study://` 解析到 legacy 根✓、带 resolver 走 data_root✓、`resolve_path("study://…")` 不再误当裸路径✓、`elys://studies/` 不受影响✓、`../`/`%2e%2e/`/`file://` 穿越仍被拒✓、`project://` 现报"Unsupported"✓，全 PASS。

**Why**：任何被存成 `study://…` 的 URI 在读取链路（`resolve_uri` / `resolve_path`）都会落到"Unsupported storage URI"或被误当裸路径，影响数据集导入后的文件读取、缓存命中引用、Study 文件浏览。

**留待**：把 legacy `study://`/`data_root` 整体迁移到新 `elys://studies/`/`STUDIES_STORAGE_ROOT`（含物理搬迁与生成端、测试改写）是独立的存储统一任务，本次不做。

## 2026-06-05 · 数据导入异步化：新增 /recordings/import-async + Celery worker + 客户端轮询

**背景**：调试用的 ERP 测试链（`elys_scripts/projects/01_erp_basic/setup.py`）上传 BrainVision 三件套时"屏幕干等几十秒、看不出卡在哪"。根因：当时唯一能用的导入端点 `POST /studies/{id}/recordings/import`（`backend/app/routers/datasets.py`）是**全同步**——一个 POST 里走完 存盘 → 校验 → `generate_canonical_fif`（BrainVision→FIF，MNE 转换，重活）→ 写库 才返回，客户端从上传到转换全程阻塞且零反馈。异步框架其实早搭了一半（`POST /recordings/import-task` + Celery + `/tasks/{id}` 状态 / 事件 / SSE 端点），但那个 worker `run_dataset_import` 是空壳（返回 `import_performed: False`，注释写"staged upload workers 启用前同步上传仍是唯一路径"），且配套的 staged 上传端点从不存在。

> 黑话铺垫：**multipart/form-data** 是浏览器传文件那种"带分隔线拼多文件"的请求体编码；**流式上传**指不把整包先攒进内存再发、而是从盘一块块读一块块发（才数得出进度）；**Celery** 是把慢活丢给独立 worker 进程的后台任务队列，HTTP 请求秒回、前端再轮询进度；**canonical FIF** 是平台把各种原始格式统一转成的 MNE `.fif` 标准件。

**改了什么**：

- **抽出共享核心 `materialize_recording_import`**（`routers/datasets.py`）：把"对已落盘文件做 校验 → 转 canonical FIF → 写库 → audit → commit"这段重活抽成一个函数，**同步端点与异步 worker 共用，单一事实源**；另抽 `_build_import_context`（鉴权 / 解析 asset / 重复 409 / 算 job_dir / 写 archiving manifest 等请求阶段前置）。同步老端点 `/recordings/import` 重构为调这两个 helper，**对外行为 / 响应不变**（纯去重，约 200 行内联逻辑收敛掉）。
- **新增端点 `POST /studies/{id}/recordings/import-async`**：请求内只把文件 archive 到 job_dir 就**秒回 task_id**，转 FIF 的重活派发给 Celery；权限、重复 409 等快判校验仍在请求内同步做掉，客户端立刻能拿到 409。
- **实装 worker `run_dataset_import`**（`tasks/file_tasks.py`）：从 `task.payload_json` 重建上下文（study / asset / version / duplicate / 各 BIDS label / job_dir / archived「扩展名→绝对路径」映射，全部从 payload 取——**不让 worker 重算 `upload_seq` / `job_id` 致路径漂移**）、读暂存文件、调 `materialize_recording_import`，全程 `record_task_event` 上报进度（10 暂存 → 30 校验 → 45 转换中 → 100 完成），recording 元信息写进 `result_json`。worker 用**惰性 import** 引 `routers.datasets`（顶层 import 会把 router 层拉进 worker 进程并可能造成循环 import）。
- **客户端 + 测试链**（`elys_scripts/`）：`common/elys_client.py` 新增 `import_recording_async`（手写流式 multipart 带上传进度条 → 拿 task_id → 轮询 `GET /studies/{id}/tasks/{task_id}` 直到 succeeded/failed），同步 `import_recording` 也顺手加了"上传进度条 + 转换计时"；`01_erp_basic/setup.py` 上传改走异步路径。上传体验由"一行干等几十秒"变成"上传进度条 + 轮询出的服务端阶段"两段可见。

**验证**：四个改动文件均 `py_compile` 通过；worker 里惰性 import 的符号（`materialize_recording_import` / `recording_to_response` / `get_active_study_dataset_mount_for_asset`，以及 `app.models` 的 `Study` / `User` / `Subject` / `DatasetVersion`）逐一核实可导入。无本地运行环境，真实跑通待部署到云端——**前提是计算服已有 Celery worker 消费 `CELERY_WORKFLOW_QUEUE`**（Pipeline 执行已走该队列、file 任务路由同队列，故 worker 大概率在跑；否则任务永远 `queued`、客户端轮询到超时）。

**Why**：兑现 [7-00](7-00-后端架构总览.md) §5「Dataset 导入异步化」一项，根治"大文件 / 重转换时上传请求长阻塞且无反馈"；顺带把同步端点 200 行内联逻辑抽成共享核心，消除"同步 / 异步两份转换逻辑各自漂移"的隐患。

**未做 / 留待**：真正的客户端直传对象存储（presigned / staged upload，免经 API 进程中转大文件）仍是后续；worker 转换失败只标任务 `failed`（`error_json` 带因）、未回写 manifest 的 failed 状态（任务状态为权威信号）；自动重试场景下 canonical 目录的幂等（当前 `max_attempts=1` 无自动重试，暂不触发）。
