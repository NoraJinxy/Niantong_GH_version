## 2026-06-09 · PipelinePage 巨石组件拆分（第 1 批）：抽出常量 / 纯函数到 composables

**背景**：`PipelinePage.vue` 是工作流页（节点库 + LiteGraph 画布 + 参数检查器 + 运行 / 执行 / 派生数据管理）的单文件实现，已膨胀到 **7297 行 / 271 KB**——一个文件揽下画布引擎、节点编辑、数据筛选、运行调度、产物管理等五六个独立关注点，任何改动都得在七千行里翻找，是典型的「巨石组件」。

> 黑话铺垫：**巨石组件（God Component）** 指一个组件什么都干、状态与逻辑高度耦合、谁都改不动的反模式；**composable（组合式函数）** 是 Vue 3 把「一组相关的状态 + 方法」打包成 `useXxx.ts` 复用单元的写法，相当于「带状态的工具模块」，是给巨石组件拆方的主刀工具。

**拆分总思路（分批进行）**：逻辑层抽成 `composables/pipeline/useXxx.ts`、模板层抽成子组件 `.vue`；并先把被各处共享的「承重墙」状态（`definition` / 选中节点 / `nodeSpecs`）收拢成一个根 composable，其它模块向它取数据。整套计划约 6 批（常量 / 格式化 → 承重墙 → 草稿 / 布局 / 节点库等叶子 → 产物 / 执行 → 画布引擎 → 模板子组件化）；**本条只落地第 1 批，后续批次为规划。**

**第 1 批改了什么（已落地）**：

- 新增 `composables/pipeline/pipelineConstants.ts`——把 **39 个模块级常量**（节点类型标识、分类 / 端口 / 状态配色表、执行模式与保存策略选项、画布尺寸 / 缩放阈值、草稿与布局 localStorage 前缀等）按原名 `export`。
- 新增 `composables/pipeline/pipelineFormatters.ts`——把 **33 个纯展示 / 格式化函数**（状态文案、配色映射、文件大小 / 时间 / 时长格式化、端口兼容判断等）抽出；逐个验证为「纯函数」（只依赖入参与模块常量、不碰任何组件状态 `ref`），依赖到的常量从 `pipelineConstants` import。
- `PipelinePage.vue` 删掉这 72 个定义、改为两条具名 import，**所有引用处（含 template 调用）一字未动**——行为完全不变。主文件 **7297 → 7039 行**（净删 ~320 行定义、回填 ~63 行 import）。

**刻意留下没抽的**：`describeError`（勾连本地类型守卫 `isRecord`）、`artifactActionStatusText`（依赖本地 `type ArtifactAction`）、`buildArtifactPreview*` / `getPreviewSummary`（属「产物预览」域）——避免范围蔓延，留给后续对应批次。

**范围 / 验证**：纯前端内部重构，不动后端 / API / 类型签名 / 页面功能；`npm run typecheck`（vue-tsc）零错误通过。调试期，不留兼容层。

**Why**：七千行单文件的复杂度已压垮可维护性。先抽出零依赖、零风险的常量与纯函数（占行数不多但散落各处），既立刻减负、又跑通「抽取 → 删定义 → 改 import → typecheck」的安全流程，为后续动承重墙、画布等高风险批次铺垫。

**事实源**：`frontend/elys-web/src/composables/pipeline/pipelineConstants.ts`·`pipelineFormatters.ts`、`frontend/elys-web/src/views/PipelinePage.vue`。

## 2026-06-09 · 数据集生命周期 v2 定稿：发布≠分享、可见范围只升不降（废止 06-07 旧决策）

**背景**：起因于 DatasetsPage 把未发布态的内部英文枚举值直接暴露给用户，进而对 ELYS 数据集（`DatasetAsset` / `DatasetVersion`）的生命周期、状态、权限做了一次彻底重审，并对 wiki 与代码逐项核对。产出《数据集生命周期重构_综合报告 v2》（11 项决策闭环）+《落地实施清单》，作为新设计基线，落地后 [3-25](3-25-数据集生命周期与发布机制.md) 据此改写。

**这条作什么用**：本条只**宣告 v2 定稿并废止 06-07 旧决策**；逐项 schema / 服务层 / 路由 / 前端 / wiki 的落地改动随各自提交另记。06-07 两条旧记录（「可见范围=发表级、发布自动私有→共享」与「徽章用可见范围轴 B 方案」，见本页下方）**保留不改**，作历史留痕。

**v2 相对 06-07 变了什么（核心 5 条 + 配套清理）**：

- **发布 ≠ 分享（废止「发布自动私有→共享」）**：发布只做两件事——冻结版本文件 + 铸 DOI；可见范围**默认私有、不自动转共享**。是否对外可见，由负责人在发布后**单独**决定。06-07 的「发布即自动 `private→shared`」被废止（删 `dataset_lifecycle.py` 里那段自动跳变）。
- **可见范围「只升不降、无降级接口」（修正 06-07 B 方案的「只读徽章随发布联动」轴）**：私有→共享→公开可跳级开放，但**任何降级都没有入口**（共享/公开＝不可逆释放，类比论文发表）。可见范围从「通用 PATCH 可写」改由**专门的「开放」端点**处理（只升、仅负责人）；要可撤销的协作改用「私有 + 把人加进研究项团队」。
- **共享 = 邀请制（按用户授权），不再等于「任意登录用户可见」**：新建 `dataset_members` 表 `(asset_id, user_id, granted_by, granted_at)`，负责人**按用户**授权；`shared` 仅被授权者可读 / 可关联。`public` 才是「任何注册用户」——平台全员注册、**无匿名访问**，故公开＝全平台登录用户、无需匿名路由。私有＝负责人 + 管理员 + **主研究项成员**。
- **发布是 PII / 伦理 / 版权关口**：未发布→已发布时强制勾选「已脱敏」确认并声明伦理与版权，缺则不能发布；每次发布都要重做（每个已发布版本是独立不可变制品）。
- **撤回审核中禁止新关联**（修正旧代码「允许新挂载」）：已有关联保留，但不接受新关联；已撤回为终态墓碑，只能开新版本 v+1 前进。
- **配套清理**：发布状态枚举全栈统一为 `unpublished`（替换旧未发布枚举值，含 DB CHECK / 接口 / 前端，物理槽位名 `version_label="working"` 不在此列）；资产 `dataset_assets.status` 的 `working` / `active` 合并为 `working`；清理已被 `state` 取代的旧字段 `dataset_versions.status`；发布/授权/撤回申请收敛为**仅负责人**（管理员只保留撤回审核、紧急下架、隔离等平台治理；`superadmin` 角色保留另作平台治理用）。

**两根正交轴（概念模型）**：发布状态轴（版本级 `DatasetVersion.state`：`unpublished` / `published` / `withdraw_requested` / `withdrawn`）管「能不能改 / 删、是否冻结、是否铸 DOI」；可见范围轴（资产级 `DatasetAsset.visibility`：`private` / `shared` / `public`）管「谁能看、谁能关联」。核心一句话：**发布只冻结＋铸 DOI，分享是另一个独立动作**。

**术语锁定**：界面同时给中英两套标签，「导入 Import / 关联 Link / 加载 Load」三件事严格不混——导入＝外部文件进平台造数据集，关联＝研究项接上已有数据集（数据不搬动，原「挂载 Mount」改称），加载＝Pipeline LoadData 节点运行时读数据；专有名词中英一一对应、杜绝中英混排。

**影响哪些页面**：[3-25](3-25-数据集生命周期与发布机制.md)（状态机 + 权限矩阵据 v2 改写，为文档侧最高优先级）、[3-20](3-20-Dataset与采集记录表.md) / [3-50](3-50-协作权限状态与迁移.md) / [3-00](3-00-数据库设计总览.md)（删「发布自动 private→shared」「可手动调可见范围」，改「发布默认私有、只升不降」）、[6-05](6-05-信息分级与领域语言.md)（B 方案解耦：可见范围改「负责人显式开放」、保留两轴各自只读展示）、[5-10](5-10-Study研究项管理.md)（`primary_study_id` 与私有可见对齐、发布版现在时）、[3-45](3-45-DerivedDataset.md)（DDL 补 `lifecycle_state` / `visibility` 列；派生数据是否随 v2 调整待确认）。

**范围 / 状态**：本条为**设计定稿宣告**；代码与文档的逐项落地按《落地实施清单》第五节依赖顺序施工（schema→seed→schemas→服务层→路由→前端→wiki→静态校验+部署），各步另记。调试期 DROP + 重建，不写迁移、不留兼容层。

**Why**：科研数据一旦对外共享 / 被引用即具备论文发表级的不可撤销性。把「开放可见范围」做成轻飘飘的下拉、或让发布顺带自动公开，都会诱发误操作并破坏引用方信任。v2 把两轴彻底解耦、把可见范围做成「只升不降的郑重动作」，并用邀请制把共享收敛到「明确授权的人」，让非法状态压根表达不出来。

**事实源**：`日志/2_meeting260609/数据集生命周期重构_综合报告.md`（设计基线）、`日志/2_meeting260609/数据集生命周期_落地实施清单.md`（施工清单）；代码落点 `backend/app/services/dataset_lifecycle.py`·`dataset_assets.py`、`database/schema/03_datasets.sql`、`schemas/dataset_lifecycle.py`·`dataset.py`、`routers/datasets.py`·`dataset_versions.py`、`frontend/elys-web/src/views/DatasetsPage.vue`。

## 2026-06-08 · 新增 buy_ecs：按启动模板 + 抢占式购买 ECS（cmd → ps1，用 aliyun CLI、不引 Python）

**背景**：计算服务器是阿里云按量 / 抢占实例、**公网 IP 每次部署都会变**（见 `AGENTS.md`），过去每次都得到 ECS 控制台手动开机、再把新公网 IP 抄回 `deploy/profiles/aliyun-test.env` 的 `COMPUTE_SERVER_IP`，繁琐且易抄错。用户要"按**自己制定的启动模板**、用**抢占式**买，而且不用 Python、像部署那样直接写个 `cmd`"。

> 黑话铺垫：**启动模板（LaunchTemplate）** 是预先存在 ECS 控制台里的一套实例规格（镜像 / 机型 / 安全组 / 交换机 / 磁盘），开机时引用它就不必每次填一大堆参数；**抢占式（Spot）实例** 是按市场价竞价的廉价 ECS（常比按量便宜一大截），代价是库存紧张时可能被自动释放；**DryRun** 是"演练"——只让阿里云校验参数对不对、并不真正下单扣费；**幂等（ClientToken）** 指带一个唯一令牌，网络重试时阿里云认得"这单下过了"、不会重复扣费开两台。

**改了什么**：

- 新增 `buy_ecs.cmd`（仓库根，4 行壳子，与 `deploy_remote.cmd` 同款）转手调 `elys_project/deploy/buy_ecs.ps1`；真活全在 ps1 的 `param()` 块里。
- **底层用阿里云官方 `aliyun` CLI（单个 exe），不引 Python SDK / venv**——契合"像部署那样一个 cmd 就跑"。
- **路径①启动模板（主）**：`-LaunchTemplateName` / `-LaunchTemplateId`，规格全交给模板，脚本只叠加抢占式策略 + 数量；显式给了 `-InstanceType` 等参数才覆盖模板对应项。**路径②显式配置（兜底）**：无模板时靠 `-InstanceType` / `-SecurityGroupId` / `-VSwitchId` 等逐项指定（镜像可留空，自动取最新 Ubuntu 22.04）。
- **默认演练**：不加 `-Yes` 永远只 DryRun（不下单、不花钱）；`-Yes` 才真买。抢占式默认 `SpotAsPriceGo`（随市场价自动出价），可切 `-SpotStrategy SpotWithPriceLimit -SpotPriceLimit <每小时上限价>`。每次带幂等 `ClientToken`（网络重试不会重复下单）。
- **闭环 IP**：真买后轮询到 `Running`、打印公网 IP + `ssh root@<IP>`；加 `-UpdateProfile` 直接把公网 IP 写回 `aliyun-test.env` 的 `COMPUTE_SERVER_IP`，紧接着 `deploy_remote.cmd` 就能部署。
- `-List` 列出账号里的 启动模板 / 安全组 / 交换机 / 镜像（用来填参）。
- 默认地域 `cn-shenzhen`（华南1，与现有计算服 IP 段一致）；凭证从环境变量 `ALIBABA_CLOUD_ACCESS_KEY_ID` / `_SECRET` 读，或走 `aliyun configure`，**不进仓库**。检测不到 `aliyun` CLI 时打印完整安装 / 配置指引并退出。

**范围 / 不进部署**：纯新增的本地运维脚本，不参与 `deploy.sh`，不碰后端 / 前端 / DB。`.ps1` 存为 **UTF-8 BOM**（与 `deploy_remote.ps1` 一致）——否则 Windows PowerShell 5.1 会按 GBK 解码、中文注释把引号 / 括号"吃掉"导致解析直接失败（本次踩过、已修）。

**验证**：本机无 `aliyun` CLI、也不真实下单（且真买已挡在 `-Yes` 之后）；已做 PowerShell AST 解析校验 + 运行时冒烟（参数绑定、中文不乱码、缺 CLI 的友好提示均 OK）。真实下单待有 CLI + 凭证的环境跑。

**Why**：把"按模板开一台便宜的抢占式计算服 → 拿公网 IP → 回写 profile → 部署"从"控制台点点 + 手抄 IP"压成一条命令；抢占式契合调试期"数据可重建、机器随时可弃"的特点，省钱。复用部署同款 `cmd → ps1` 模式，零额外学习成本。

**事实源**：`buy_ecs.cmd`、`elys_project/deploy/buy_ecs.ps1`；与 `deploy/profiles/aliyun-test.env`（`COMPUTE_SERVER_IP`）联动，计算服网络背景见 [2-10 部署架构与网络拓扑](2-10-部署架构与网络拓扑.md)。

## 2026-06-08 · 研究项升级为「容器」：导航从四平级 tab 改为以研究项为容器（C 档重构）

**背景**：研究项本应是把「数据 → 工作流 → 结果」串起来的枢纽，但导航把它做成了和 数据集 / 工作流 / 派生数据 平级的"四选一 tab"之一——同一个研究项的信息被切到三页（`/studies` 右栏摘要、`/studies/:id` 采集记录、`/results` 完整结果），每个动作（导数据 / 配流程 / 看结果）都把用户甩出 studies 跳到另一个顶级页，那些页又各自带"先选哪个研究项"的下拉。用户一句"这个连接项把数据集 / 工作流 / 结果组织在一起、但呈现散乱"点中要害。

## 2026-06-07 · 决策：数据集可见范围（私有 / 共享 / 公开）是「发表级」严肃动作

**决策**：数据集的可见范围（`dataset_assets.visibility`）不是一个能随手切换的开关，而是**类比学术论文发表的严肃决策**。它只有三档，且只能通过郑重的发布 / 撤回流程流转，**UI 不提供随意下拉**。

**三档语义**：

| 档位 | 取值 | 谁能看 / 用 | 怎么进入 |
|---|---|---|---|
| **私有** | `private`（默认） | 仅**主研究项**可见、可挂载使用 | 新建数据集即私有 |
| **共享** | `shared` | **其他研究项**可挂载 / 引用（跨 Study 解锁） | 由「**发布版本**」流程触发：发布某版本时自动 `private→shared` |
| **公开** | `public` | 全平台可见 | 比"发布=共享"更进一步的 deliberate 动作（确认弹窗），**留作后续**，当前无 UI 入口 |

**流转规则**：

- **开放（私有→共享）= 发布**：必须走「发布版本」流程（强制 SemVer 版本号、发布后该版本文件不可改、要改开新版本），等同于"把这版数据正式发表出去"。发布成功后可见范围自动升到 `shared`。
- **收回 = 撤回，不是回退**：已发布版本要下架，走「申请撤回 → 管理员审核」流程（紧急情况由超级管理员紧急下架，事后补审计）；`withdrawn` 是终态，要继续工作只能开新版本前向演进。**可见范围不因撤回自动降级回私有**——已发布过即视为"曾公开"，其他研究项可能已引用。
- 因此**不存在"把已发布数据一键改回私有"的随意操作**；这条铁律就是不给 UI 下拉控件的原因。

**UI 落地**（同日实现，详见下方"可见范围轴"与"交互回退"两条）：数据集徽章**只读展示**当前可见范围（私有/共享/公开）+ 解释性 tooltip；改变可见范围一律经由发布 / 撤回流程，不出现随意下拉。

**Why**：科研数据一旦对外共享 / 被他人引用，就具备了和论文发表同等的不可随意撤销性（下游引用稳定性、学术诚信、DOI 不可逆）。把"开放可见范围"做成一个轻飘飘的下拉，会诱发误操作并破坏引用方的信任；交给版本发布这个本就郑重、可追溯、带版本号的流程，才与这件事的严肃程度匹配。

**相关事实源**：`backend/app/services/dataset_lifecycle.py`（发布自动 `private→shared`、撤回不降级）、`database/schema/03_datasets.sql`（`visibility` CHECK 三档）、`wiki/docs/3-25-数据集生命周期与发布机制.md`（draft/published/withdrawn 生命周期与跨 Study 引用门控）。

## 2026-06-05 · 找茬收尾：4 个未深验候选逐个核实（3 个坐实并修、1 个确认非 bug）

**背景**：上一条「代码逻辑找茬」留了 4 个"看着可疑但没逐行坐实"的候选。本次逐个 Read 代码核实，是真 bug 才改、不误报。

**核实结论 + 处理**：

- ✅ **修 · 异步导入 worker 不复检 asset/mount 状态**（`tasks/file_tasks.py::run_dataset_import`）：同步导入在请求内由 `resolve_upload_dataset_asset` 校验"asset 状态可上传 + asset 已 active 挂载到本 Study"，但异步 worker 从 payload 直接按 id 取 asset、没复检——请求受理到 worker 执行有时间窗，期间 asset 被归档/隔离/删除、或 mount 被停用，worker 仍照写。已在 materialize 前补 `ensure_dataset_asset_uploadable` + `ensure_dataset_asset_active_mounted`，与同步路径对齐（不合规则任务 failed、带原因）。
- ✅ **修 · canonical FIF legacy 镜像复制失败留孤儿目录**（`routers/datasets.py::generate_canonical_fif`）：转完 FIF 先 `shutil.move` 到 canonical 目录并置 `committed=True`，再逐个复制镜像到 legacy 兼容目录。若镜像复制中途失败（磁盘满/权限），原 `except` 因 `committed=True` 不清理 → canonical 目录留盘、但上层 `db.rollback()` 致 DB 查无 → 孤儿目录（且会以 409 挡住后续同 seq 重试）。已把 legacy 镜像包进 try，失败时回滚 canonical + legacy 两个目录再 raise，做成 all-or-nothing。
- ✅ **修 · 紧急下架后遗留"永远 pending"的撤回申请**（`services/dataset_lifecycle.py::emergency_takedown_version`）：对 `withdraw_requested` 版本紧急下架时，新建一条 `decision='emergency'` 申请、但原来那条等审批的 `decision=NULL` 申请不动 → 它永远留在管理员 `/pending` 列表、点 review 又因版本状态已变而 409。已在下架时把同版本的 pending 申请一并标 `decision='emergency'` + reviewed 字段关闭（`emergency` 是 CHECK 允许值）。
- ❌ **非 bug · `get_next_upload_seq` 探测目录硬编码 `working` label**：探测用 `build_canonical_fif_base_path_for_asset`（默认 `version_label="working"`）、落盘用 `build_canonical_fif_base_path(target_version,...)`（取真实 label）——两者确实取不同字段。但核实导入链路：`_build_import_context` 里 `target_version = get_or_create_working_dataset_version(...)`（`datasets.py:3170`），即导入**永远**针对 working 版本，`target_version.version_label` 恒为 `"working"`，探测与落盘一致、当前根本触发不到（且有 409 兜底）。属"发布-rename 真启用后才可能冒头"的潜伏点，且现行 import 路径写死 get-or-create-working、不会走到，故**不改工作代码**，记此备查。

**验证**：3 个改动文件 `python -m py_compile` 通过。无本地运行环境，真实跑通待部署云端。

**Why**：把上一条留的尾巴收干净——异步/同步导入校验对齐、FIF 落盘原子化、紧急下架不留脏 pending；同时坐实第 4 个是不可达的潜伏点、避免为它改动工作代码（不误报、不过度修）。

## 2026-06-05 · 代码逻辑找茬：修 8 处后端/前端真实 bug（锁恢复 / retention / superadmin / 缓存 / 乐观锁 / 单活跃 / batch 事务 / refresh 单飞）

**背景**：延续 wiki 全章核对的思路，反过来拿 wiki 描述的"应有行为"当规格去读代码找**逻辑错误**（不是文档措辞）。5 个子代理按子系统并行深挖，再逐条亲自 Read 代码复验（子代理有误报前科，下文标了两处被纠正的高估）。共坐实并修复 8 处。

> 黑话铺垫：**乐观锁**指保存时带上"我看到的版本号"，服务端发现版本对不上就拒绝(409)、防止后写覆盖先写；**单飞(single-flight)** 指同一时刻多个请求要做同一件事(刷 token)时只真正做一次、其余共享结果；**CHECK 约束**是数据库给某列限定的合法取值集合，写了集合外的值会直接报错拒绝写入。

**改了什么（按严重度）**：

- 🔴 **锁恢复分支 500 + 运行锁泄漏**（`routers/pipelines.py`）：创建 Execution 抢运行锁失败后的"清理 stale 锁再重试"分支里，重试调用没接收返回值——若并发窗口里别的运行刚好结束、这次重试**成功**，`execution_lock` 变量未赋值会在后面 `str(execution_lock.id)` 抛 `UnboundLocalError`(500)，且刚拿到的锁引用丢失、泄漏到 10 分钟 TTL（期间该 Pipeline 全部 409）。改成赋值写法，三条路径都正确收敛。
- 🔴 **`retention_status='none'` 撞数据库 CHECK**（`pipeline/save_settings.py`）：用户给节点设 `retention: none`（或旧 NodeSpec 的 `temporary`/`trash`）时返回 `"none"`，但 `derived_datasets.retention_status` 的 CHECK 六值里没有 `none` → 写库报错、整个节点产物登记失败、execution 挂掉。改成映射到合法的 `temporary`（expires 为空 → 下次 cleanup 立即可回收，语义一致）。
- 🔴 **`superadmin` 角色不存在致紧急下架永远 403**（`services/dataset_lifecycle.py`）：`_ensure_superadmin` 要求 `has_role("superadmin")`，但 seed 只建 `admin`/`pi`（还主动删了 researcher/reviewer）。从零自建的环境里没人能持有 superadmin → 紧急下架对所有人 403、整条路径在实测里是死的。改成一并放行 `admin`（seed 里 admin 拥有全部权限）。
- 🟠 **缓存命中复用已删派生数据**（`pipeline/cache.py`）：cleanup 把过期 cached 数据标 `deleted` 但**保留物理文件**，而缓存查找只按 job_id 取、只校验"文件在 + sha256 对"，没排除 deleted → 重跑会把用户视角已删除的派生数据当命中复用。加 `deleted_at IS NULL` 过滤，与 content-addressed dedup 路径口径对齐。
- 🟡 **保存遇 409 乐观锁冲突死循环**（前端 `PipelinePage.vue`）：保存版本冲突后只显示报错、不刷新本地版本号 → 再点保存仍发旧 `expected_version`、永远 409，直到手动重载才逃。改成 409 时拉最新版本号刷新（保留画布改动），提示用户确认后可重新保存。
- 🟡 **`single_active_pipeline_run` 形同虚设**（`routers/pipelines.py`）：策略默认 `true`、能存能改，但创建 execution 时从没读过它，并发控制只有 per-pipeline 运行锁（挡不住同 Study 不同 Pipeline 并发）。补上按 `run_policy` 的 Study 级前置检查（已有活跃运行则 409）。**这是行为变化，见下**。
- 🟡 **batch 改 retention 部分提交无回滚**（`routers/pipelines.py`）：批量删除时，单条 helper 命中依赖 blocker 会"先 commit 再抛 409"，导致前几条改动已落库、后面抛错且无回滚。改成删除前全量预检 blocker、命中就在动数据之前一次性 409。
- 🟡 **前端 401 refresh 无单飞**（前端 `api/client.ts`）：并发 401 各自发一次 `/auth/refresh`。当前后端 refresh 无状态、不吊销旧 token，所以**不会**把人踢下线（子代理"几乎必现被踢"的判断已纠正），只是多刷几次；但将来若加 refresh token 轮换/黑名单就会踩雷。加模块级单飞 Promise，两个 client + 并发请求共享一次刷新。

**⚠️ 行为变化（single_active）**：修复后默认"同一研究项同一时刻只允许一个运行"（之前默认 true 但没强制，所以可能一直在并发跑多个）。经用户确认**目前保持此限制**，将来要并行并发时再放开（去研究项设置把 `run_policy.single_active_pipeline_run` 改 false）。做法是前置查询 + 409（同 Pipeline 仍由运行锁兜底）；跨 Pipeline 硬互斥需引 Study 级锁，留待后续。

**验证**：后端 4 个改动文件 `python -m py_compile` 全通过；前端 `npm run typecheck`（vue-tsc）退出 0。无本地运行环境，真实跑通待部署云端。

## 2026-06-05 · 滤波节点统一为 eeg/filter/apply + 新增 visible_when / advanced 两个 NodeSpec 原语

## 2026-06-05 · 修复 storage.py `study://` URI 解析 bug（dispatch 误写成 `project://`）

**背景**：上一条 wiki 核对中发现的代码真 bug——`services/storage.py` 的 `resolve_uri` 解析端没有 `study://` 分支，而生成端（`studies.py` / `datasets.py` / `cache.py`）大量产出 `study://{study_id}/...`。本次核实并修复。

> 黑话铺垫：**storage URI / scheme** 指给文件一个抽象地址（`scheme://netloc/path`，如 `study://202605000001/fifdata/x.fif`），由 `StorageService` 翻译成真实磁盘路径，业务层不直接拼物理路径；**dispatch** 指 `resolve_uri` 按 scheme 分流到不同解析函数。

**根因**：`resolve_uri` 的 dispatch 把 legacy 分支的 scheme 写成了 `project`（line 58），但**全后端没有任何地方生成 `project://`**（仅存在于 `_old/` 旧版与 wiki/会议日志）——是一次改名只改了 dispatch、漏改回 `study`。佐证：`_resolve_legacy_study_uri` 的 docstring（line 124）、生成端、`tests/test_storage_service.py`（line 48/62/104/105 直接 `resolve_uri("study://…")` 并断言成功）用的全是 `study://`，即这些测试此前必然 FAIL。

**为什么不按 DDL 注释统一到 `elys://studies/`**（纠正上一条的设想）：核实发现两者解析到**不同物理根**——`study://` 走 legacy resolver → `STUDIES_DIR/{id}`（= `study.data_root`，`studies.py:247` 设定，也是数据集导入 `resolve_study_relative_path` 实际写文件的地方）；`elys://studies/` 走新根 → `STUDIES_STORAGE_ROOT/{id}`（另一个目录）。把生成端改成 `elys://studies/` 等于把读取目标从有数据的 data_root 挪到空目录，是一次物理迁移而非 bug 修复。命名上 `legacy_*` / `_resolve_legacy_study_uri` 也表明 `elys://studies/`（新 Study 存储）是迁移目标、`study://`（data_root）是仍在用的现状。故采用最小正解：让解析端重新认 `study://`。

**改了什么**：
- `services/storage.py`：dispatch（line 58）`project` → `study`；`resolve_path` 的 scheme 白名单（line 81）`{"project","elys"}` → `{"study","elys"}`（否则 `study://` 会被当裸文件路径）；`_resolve_legacy_study_uri` 返回的 `scheme="project"` → `"study"`。死 scheme `project://` 直接删除不留兼容（调试期、零产出）。
- `database/schema/03_datasets.sql:197`：`dataset_files.storage_uri` 的 COMMENT 原写"例如 `elys://studies/...`"与现状不符，改为如实说明——当前导入写 legacy `study://{study_id}/{relative_path}`（解析到 data_root）、新 Study 存储用 `elys://studies/{study_id}/{relative_path}`（解析到 STUDIES_STORAGE_ROOT）。

**验证**：`py_compile` 通过；本地无 pytest/依赖，用桩掉 `app.config` 的内联脚本复刻测试断言——`study://` 解析到 legacy 根✓、带 resolver 走 data_root✓、`resolve_path("study://…")` 不再误当裸路径✓、`elys://studies/` 不受影响✓、`../`/`%2e%2e/`/`file://` 穿越仍被拒✓、`project://` 现报"Unsupported"✓，全 PASS。

**Why**：任何被存成 `study://…` 的 URI 在读取链路（`resolve_uri` / `resolve_path`）都会落到"Unsupported storage URI"或被误当裸路径，影响数据集导入后的文件读取、缓存命中引用、Study 文件浏览。

**留待**：把 legacy `study://`/`data_root` 整体迁移到新 `elys://studies/`/`STUDIES_STORAGE_ROOT`（含物理搬迁与生成端、测试改写）是独立的存储统一任务，本次不做。

## 2026-06-05 · 数据导入异步化：新增 /recordings/import-async + Celery worker + 客户端轮询

**背景**：调试用的 ERP 测试链（`elys_scripts/projects/01_erp_basic/setup.py`）上传 BrainVision 三件套时"屏幕干等几十秒、看不出卡在哪"。根因：当时唯一能用的导入端点 `POST /studies/{id}/recordings/import`（`backend/app/routers/datasets.py`）是**全同步**——一个 POST 里走完 存盘 → 校验 → `generate_canonical_fif`（BrainVision→FIF，MNE 转换，重活）→ 写库 才返回，客户端从上传到转换全程阻塞且零反馈。异步框架其实早搭了一半（`POST /recordings/import-task` + Celery + `/tasks/{id}` 状态 / 事件 / SSE 端点），但那个 worker `run_dataset_import` 是空壳（返回 `import_performed: False`，注释写"staged upload workers 启用前同步上传仍是唯一路径"），且配套的 staged 上传端点从不存在。

> 黑话铺垫：**multipart/form-data** 是浏览器传文件那种"带分隔线拼多文件"的请求体编码；**流式上传**指不把整包先攒进内存再发、而是从盘一块块读一块块发（才数得出进度）；**Celery** 是把慢活丢给独立 worker 进程的后台任务队列，HTTP 请求秒回、前端再轮询进度；**canonical FIF** 是平台把各种原始格式统一转成的 MNE `.fif` 标准件。

**改了什么**：

- **抽出共享核心 `materialize_recording_import`**（`routers/datasets.py`）：把"对已落盘文件做 校验 → 转 canonical FIF → 写库 → audit → commit"这段重活抽成一个函数，**同步端点与异步 worker 共用，单一事实源**；另抽 `_build_import_context`（鉴权 / 解析 asset / 重复 409 / 算 job_dir / 写 archiving manifest 等请求阶段前置）。同步老端点 `/recordings/import` 重构为调这两个 helper，**对外行为 / 响应不变**（纯去重，约 200 行内联逻辑收敛掉）。
- **新增端点 `POST /studies/{id}/recordings/import-async`**：请求内只把文件 archive 到 job_dir 就**秒回 task_id**，转 FIF 的重活派发给 Celery；权限、重复 409 等快判校验仍在请求内同步做掉，客户端立刻能拿到 409。

## 2026-06-05 · 修复 study_locks.lock_type CHECK 漏改导致所有 Pipeline 运行 409

**问题**：点「运行」一律 409「该工作流正在被运行」，但 `study_locks` / `pipeline_executions` 表全空。根因：`study_locks.lock_type` 的 CHECK 约束仍是早期值 `('edit', 'run')`，而运行锁代码用 `lock_type='execution'`（`pipeline_runs → pipeline_executions` 改名时漏改这条 CHECK）。INSERT 撞 CHECK → `acquire_study_lock` 把任何 `IntegrityError` 都当"锁冲突"抛 → 前端显示"正在被运行"，把真实约束错误盖住，极难定位。

**修复**：`database/schema/02_studies.sql` 的 CHECK 改为 `('edit', 'execution')`。顺带把部署默认 `PIPELINE_EXECUTION_MODE` 由 `auto` 改 `celery`、worker ping 超时 `0.5s → 3.0s`（`auto` 的 0.5s 广播 ping 探不到活着的 worker，会误回退 inline 同步执行、拖长请求并占锁）。修复后运行链路打通：派发到 Celery worker → 执行 LoadData→Epoch→ERP → `succeeded`。

**加固**：`acquire_study_lock` 不再把所有 `IntegrityError` 一律当锁冲突——只有真正撞唯一锁约束（同资源已有活跃锁）才报"正在被运行"；外键 / CHECK / 非空等约束错误照实抛出（500 + 真实报错），避免下次再被"正在被运行"盖住真因。

**与 A+B 重构无关**：属更早 Pipeline/Execution 改名的遗留；A+B（Dataset→Recording / ArtifactStore→DerivedDatasetStore）部署后导入 / 采集记录 / LoadData / 运行均已实测跑通。

## 2026-06-04 · A+B 重构（Dataset→Recording / ArtifactStore→DerivedDatasetStore）

**决策方向**：一次性消除后端两层语义错位——①原 `Dataset` ORM 实际承载 BIDS 单次采集（Recording）却与用户视角的"数据集"（DatasetAsset）撞名；②`derived_datasets` 已取代旧 `pipeline_artifacts` 但类名 / 目录 / 字段仍残留 `artifact`。调试期无真实数据，全栈彻底改名、不留兼容别名、不写迁移（DB 走 DROP + 重建）。

**方向 A：Dataset → Recording**

- ORM：`Dataset`→`Recording`、`DatasetUpload`→`RecordingVersion`；字段 `current_upload_id`→`current_version_id`、`upload_seq`→`version_seq`、`dataset_files.dataset_id`→`recording_id`、`recording_versions.recording_id`（原 `dataset_uploads.dataset_id`）、`dataset_upload_id`→`recording_version_id`；反向 relationship 统一为 `Study/Subject/DatasetAsset.recordings`
- API 端点迁移：`import` / `import-task` / `{rid}/qa` / `qa/mock-run` / `qa/review` 由 `/studies/{id}/datasets/*` 迁到 `/studies/{id}/recordings/*`；删除与 recording_router 重复的 list / files 旧端点；`/datasets/mounts/*` 保留（Mount 关于 DatasetAsset，不动）
- Schema：删 `DatasetResponse` / `DatasetListResponse` / `DatasetUploadResponse`，改用 `RecordingResponse` / `RecordingListResponse`，新增 `RecordingUploadResponse`
- 前端：删 `Dataset` / `DatasetListResponse` / `DatasetUploadResponse` / `LegacyRecording` 类型与 `recordingApi.listLegacyDatasets` 回退；`datasetApi` 五个方法路径改指 `/recordings/*`；bootstrap `next_upload.upload_endpoint` 与 DatasetsPage 上传入口改 `/recordings/import`

**方向 B：ArtifactStore → DerivedDatasetStore（前序已落地，本次补完测试）**

- 物理目录 `artifacts/`→`derived/`；`study_settings.artifact_retention_policy`→`derived_dataset_retention_policy`；旧 `pipeline-artifacts` 路由由 `/derived-datasets/*`（`update_derived_dataset` + `apply_derived_dataset_retention_action`）取代
- 测试同步：`PipelineArtifact`→`DerivedDataset`、`upstream_artifact_id`→`upstream_dataset_id`、`input_kind`/`dependency_kind` 取值更新、删除已失效的 `PipelineArtifactActionRequest` 与 pin/unpin/hide 旧路由测试
