## 2026-06-05 · 数据导入异步化：新增 /recordings/import-async + Celery worker + 客户端轮询

**背景**：调试用的 ERP 测试链（`elys_scripts/projects/01_erp_basic/setup.py`）上传 BrainVision 三件套时"屏幕干等几十秒、看不出卡在哪"。根因：当时唯一能用的导入端点 `POST /studies/{id}/recordings/import`（`backend/app/routers/datasets.py`）是**全同步**——一个 POST 里走完 存盘 → 校验 → `generate_canonical_fif`（BrainVision→FIF，MNE 转换，重活）→ 写库 才返回，客户端从上传到转换全程阻塞且零反馈。异步框架其实早搭了一半（`POST /recordings/import-task` + Celery + `/tasks/{id}` 状态 / 事件 / SSE 端点），但那个 worker `run_dataset_import` 是空壳（返回 `import_performed: False`，注释写"staged upload workers 启用前同步上传仍是唯一路径"），且配套的 staged 上传端点从不存在。

> 黑话铺垫：**multipart/form-data** 是浏览器传文件那种"带分隔线拼多文件"的请求体编码；**流式上传**指不把整包先攒进内存再发、而是从盘一块块读一块块发（才数得出进度）；**Celery** 是把慢活丢给独立 worker 进程的后台任务队列，HTTP 请求秒回、前端再轮询进度；**canonical FIF** 是平台把各种原始格式统一转成的 MNE `.fif` 标准件。

**改了什么**：

- **抽出共享核心 `materialize_recording_import`**（`routers/datasets.py`）：把"对已落盘文件做 校验 → 转 canonical FIF → 写库 → audit → commit"这段重活抽成一个函数，**同步端点与异步 worker 共用，单一事实源**；另抽 `_build_import_context`（鉴权 / 解析 asset / 重复 409 / 算 job_dir / 写 archiving manifest 等请求阶段前置）。同步老端点 `/recordings/import` 重构为调这两个 helper，**对外行为 / 响应不变**（纯去重，约 200 行内联逻辑收敛掉）。
- **新增端点 `POST /studies/{id}/recordings/import-async`**：请求内只把文件 archive 到 job_dir 就**秒回 task_id**，转 FIF 的重活派发给 Celery；权限、重复 409 等快判校验仍在请求内同步做掉，客户端立刻能拿到 409。
- **实装 worker `run_dataset_import`**（`tasks/file_tasks.py`）：从 `task.payload_json` 重建上下文（study / asset / version / duplicate / 各 BIDS label / job_dir / archived「扩展名→绝对路径」映射，全部从 payload 取——**不让 worker 重算 `upload_seq` / `job_id` 致路径漂移**）、读暂存文件、调 `materialize_recording_import`，全程 `record_task_event` 上报进度（10 暂存 → 30 校验 → 45 转换中 → 100 完成），recording 元信息写进 `result_json`。worker 用**惰性 import** 引 `routers.datasets`（顶层 import 会把 router 层拉进 worker 进程并可能造成循环 import）。
- **客户端 + 测试链**（`elys_scripts/`）：`common/elys_client.py` 新增 `import_recording_async`（手写流式 multipart 带上传进度条 → 拿 task_id → 轮询 `GET /studies/{id}/tasks/{task_id}` 直到 succeeded/failed），同步 `import_recording` 也顺手加了"上传进度条 + 转换计时"；`01_erp_basic/setup.py` 上传改走异步路径。上传体验由"一行干等几十秒"变成"上传进度条 + 轮询出的服务端阶段"两段可见。

**验证**：四个改动文件均 `py_compile` 通过；worker 里惰性 import 的符号（`materialize_recording_import` / `recording_to_response` / `get_active_study_dataset_mount_for_asset`，以及 `app.models` 的 `Study` / `User` / `Subject` / `DatasetVersion`）逐一核实可导入。无本地运行环境，真实跑通待部署到云端——**前提是计算服已有 Celery worker 消费 `CELERY_WORKFLOW_QUEUE`**（Pipeline 执行已走该队列、file 任务路由同队列，故 worker 大概率在跑；否则任务永远 `queued`、客户端轮询到超时）。

**Why**：兑现 [7-00](7-00-后端架构总览.md) §5「Dataset 导入异步化」一项，根治"大文件 / 重转换时上传请求长阻塞且无反馈"；顺带把同步端点 200 行内联逻辑抽成共享核心，消除"同步 / 异步两份转换逻辑各自漂移"的隐患。

**未做 / 留待**：真正的客户端直传对象存储（presigned / staged upload，免经 API 进程中转大文件）仍是后续；worker 转换失败只标任务 `failed`（`error_json` 带因）、未回写 manifest 的 failed 状态（任务状态为权威信号）；自动重试场景下 canonical 目录的幂等（当前 `max_attempts=1` 无自动重试，暂不触发）。

## 2026-06-05 · 前端整体风格迁移到 Steel 钢蓝主题（去花哨、降饱和；内容与交互不变）

**背景**：原全局样式 `frontend/elys-web/src/style.css` 是「v2（ported from demo）」——主色亮蓝 `#2E6BFF` + 青绿 `#00C2A8` 双跳色、主按钮蓝光晕、`.stat` 装饰圆斑、登录 / 落地 / 模块页大量蓝青径向渐变背景、头像与标题文字渐变。用户反馈"太鲜艳 / 活泼 / 廉价、缺冷静科技感"，要求**整体迁移到更克制的钢蓝（Steel）**，但**显示内容与交互方式一律不变**。

**做法（只动样式层，零 `.vue` 改动）**：在唯一的全局样式 `style.css` 上「换肤 + 去装饰」——
- **令牌降饱和**：`:root` 的 L1 品牌 / L2 语义 / L3 中性全部改钢蓝系（主色 `#2E6BFF`→`#3F5E8F`、删青绿副色、品牌渐变改同色系、语义色降彩度、中性灰转冷）。全站组件都引用 `var(--c-*)`，故 21 页一次性换肤。
- **去花哨**：主按钮光晕→极轻阴影；`.avatar` 渐变→品牌令牌；`.auth-stage`/`.hero`/`.module-hero` 蓝青渐变背景→纯色面；`.hero h1 .grad` 文字渐变→实色；脉冲动画 / 上传「处理中」蓝残留→钢蓝。
- **补字阶令牌** `--fs-display…--fs-micro`（不强改现有组件字号，避免动版式）。

**为什么这样迁**：用户强调「内容与交互不变」。新设计系统 kit 组件（分段统计卡 / 数据表 / tag2…）若套到生产页会改变信息结构与交互，属违例。故 production 迁移走「全局令牌换肤 + 去装饰」最稳：一处 CSS、全站生效、行为零风险。像素级贴近 mockup 的组件级重排留作后续按页评审。

**验证**：本地 `npm run build`（vite）通过——21 页全编译、CSS 打包无误（仅 PipelinePage 体积告警，既有）；顺带刷新 `dist/`（清掉 `ProjectsPage`/`ImportPage` 等旧迭代残留）。无运行环境，视觉待部署后核。另修了一个**本地构建早已损坏**的环境坑：`main.ts` 依赖 `@fontsource-variable/inter` 未装，`npm install` 补上。

**捋前端（顺带）**：`style.css` 3277 行，堆叠 v1 业务 / v2 demo / landing / module-* 多代迭代；抽查 `study-card`/`module-stage`/`import-scope`/`pipeline-mock` 等遗留类仍在 Index/Studies/StaticWorkbench/Datasets 使用（非死代码），`net-edge`/`task-dock` 疑似孤儿，建议后续用 PurgeCSS 做正式死 CSS 审计。仓库**无 git**，已把 `src/` 快照备份到 `_backups/elys-web-src-20260605`。

**未做（按指示 / 留待）**：observe 等"死页面"只吃全局换肤；datasets 状态列统一、组件级贴 mockup、死 CSS 审计、6-01/6-05 设计文档与令牌漂移对账，均列后续。完整说明见 `design/STYLE-MIGRATION-2026-06-05.md`。

## 2026-06-05 · 修复 study_locks.lock_type CHECK 漏改导致所有 Pipeline 运行 409

**问题**：点「运行」一律 409「该工作流正在被运行」，但 `study_locks` / `pipeline_executions` 表全空。根因：`study_locks.lock_type` 的 CHECK 约束仍是早期值 `('edit', 'run')`，而运行锁代码用 `lock_type='execution'`（`pipeline_runs → pipeline_executions` 改名时漏改这条 CHECK）。INSERT 撞 CHECK → `acquire_study_lock` 把任何 `IntegrityError` 都当"锁冲突"抛 → 前端显示"正在被运行"，把真实约束错误盖住，极难定位。

**修复**：`database/schema/02_studies.sql` 的 CHECK 改为 `('edit', 'execution')`。顺带把部署默认 `PIPELINE_EXECUTION_MODE` 由 `auto` 改 `celery`、worker ping 超时 `0.5s → 3.0s`（`auto` 的 0.5s 广播 ping 探不到活着的 worker，会误回退 inline 同步执行、拖长请求并占锁）。修复后运行链路打通：派发到 Celery worker → 执行 LoadData→Epoch→ERP → `succeeded`。

**加固**：`acquire_study_lock` 不再把所有 `IntegrityError` 一律当锁冲突——只有真正撞唯一锁约束（同资源已有活跃锁）才报"正在被运行"；外键 / CHECK / 非空等约束错误照实抛出（500 + 真实报错），避免下次再被"正在被运行"盖住真因。

**与 A+B 重构无关**：属更早 Pipeline/Execution 改名的遗留；A+B（Dataset→Recording / ArtifactStore→DerivedDatasetStore）部署后导入 / 采集记录 / LoadData / 运行均已实测跑通。

## 2026-06-04 · A+B 重构（Dataset→Recording / ArtifactStore→DerivedDatasetStore）

**决策方向**：一次性消除后端两层语义错位——①原 `Dataset` ORM 实际承载 BIDS 单次采集（Recording）却与用户视角的"数据集"（DatasetAsset）撞名；②`derived_datasets` 已取代旧 `pipeline_artifacts` 但类名 / 目录 / 字段仍残留 `artifact`。调试期无真实数据，全栈彻底改名、不留兼容别名、不写迁移（DB 走 DROP + 重建）。

**方向 A：Dataset → Recording**

- ORM：`Dataset`→`Recording`、`DatasetUpload`→`RecordingVersion`；字段 `current_upload_id`→`current_version_id`、`upload_seq`→`version_seq`、`dataset_files.dataset_id`→`recording_id`、`recording_versions.recording_id`（原 `dataset_uploads.dataset_id`）、`dataset_upload_id`→`recording_version_id`；反向 relationship 统一为 `Study/Subject/DatasetAsset.recordings`
