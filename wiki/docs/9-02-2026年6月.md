## 2026-06-11 · 修复输出 register 撞 sha256 唯一索引：死行就地复活（06-10 残留项收口）

接 06-10「修复输出回收站两缺陷」的已知残留（出处 `日志/3_元素档案260610/06_输出_StudyOutput.md` §3.3）：唯一索引 `idx_study_output_sha256 (study_id, sha256) WHERE sha256 IS NOT NULL` **不区分死活**——回收站（`deleted_at`）/ 已清盘（`purged_at`）行同样占位；而 `StudyOutputStore.register` 做 content-addressed 去重时只查活跃行、未命中即 INSERT。后果：同 study 内某输出进回收站或被 GC 清盘后，重跑工作流产出字节相同的产物 → 查不到活跃行 → INSERT 撞唯一索引 → IntegrityError → 节点执行失败。

**方案权衡（二选一，选 b）**：

- a) 索引加 `WHERE deleted_at IS NULL`：允许死行与活跃行共存同 sha——但只是把雷挪了个坑：用户恢复回收站行（清 `deleted_at`）时若活跃行已存在，flush 照样撞同一索引，IntegrityError 从 register 转移到 restore，还得再给恢复路径加预检；且结果页 / 回收站会出现同内容重复行。
- b) **register 查重不分死活、命中死行就地复活**（采用）：保住「同 `(study_id, sha256)` 恒 ≤1 行」强不变式，06-10 刚修的 restore 409 守卫、GC 删盘前共享检查、所有查询口径全部不动。复活的物理前提天然成立——`register` 被调用前同 sha 文件刚被写回同一 content-addressed 路径（未清盘行文件本来就在；已清盘行文件刚被重新 move 回来），与 06-10 封掉的「用户手动恢复 purged 行」（文件没回来的幽灵行）语义上是两回事。

**修复**：`_register_study_output` 查重去掉 `deleted_at IS NULL` 过滤；命中死行 → 清 `deleted_at`/`purged_at`，`keep`/`cache_eligible`/`retention_expires_at` 重置为本次 `apply_save_settings` 决策值（keep=true 则 TTL 清 NULL），血缘 `produced_by_*` 与用户层 `display_name`/`tags` 保留原值（与活跃行复用同口径）。schema 不动。

**顺带修复两处预存在问题**：

- 测试设施欠账：P5 给 register 加 `db.query(...)` 去重后，`test_study_output_store_study_storage.py` 的 `FakeDb` 没有 `query` 方法，两个存量测试在现行代码下本就应红——补 `_FakeColumn`/`FakeQuery` 最小查询桩。
- `StudyOutputSummary.to_dict()` 的兼容键 `storage_path` 用 `storage_uri.split("/", 3)` 截取，对 `elys://studies/{id}/outputs/...` 会把 `{study_id}/` 段留在头上——dispatcher/cache 按 `study_root / storage_path` 解析时拼出双 study_id 死路径（现网未炸是因为 `_artifact_path` 优先走 `storage_uri` 正确解析，`storage_path` 只是 fallback，但它污染 data_info 的 `fif_path`/`logical_path` 等键）。改为直接输出 `self.logical_path`（register 登记的就是相对 study_root 的 `outputs/...`）。

**测试**：补 3 条——同 sha 活跃行复用不重插 / 回收站行复活（生命周期按本次重算、keep=true 清 TTL）/ 已清盘行复活（先物理删文件模拟 GC，断言重跑后文件重新落盘 + `purged_at` 清空）。本机无 pytest / 后端依赖，用一次性 runner（stub `pydantic_settings` + 复刻 tmp_path/monkeypatch）自跑 **5/5 通过**（含修好的 2 条存量）；`py_compile` + `compileall app` 过；真实 pytest 与节点重跑行为验证需云端。

**wiki 同步**：[3-45](3-45-StudyOutput.md) §6 register 口径改写（查重不分死活 + 复活语义 + 与手动恢复 purged 行的区别）。

**事实源**：`backend/app/pipeline/study_output_store.py`、`backend/app/pipeline/contracts.py`、`backend/tests/test_study_output_store_study_storage.py`。

## 2026-06-10 · 修复输出回收站两缺陷：恢复 / 取消保留补 TTL + 已清盘行禁止恢复

元素档案盘点（`日志/3_元素档案260610/06_输出_StudyOutput.md` §9、`00_索引.md` B1/B2）发现的两个高置信度缺陷，均在「输出」的 PATCH / batch-update 链路（`routers/pipelines.py` 的 `apply_study_output_retention_action`）。

> 黑话铺垫：**TTL（time to live）** 指行的"存活期限"（`retention_expires_at` 字段），到期由每日 cleanup 任务软删进回收站；**幽灵行** 指 DB 里是活跃状态、磁盘上却已没有对应文件的登记行。

**缺陷 1 · 恢复 / 取消保留不补 TTL（用户操作形同无效）**：

- 现象：把 keep 改 false、或把回收站行恢复（deleted=false）后，`retention_expires_at` 保持 NULL 或已过期值；而每日 cleanup（`tasks/file_tasks.py` 的 `run_study_output_cleanup`）把 NULL / 已过期都视为立即可回收——下一轮定时任务直接再次软删，用户感知是"我刚恢复它怎么又没了"。
- 修复：`save_settings.py` 新增 `retention_expiry_after_user_action(keep, cache_eligible)` 作为用户动作后的 TTL 重算口径——keep=true → NULL（永不自动清，原行为不变）；keep=false 且 cache_eligible → 缓存档 `now+7d`（与产出时口径一致）；否则给宽限期 `USER_ACTION_GRACE_DAYS = 7` 天（产出时临时档"登记即过期"保持不变，仅用户显式动作走宽限；天数对齐决策清单 P3-g~l 拍板的"删除/恢复 TTL 7 天"）。`apply_study_output_retention_action` 在显式传 keep、或恢复后行仍是 keep=false 时调用重算。

**缺陷 2 · 已清盘行不挡恢复（幽灵行）**：

- 现象：PATCH 恢复不检查 `purged_at`，可把 GC 已物理删盘的行恢复成"活跃但磁盘无文件"（预览 / 下载必挂），且该行占用 `(study_id, sha256)` 唯一索引、挡同内容输出再登记；此前仅前端禁用按钮、后端无校验，直接调 API 即可绕过。
- 修复：单条 PATCH 对 `purged_at IS NOT NULL` 行的恢复返回 **409 `OUTPUT_PURGED`**（守卫排在清 deleted_at 之前，写 `.blocked` 审计，与下游依赖拦截同款）；batch-update 仿照 deleted=true 的 blocker 预检——`deleted=false` 时先全量预检 purged 行，任一命中就在改动任何数据之前整体 **409 `OUTPUT_BATCH_PURGED`**（避免循环中 commit-then-raise 造成部分成功）。

**测试**：`test_save_settings.py` 补 3 条 TTL 口径单测（keep=true 清空 / 缓存档 7d / 非缓存宽限必须在未来）；`test_pipeline_execution_routes.py` 补 3 条源码守卫（purged 守卫先于清 deleted_at、TTL 重算两处调用、batch 预检先于套用循环），并顺带修复一条 P3 改名后已失效的旧断言（仍查 `target_status == ARTIFACT_DELETED_STATUS`，该符号全仓已不存在，该测试在现行代码下本就应红）。

**已知残留（另立任务）**：回收站 / 已清盘行本身仍占 `(study_id, sha256)` 唯一索引——重跑产出同内容文件时 `StudyOutputStore.register` 只查活跃行、未命中即 INSERT，会撞索引使节点执行失败；放宽索引条件（加 `WHERE deleted_at IS NULL`）或登记时"复活"死行，需另行权衡后定，出处见 06 档案 §3.3。——已于 06-11 修复（选"复活死行"方案），见当日条目。

## 2026-06-10 · Save 重构 P5 收官：GC 物理清盘 + celery beat 定时 + 回收站

Save 重构（P1–P5）最后一块。P3 已把回收站基础（软删 `deleted_at` + 恢复 + 前端"已删除"chip）做了，本条补「物理清盘 GC」+「定时自动维护」。

> 黑话铺垫：**GC（garbage collector，垃圾回收）** 这里指后台任务定期把回收站里超期的文件真正从磁盘删掉；**content-addressed（内容寻址）** 指文件按内容哈希（sha256）存放、同样内容只存一份、被多处引用。

**三层删除语义**（用户拍板）：
- `deleted_at`（软删 / 回收站）：用户删除或 cleanup 标记，文件还在、可恢复。
- `purged_at`（物理清盘）：GC 删磁盘文件后置位，**保留期 30 天**——删后 30 天内可恢复，超期 GC 物理清盘。**只删磁盘文件、保留 DB 行**（标记 purged，血缘 / 审计可追溯"曾经有过这个输出"）。

**GC 任务 `run_study_output_gc`**：
- 清盘条件 `deleted_at < now − 30d AND purged_at IS NULL`。
- **content-addressed 安全检查**：删物理文件前查同 `sha256` 是否还有活跃（未删）行引用——有则保留物理文件、只标本行 purged（多个 execution 复用同一物理文件）；无则真删磁盘。
- 加 `POST /outputs/gc` 手动触发端点 + `study_output_gc` task 类型注册。

**定时自动维护（celery beat）**：
- `run_storage_maintenance`：每天一次全局跑 cleanup（软删过期缓存）+ GC（清盘超期回收站）；`cleanup` 改成支持全局（`study_id=None`）。
- `celery_app.py` 配 `beat_schedule`；`deploy.sh` 的 worker 加 `-B` 内嵌 beat 调度器（调试期单实例最简单）。

**前端**：`StudyOutput.purged_at`；结果页徽章加「已清盘」态、恢复按钮在 purged 后禁用（文件已删不可恢复）。

## 2026-06-10 · Save 保留策略重构启动（P1 死代码清理 + P4 节点缓存评分）

**背景**：Pipeline 的「保存 / 保留」这条线攒了一堆历史债——`Execution.save_policy` 与 `Study.derived_dataset_retention_policy` 两个**从不驱动任何行为**的死配置、节点**一刀切全缓存**（不分计算贵贱与产物大小）、retention 枚举里 `pinned` / `quarantined` 名不副实或从没人写。完整诊断（14 条逻辑缺陷 + Q1–Q10 决策）见 `日志/2_meeting260609/Save保留策略-重构方案.md`。本条落地其中两步：P1 清死代码、P4 把缓存改成按 ROI 评分。

> 黑话铺垫：**死配置（dead config）** 指字段 / 选项在代码里被创建、存储、展示，却没有任何一处真正读它做决策——纯占位、还误导用户去选；**ROI（投资回报）** 这里指缓存的性价比 = 省下的重算 ÷ 占用的存储。

**P1 删死代码**：
- 砍 `Execution.save_policy`（全栈 30+ 处：DDL 列 + 索引 + COMMENT、PipelineExecution model、3 schema、2 service、manifest、routers 10 处、前端运行对话框死下拉 + 类型 + 6 文件、2 测试）——它从不驱动产物 retention（实际由 save_settings 按节点定）。
- 砍 `Study.derived_dataset_retention_policy`（自由 dict、无消费方，7 处全栈）。
- 删 derived 侧死态 `quarantined`（`05_derived.sql` 的 CHECK + 前端枚举 / pill / label）；`dataset_assets` 侧的 `quarantined` 是活的、**保留不动**。`pinned` / `temporary` 暂留，待 P3 与 keep 布尔改造一起处理。

**P4 节点缓存评分（存储优先）**：
- 新增 `pipeline/cache_policy.py`：`cache_score = compute_cost − STORAGE_WEIGHT × output_footprint`（`> 0` 才缓存），`STORAGE_WEIGHT = 2`（存储优先旋钮）；三条硬规则——interactive 节点强制不缓存（防缓存恢复跳过人工选 ICA 成分）、`explosive` 永不物化全量、缺标签默认不缓存。
- 8 个节点 spec 删一刀切 `cache.enabled`，7 个计算节点打 `compute_cost` / `output_footprint` 标签（LoadData 这类 source 节点不打 → 评分自动判不缓存）。
- `executor` 缓存门控由读 `cache.enabled` 改为调 `is_cache_eligible(spec)`；`node_hash` 移除 cache 块（缓存策略不影响算法字节，调标签 / 权重不破缓存）。
- 效果：当前 8 节点**只有 `ica/compute` 命中缓存**（expensive 3 − 2×small 1 = +1，算得最久、产物最小），其余跑完即走、省空间。

**Why**：死配置让用户在运行对话框选一个「选完就扔进黑洞」的保存策略、徒增认知负担；一刀切全缓存对滤波这种「算得快、产物大」的节点是**负收益**（存它 + 读它算哈希比重算还慢），对未来的单试次 TFR 更是 OOM 灾难。先清债、再把缓存改成按 ROI 自动判定（存储优先），是 Save 重构里最独立、最可静态验证的两步。

**范围 / 验证**：纯后端 + 前端，不碰运行环境；后端 `py_compile`、前端 `npm run typecheck`、全仓 `grep save_policy` 归零均通过；`cache_policy` 逻辑本机跑 8 节点确认仅 ICA 命中。调试期 DROP 重建、不留兼容层。**后续 P2（输出改名）/ P3（retention 三层解耦）/ P5（GC + 回收站）的关键正确性（表名 / 外键 / 部署）本机验不了，待云端验证后续推。**

**事实源**：`backend/app/pipeline/cache_policy.py`·`hash.py`·`executor.py`·`nodes/*.json`、`database/schema/02_studies.sql`·`04_pipelines.sql`·`05_derived.sql`、`backend/app/{models,schemas,services,routers}` 相关、`frontend/elys-web/src/{types,composables/pipeline,views}`；方案 `日志/2_meeting260609/Save保留策略-重构方案.md`。

## 2026-06-10 · 修复工作流画布卡"正在初始化" + 右键无菜单：拆掉 keep-alive 里的 Teleport

**现象**：进研究项「工作流·运行」tab，画布永远停在"正在初始化画布"、节点右键弹不出菜单、底部状态栏"节点 0"与画布里实际节点数对不上——但 LiteGraph 画布本身有节点、能拖拽加节点。控制台一串 `TypeError: Cannot use 'in' operator to search for 'value' in null` 与 `Cannot read properties of null (reading 'insertBefore')`。

**真因**：`PipelinePage.vue` 顶部把「工作流选择器 / 新建」用 `<Teleport to=".study-layout__extra">` 吊到研究项容器标题栏，而 PipelinePage 又被 StudyLayout 的 `<keep-alive>` 缓存。`<Teleport>` + `<keep-alive>` + 内含 `<select :value>` 三者相撞，触发 **Vue 渲染器**（`runtime-dom` / `runtime-core`，**非 LiteGraph**）在 patch 阶段给 null 元素写 `value` 属性、往 null 父节点 `insertBefore`，**整页 Vue 的 DOM 更新被这个崩溃冻结**。于是 `liteGraphReady` 其实早已 true、但 DOM 刷不动 → 永远"正在初始化"；右键把菜单 `open=true` 也渲染不出；节点数文字绑定同样卡死。LiteGraph 直接画在 canvas 上、绕过 Vue，所以画布节点正常——造成"画布有节点、Vue 文字全卡"的假象。

> 黑话铺垫：**Teleport** 是 Vue 把一段模板"瞬移"到 DOM 别处渲染的内置组件；**keep-alive** 是缓存组件实例、切走不销毁、切回不重建。两者叠加是 Vue 已知的脆弱组合——被缓存组件的 DOM 搬移会让 Teleport 目标在 patch 时变 null。

**改了什么**：删掉该 `<Teleport>`，工作流选择器 / 新建**就地渲染**在工作流页自己的工具条里（回到加该特性之前）；连带删 `teleportActive` ref 及其在 `onActivated` / `onDeactivated` 的开关。

**副作用**：撤掉了"把工具条吊到研究项顶栏"的视觉效果——选择器现在在工作流页工具条内、不在最顶 bar。若要保留该效果，须改 keep-alive 安全的跨层传递（provide/inject 或 store），别再用 Teleport；StudyLayout 的 `.study-layout__extra` 槽位暂闲置但无害。

**定位方法论**（留给后续）：生产构建报错是 minified 单字母栈（`Df` / `P` / `_`），曾连猜 HMR、LiteGraph 悬空连线均错。最终在 `vite.config.ts` 临时开 `build.sourcemap` 重新部署，报错才显真名、直指 Vue 渲染器，一举定位；修复确认后已关回。教训：云端 minified 报错看不懂时，先开 sourcemap 重部署拿真实栈，别耗在猜混淆名上。

**范围 / 验证**：纯前端；`npm run typecheck` + `npm run build` 通过；真机部署后画布初始化、右键菜单、节点计数全部恢复。

**事实源**：`frontend/elys-web/src/views/PipelinePage.vue`、`frontend/elys-web/src/views/study/StudyLayout.vue`。

## 2026-06-09 · 数据集生命周期 v2 定稿：发布≠分享、可见范围只升不降（废止 06-07 旧决策）

**背景**：起因于 DatasetsPage 把未发布态的内部英文枚举值直接暴露给用户，进而对 ELYS 数据集（`DatasetAsset` / `DatasetVersion`）的生命周期、状态、权限做了一次彻底重审，并对 wiki 与代码逐项核对。产出《数据集生命周期重构_综合报告 v2》（11 项决策闭环）+《落地实施清单》，作为新设计基线，落地后 [3-25](3-25-数据集生命周期与发布机制.md) 据此改写。

**这条作什么用**：本条只**宣告 v2 定稿并废止 06-07 旧决策**；逐项 schema / 服务层 / 路由 / 前端 / wiki 的落地改动随各自提交另记。06-07 两条旧记录（「可见范围=发表级、发布自动私有→共享」与「徽章用可见范围轴 B 方案」，见本页下方）**保留不改**，作历史留痕。

**v2 相对 06-07 变了什么（核心 5 条 + 配套清理）**：

- **发布 ≠ 分享（废止「发布自动私有→共享」）**：发布只做两件事——冻结版本文件 + 铸 DOI；可见范围**默认私有、不自动转共享**。是否对外可见，由负责人在发布后**单独**决定。06-07 的「发布即自动 `private→shared`」被废止（删 `dataset_lifecycle.py` 里那段自动跳变）。
- **可见范围「只升不降、无降级接口」（修正 06-07 B 方案的「只读徽章随发布联动」轴）**：私有→共享→公开可跳级开放，但**任何降级都没有入口**（共享/公开＝不可逆释放，类比论文发表）。可见范围从「通用 PATCH 可写」改由**专门的「开放」端点**处理（只升、仅负责人）；要可撤销的协作改用「私有 + 把人加进研究项团队」。
- **共享 = 邀请制（按用户授权），不再等于「任意登录用户可见」**：新建 `dataset_members` 表 `(asset_id, user_id, granted_by, granted_at)`，负责人**按用户**授权；`shared` 仅被授权者可读 / 可关联。`public` 才是「任何注册用户」——平台全员注册、**无匿名访问**，故公开＝全平台登录用户、无需匿名路由。私有＝负责人 + 管理员 + **主研究项成员**。
- **发布是 PII / 伦理 / 版权关口**：未发布→已发布时强制勾选「已脱敏」确认并声明伦理与版权，缺则不能发布；每次发布都要重做（每个已发布版本是独立不可变制品）。
- **撤回审核中禁止新关联**（修正旧代码「允许新挂载」）：已有关联保留，但不接受新关联；已撤回为终态墓碑，只能开新版本 v+1 前进。
- **配套清理**：发布状态枚举全栈统一为 `unpublished`（替换旧未发布枚举值，含 DB CHECK / 接口 / 前端，物理槽位名 `version_label="working"` 不在此列）；资产 `dataset_assets.status` 的 `working` / `active` 合并为 `working`；清理已被 `state` 取代的旧字段 `dataset_versions.status`；发布/授权/撤回申请收敛为**仅负责人**（管理员只保留撤回审核、紧急下架、隔离等平台治理；`superadmin` 角色保留另作平台治理用）。

**两根正交轴（概念模型）**：发布状态轴（版本级 `DatasetVersion.state`：`unpublished` / `published` / `withdraw_requested` / `withdrawn`）管「能不能改 / 删、是否冻结、是否铸 DOI」；可见范围轴（资产级 `DatasetAsset.visibility`：`private` / `shared` / `public`）管「谁能看、谁能关联」。核心一句话：**发布只冻结＋铸 DOI，分享是另一个独立动作**。

**术语锁定**：界面同时给中英两套标签，「导入 Import / 关联 Link / 加载 Load」三件事严格不混——导入＝外部文件进平台造数据集，关联＝研究项接上已有数据集（数据不搬动，原「挂载 Mount」改称），加载＝Pipeline LoadData 节点运行时读数据；专有名词中英一一对应、杜绝中英混排。

## 2026-06-08 · 新增 buy_ecs：按启动模板 + 抢占式购买 ECS（cmd → ps1，用 aliyun CLI、不引 Python）

**背景**：计算服务器是阿里云按量 / 抢占实例、**公网 IP 每次部署都会变**（见 `AGENTS.md`），过去每次都得到 ECS 控制台手动开机、再把新公网 IP 抄回 `deploy/profiles/aliyun-test.env` 的 `COMPUTE_SERVER_IP`，繁琐且易抄错。用户要"按**自己制定的启动模板**、用**抢占式**买，而且不用 Python、像部署那样直接写个 `cmd`"。

**改了什么**：

- 新增 `buy_ecs.cmd`（仓库根，4 行壳子，与 `deploy_remote.cmd` 同款）转手调 `elys_project/deploy/buy_ecs.ps1`；真活全在 ps1 的 `param()` 块里。

## 2026-06-07 · 决策：数据集可见范围（私有 / 共享 / 公开）是「发表级」严肃动作

**决策**：数据集的可见范围（`dataset_assets.visibility`）不是一个能随手切换的开关，而是**类比学术论文发表的严肃决策**。它只有三档，且只能通过郑重的发布 / 撤回流程流转，**UI 不提供随意下拉**。

**三档语义**：

| 档位 | 取值 | 谁能看 / 用 | 怎么进入 |
|---|---|---|---|
| **私有** | `private`（默认） | 仅**主研究项**可见、可挂载使用 | 新建数据集即私有 |
| **共享** | `shared` | **其他研究项**可挂载 / 引用（跨 Study 解锁） | 由「**发布版本**」流程触发：发布某版本时自动 `private→shared` |
| **公开** | `public` | 全平台可见 | 比"发布=共享"更进一步的 deliberate 动作（确认弹窗），**留作后续**，当前无 UI 入口 |

**流转规则**：

- **开放（私有→共享）= 发布**：必须走「发布版本」流程（强制 SemVer 版本号、发布后该版本文件不可改、要改开新版本），等同于"把这版数据正式发表出去"。发布成功后可见范围自动升到 `shared`。
- **收回 = 撤回，不是回退**：已发布版本要下架，走「申请撤回 → 管理员审核」流程（紧急情况由超级管理员紧急下架，事后补审计）；`withdrawn` 是终态，要继续工作只能开新版本前向演进。**可见范围不因撤回自动降级回私有**——已发布过即视为"曾公开"，其他研究项可能已引用。
- 因此**不存在"把已发布数据一键改回私有"的随意操作**；这条铁律就是不给 UI 下拉控件的原因。

**UI 落地**（同日实现，详见下方"可见范围轴"与"交互回退"两条）：数据集徽章**只读展示**当前可见范围（私有/共享/公开）+ 解释性 tooltip；改变可见范围一律经由发布 / 撤回流程，不出现随意下拉。

**Why**：科研数据一旦对外共享 / 被他人引用，就具备了和论文发表同等的不可随意撤销性（下游引用稳定性、学术诚信、DOI 不可逆）。把"开放可见范围"做成一个轻飘飘的下拉，会诱发误操作并破坏引用方的信任；交给版本发布这个本就郑重、可追溯、带版本号的流程，才与这件事的严肃程度匹配。

**相关事实源**：`backend/app/services/dataset_lifecycle.py`（发布自动 `private→shared`、撤回不降级）、`database/schema/03_datasets.sql`（`visibility` CHECK 三档）、`wiki/docs/3-25-数据集生命周期与发布机制.md`（draft/published/withdrawn 生命周期与跨 Study 引用门控）。

## 2026-06-05 · 找茬收尾：4 个未深验候选逐个核实（3 个坐实并修、1 个确认非 bug）

**核实结论 + 处理**：

- ✅ **修 · 异步导入 worker 不复检 asset/mount 状态**（`tasks/file_tasks.py::run_dataset_import`）：同步导入在请求内由 `resolve_upload_dataset_asset` 校验"asset 状态可上传 + asset 已 active 挂载到本 Study"，但异步 worker 从 payload 直接按 id 取 asset、没复检——请求受理到 worker 执行有时间窗，期间 asset 被归档/隔离/删除、或 mount 被停用，worker 仍照写。已在 materialize 前补 `ensure_dataset_asset_uploadable` + `ensure_dataset_asset_active_mounted`，与同步路径对齐（不合规则任务 failed、带原因）。

## 2026-06-05 · 代码逻辑找茬：修 8 处后端/前端真实 bug（锁恢复 / retention / superadmin / 缓存 / 乐观锁 / 单活跃 / batch 事务 / refresh 单飞）

**背景**：延续 wiki 全章核对的思路，反过来拿 wiki 描述的"应有行为"当规格去读代码找**逻辑错误**（不是文档措辞）。5 个子代理按子系统并行深挖，再逐条亲自 Read 代码复验（子代理有误报前科，下文标了两处被纠正的高估）。共坐实并修复 8 处。

> 黑话铺垫：**乐观锁**指保存时带上"我看到的版本号"，服务端发现版本对不上就拒绝(409)、防止后写覆盖先写；**单飞(single-flight)** 指同一时刻多个请求要做同一件事(刷 token)时只真正做一次、其余共享结果；**CHECK 约束**是数据库给某列限定的合法取值集合，写了集合外的值会直接报错拒绝写入。

**改了什么（按严重度）**：

- 🔴 **锁恢复分支 500 + 运行锁泄漏**（`routers/pipelines.py`）：创建 Execution 抢运行锁失败后的"清理 stale 锁再重试"分支里，重试调用没接收返回值——若并发窗口里别的运行刚好结束、这次重试**成功**，`execution_lock` 变量未赋值会在后面 `str(execution_lock.id)` 抛 `UnboundLocalError`(500)，且刚拿到的锁引用丢失、泄漏到 10 分钟 TTL（期间该 Pipeline 全部 409）。改成赋值写法，三条路径都正确收敛。
- 🔴 **`retention_status='none'` 撞数据库 CHECK**（`pipeline/save_settings.py`）：用户给节点设 `retention: none`（或旧 NodeSpec 的 `temporary`/`trash`）时返回 `"none"`，但 `derived_datasets.retention_status` 的 CHECK 六值里没有 `none` → 写库报错、整个节点产物登记失败、execution 挂掉。改成映射到合法的 `temporary`（expires 为空 → 下次 cleanup 立即可回收，语义一致）。
- 🔴 **`superadmin` 角色不存在致紧急下架永远 403**（`services/dataset_lifecycle.py`）：`_ensure_superadmin` 要求 `has_role("superadmin")`，但 seed 只建 `admin`/`pi`（还主动删了 researcher/reviewer）。从零自建的环境里没人能持有 superadmin → 紧急下架对所有人 403、整条路径在实测里是死的。改成一并放行 `admin`（seed 里 admin 拥有全部权限）。
- 🟠 **缓存命中复用已删结果**（`pipeline/cache.py`）：cleanup 把过期 cached 数据标 `deleted` 但**保留物理文件**，而缓存查找只按 job_id 取、只校验"文件在 + sha256 对"，没排除 deleted → 重跑会把用户视角已删除的结果当命中复用。加 `deleted_at IS NULL` 过滤，与 content-addressed dedup 路径口径对齐。

- 🟡 **batch 改 retention 部分提交无回滚**（`routers/pipelines.py`）：批量删除时，单条 helper 命中依赖 blocker 会"先 commit 再抛 409"，导致前几条改动已落库、后面抛错且无回滚。改成删除前全量预检 blocker、命中就在动数据之前一次性 409。

## 2026-06-05 · 修复 storage.py `study://` URI 解析 bug（dispatch 误写成 `project://`）

**背景**：上一条 wiki 核对中发现的代码真 bug——`services/storage.py` 的 `resolve_uri` 解析端没有 `study://` 分支，而生成端（`studies.py` / `datasets.py` / `cache.py`）大量产出 `study://{study_id}/...`。本次核实并修复。

> 黑话铺垫：**storage URI / scheme** 指给文件一个抽象地址（`scheme://netloc/path`，如 `study://202605000001/fifdata/x.fif`），由 `StorageService` 翻译成真实磁盘路径，业务层不直接拼物理路径；**dispatch** 指 `resolve_uri` 按 scheme 分流到不同解析函数。

**根因**：`resolve_uri` 的 dispatch 把 legacy 分支的 scheme 写成了 `project`（line 58），但**全后端没有任何地方生成 `project://`**（仅存在于 `_old/` 旧版与 wiki/会议日志）——是一次改名只改了 dispatch、漏改回 `study`。佐证：`_resolve_legacy_study_uri` 的 docstring（line 124）、生成端、`tests/test_storage_service.py`（line 48/62/104/105 直接 `resolve_uri("study://…")` 并断言成功）用的全是 `study://`，即这些测试此前必然 FAIL。

**为什么不按 DDL 注释统一到 `elys://studies/`**（纠正上一条的设想）：核实发现两者解析到**不同物理根**——`study://` 走 legacy resolver → `STUDIES_DIR/{id}`（= `study.data_root`，`studies.py:247` 设定，也是数据集导入 `resolve_study_relative_path` 实际写文件的地方）；`elys://studies/` 走新根 → `STUDIES_STORAGE_ROOT/{id}`（另一个目录）。把生成端改成 `elys://studies/` 等于把读取目标从有数据的 data_root 挪到空目录，是一次物理迁移而非 bug 修复。命名上 `legacy_*` / `_resolve_legacy_study_uri` 也表明 `elys://studies/`（新 Study 存储）是迁移目标、`study://`（data_root）是仍在用的现状。故采用最小正解：让解析端重新认 `study://`。

**改了什么**：
- `services/storage.py`：dispatch（line 58）`project` → `study`；`resolve_path` 的 scheme 白名单（line 81）`{"project","elys"}` → `{"study","elys"}`（否则 `study://` 会被当裸文件路径）；`_resolve_legacy_study_uri` 返回的 `scheme="project"` → `"study"`。死 scheme `project://` 直接删除不留兼容（调试期、零产出）。
- `database/schema/03_datasets.sql:197`：`dataset_files.storage_uri` 的 COMMENT 原写"例如 `elys://studies/...`"与现状不符，改为如实说明——当前导入写 legacy `study://{study_id}/{relative_path}`（解析到 data_root）、新 Study 存储用 `elys://studies/{study_id}/{relative_path}`（解析到 STUDIES_STORAGE_ROOT）。

**验证**：`py_compile` 通过；本地无 pytest/依赖，用桩掉 `app.config` 的内联脚本复刻测试断言——`study://` 解析到 legacy 根✓、带 resolver 走 data_root✓、`resolve_path("study://…")` 不再误当裸路径✓、`elys://studies/` 不受影响✓、`../`/`%2e%2e/`/`file://` 穿越仍被拒✓、`project://` 现报"Unsupported"✓，全 PASS。

**Why**：任何被存成 `study://…` 的 URI 在读取链路（`resolve_uri` / `resolve_path`）都会落到"Unsupported storage URI"或被误当裸路径，影响数据集导入后的文件读取、缓存命中引用、Study 文件浏览。

**留待**：把 legacy `study://`/`data_root` 整体迁移到新 `elys://studies/`/`STUDIES_STORAGE_ROOT`（含物理搬迁与生成端、测试改写）是独立的存储统一任务，本次不做。

## 2026-06-05 · 数据导入异步化：新增 /recordings/import-async + Celery worker + 客户端轮询

**背景**：调试用的 ERP 测试链（`elys_scripts/projects/01_erp_basic/setup.py`）上传 BrainVision 三件套时"屏幕干等几十秒、看不出卡在哪"。根因：当时唯一能用的导入端点 `POST /studies/{id}/recordings/import`（`backend/app/routers/datasets.py`）是**全同步**——一个 POST 里走完 存盘 → 校验 → `generate_canonical_fif`（BrainVision→FIF，MNE 转换，重活）→ 写库 才返回，客户端从上传到转换全程阻塞且零反馈。异步框架其实早搭了一半（`POST /recordings/import-task` + Celery + `/tasks/{id}` 状态 / 事件 / SSE 端点），但那个 worker `run_dataset_import` 是空壳（返回 `import_performed: False`，注释写"staged upload workers 启用前同步上传仍是唯一路径"），且配套的 staged 上传端点从不存在。

> 黑话铺垫：**multipart/form-data** 是浏览器传文件那种"带分隔线拼多文件"的请求体编码；**流式上传**指不把整包先攒进内存再发、而是从盘一块块读一块块发（才数得出进度）；**Celery** 是把慢活丢给独立 worker 进程的后台任务队列，HTTP 请求秒回、前端再轮询进度；**canonical FIF** 是平台把各种原始格式统一转成的 MNE `.fif` 标准件。

**改了什么**：

- **抽出共享核心 `materialize_recording_import`**（`routers/datasets.py`）：把"对已落盘文件做 校验 → 转 canonical FIF → 写库 → audit → commit"这段重活抽成一个函数，**同步端点与异步 worker 共用，单一事实源**；另抽 `_build_import_context`（鉴权 / 解析 asset / 重复 409 / 算 job_dir / 写 archiving manifest 等请求阶段前置）。同步老端点 `/recordings/import` 重构为调这两个 helper，**对外行为 / 响应不变**（纯去重，约 200 行内联逻辑收敛掉）。
- **新增端点 `POST /studies/{id}/recordings/import-async`**：请求内只把文件 archive 到 job_dir 就**秒回 task_id**，转 FIF 的重活派发给 Celery；权限、重复 409 等快判校验仍在请求内同步做掉，客户端立刻能拿到 409。
- **实装 worker `run_dataset_import`**（`tasks/file_tasks.py`）：从 `task.payload_json` 重建上下文（study / asset / version / duplicate / 各 BIDS label / job_dir / archived「扩展名→绝对路径」映射，全部从 payload 取——**不让 worker 重算 `upload_seq` / `job_id` 致路径漂移**）、读暂存文件、调 `materialize_recording_import`，全程 `record_task_event` 上报进度（10 暂存 → 30 校验 → 45 转换中 → 100 完成），recording 元信息写进 `result_json`。worker 用**惰性 import** 引 `routers.datasets`（顶层 import 会把 router 层拉进 worker 进程并可能造成循环 import）。
- **客户端 + 测试链**（`elys_scripts/`）：`common/elys_client.py` 新增 `import_recording_async`（手写流式 multipart 带上传进度条 → 拿 task_id → 轮询 `GET /studies/{id}/tasks/{task_id}` 直到 succeeded/failed），同步 `import_recording` 也顺手加了"上传进度条 + 转换计时"；`01_erp_basic/setup.py` 上传改走异步路径。上传体验由"一行干等几十秒"变成"上传进度条 + 轮询出的服务端阶段"两段可见。

**验证**：四个改动文件均 `py_compile` 通过；worker 里惰性 import 的符号（`materialize_recording_import` / `recording_to_response` / `get_active_study_dataset_mount_for_asset`，以及 `app.models` 的 `Study` / `User` / `Subject` / `DatasetVersion`）逐一核实可导入。无本地运行环境，真实跑通待部署到云端——**前提是计算服已有 Celery worker 消费 `CELERY_WORKFLOW_QUEUE`**（Pipeline 执行已走该队列、file 任务路由同队列，故 worker 大概率在跑；否则任务永远 `queued`、客户端轮询到超时）。

**Why**：兑现 [7-00](7-00-后端架构总览.md) §5「Dataset 导入异步化」一项，根治"大文件 / 重转换时上传请求长阻塞且无反馈"；顺带把同步端点 200 行内联逻辑抽成共享核心，消除"同步 / 异步两份转换逻辑各自漂移"的隐患。

**未做 / 留待**：真正的客户端直传对象存储（presigned / staged upload，免经 API 进程中转大文件）仍是后续；worker 转换失败只标任务 `failed`（`error_json` 带因）、未回写 manifest 的 failed 状态（任务状态为权威信号）；自动重试场景下 canonical 目录的幂等（当前 `max_attempts=1` 无自动重试，暂不触发）。

## 2026-06-05 · 修复 study_locks.lock_type CHECK 漏改导致所有 Pipeline 运行 409

**问题**：点「运行」一律 409「该工作流正在被运行」，但 `study_locks` / `pipeline_executions` 表全空。根因：`study_locks.lock_type` 的 CHECK 约束仍是早期值 `('edit', 'run')`，而运行锁代码用 `lock_type='execution'`（`pipeline_runs → pipeline_executions` 改名时漏改这条 CHECK）。INSERT 撞 CHECK → `acquire_study_lock` 把任何 `IntegrityError` 都当"锁冲突"抛 → 前端显示"正在被运行"，把真实约束错误盖住，极难定位。

**修复**：`database/schema/02_studies.sql` 的 CHECK 改为 `('edit', 'execution')`。顺带把部署默认 `PIPELINE_EXECUTION_MODE` 由 `auto` 改 `celery`、worker ping 超时 `0.5s → 3.0s`（`auto` 的 0.5s 广播 ping 探不到活着的 worker，会误回退 inline 同步执行、拖长请求并占锁）。修复后运行链路打通：派发到 Celery worker → 执行 LoadData→Epoch→ERP → `succeeded`。

**加固**：`acquire_study_lock` 不再把所有 `IntegrityError` 一律当锁冲突——只有真正撞唯一锁约束（同资源已有活跃锁）才报"正在被运行"；外键 / CHECK / 非空等约束错误照实抛出（500 + 真实报错），避免下次再被"正在被运行"盖住真因。

**与 A+B 重构无关**：属更早 Pipeline/Execution 改名的遗留；A+B（Dataset→Recording / ArtifactStore→DerivedDatasetStore）部署后导入 / 采集记录 / LoadData / 运行均已实测跑通。

## 2026-06-04 · A+B 重构（Dataset→Recording / ArtifactStore→DerivedDatasetStore）

**决策方向**：一次性消除后端两层语义错位——①原 `Dataset` ORM 实际承载 BIDS 单次采集（Recording）却与用户视角的"数据集"（DatasetAsset）撞名；②`derived_datasets` 已取代旧 `pipeline_artifacts` 但类名 / 目录 / 字段仍残留 `artifact`。调试期无真实数据，全栈彻底改名、不留兼容别名、不写迁移（DB 走 DROP + 重建）。

**方向 A：Dataset → Recording**
