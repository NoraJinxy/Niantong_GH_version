## 1. 核心问题

## 2. 设计原则

1. **数据资产先于研究项**：Dataset Asset 是物理身份，独立于 Study 存在。Study 通过 Mount 引用 Asset，不拥有 Asset。
2. **不可变发表 (Immutable Publication)**：Asset 的每次发表都是不可变快照。要修改必须开新版本，已发表版本不可改文件。
3. **版本即引用**：Mount、Pipeline Input、Derived Dataset 引用的都是具体 `DatasetVersion`，不是 Asset 本身。
4. **跨 Study 引用受发表门控**：只有 published 版本能被其他 Study 挂载和引用。draft 数据隔离在主 Study 内。
5. **撤回不删除**：撤回的版本变成墓碑，元数据、引用关系、Execution 历史全部保留。

## 3. 数据集状态机

### 3.1 状态机定义

```
                ┌─────────┐
                │ created │
                └────┬────┘
                     │
                     ▼
              ┌──────────────┐  主 Study 可读可写
              │  draft (v1)  │  其他 Study 不可见 / 不可挂载
              │              │  主 Study 内可跑 Pipeline (产物自动 draft)
              └──────┬───────┘
                     │
                     │ [owner 点发表]
                     │ ─ 校验 SemVer 格式
                     │ ─ 不强制 QA pass,但展示 qa_status
                     │ ─ 计算 content_hash (异步)
                     │ ─ 注册 Version DOI;首次发表时建 Concept DOI
                     ▼
              ┌──────────────────┐  immutable
              │ published (v1)   │  其他 Study 可挂载 (锁定到 v1)
              │ qa_status: pass  │  跨 Study 引用解锁
              │   /fail/not_run  │  派生数据可升级到 published
              └────┬──────────┬──┘
                   │          │
       [想改]      │          │  [owner 提交撤回申请 + 理由]
                   ▼          ▼
        ┌──────────────┐  ┌────────────────────┐
        │ draft (v2)   │  │ withdraw_requested │
        │ (v1 仍可用)  │  └─────────┬──────────┘
        └──────────────┘            │
                                    │ [管理员审核]
                          ┌─────────┴──────────┐
                          ▼                    ▼
                  approved             rejected
                          │                    │
                          ▼                    ▼
                  ┌────────────┐      回到 published
                  │ withdrawn  │      (审核记录留痕)
                  │  (终态)    │
                  └────────────┘
                  ─ 墓碑页保留: name/owner/dates/DOI/withdraw_reason/admin_notes
                  ─ 已有 mount/Execution 引用: 保留 (兼容历史)
                  ─ 新挂载/新 Execution 引用: 禁止
                  ─ 通知所有引用方
```

### 3.2 状态转换权限矩阵

| 转换 | 触发者 | 前置条件 | 副作用 |
|---|---|---|---|
| `created → draft` | Asset owner | 创建 Asset 即进入 draft v1 | 主 Study 自动设置 (来自 bootstrap) |
| `draft → published` | Asset owner | SemVer 校验通过 + content_hash 计算完成 | 注册 DOI、冻结 `dataset_files`、通知挂载该版本的 Study |
| `published → draft (v+1)` | Asset owner | 旧版本保持 published | 创建新版本行,v1 不受影响 |
| `published → withdraw_requested` | Asset owner | 必须填写 `withdraw_reason` | 进入审核队列 |
| `withdraw_requested → withdrawn` | 平台管理员 | 审核通过 | 写 `withdrawn_at` / `withdrawn_by` / `withdrawal_admin_notes`,生成墓碑,通知引用方 |
| `withdraw_requested → published` | 平台管理员 | 审核拒绝 | 留存审核记录,清空 `withdraw_requested_*` 字段 |
| `published → withdrawn` (紧急下架) | **超级管理员**专属 | 仅限 PII 泄露 / 法律风险等紧急场景 | 跳过审核,但必须事后补审计记录 |

### 3.3 派生数据的生命周期继承

派生数据集 (`DerivedDataset`) 的状态由 upstream 推导:

| upstream 状态 | 派生数据初始状态 | 跨 Study 可用 |
|---|---|---|
| `draft` | `draft` | ✗ |
| `published` (主 Study 内 Execution 产出) | `draft` (需 owner 选择升级) | ✗ → 升级后 ✓ |
| `withdrawn` | 联动 `withdrawn` | 已有引用保留,新引用禁止 |

## 5. 四项关键决策 (已拍板)

### 5.1 撤回机制 (DEC-2026-0531-A)

- **撤回可申请**:类比论文撤稿,owner 提交申请 + 理由
- **管理员审核**:platform admin 审批,approved 后进入 withdrawn 终态
- **不可逆**:withdrawn 是终态,不能退回 draft。要继续工作必须开 v+1 新版本 (前向演进,不是状态回退)
- **紧急下架通道**:仅限超级管理员,绕过审核,事后补审计记录。用于 PII 泄露 / 法律风险等

**反例**:不支持 "withdrawn → draft" 状态转换。理由:DataCite DOI 不可逆向、下游引用稳定性、学术撤稿标准。

### 5.2 主 Study 在 published 后保留 (DEC-2026-0531-B)

- `DatasetAsset.primary_study_id` 在 published 后**保留作"出身记录"**
- UI 显示为 "originally curated in Study X"
- 外键 `ON DELETE SET NULL`:删除 Study 不影响 Asset,但 Asset 失去主 Study 标识

**反例**:不采用"published 后解除主 Study 关系"方案。理由:出身信息有学术价值 + 删除 Study 仍能优雅降级。

### 5.3 SemVer 强制 (DEC-2026-0531-C)

`version_label` 必须符合 `x.y.z` 格式:

- **major**: 实验设计变更 (任务范式变了 / 通道布局变了 / 采样率变了)
- **minor**: 加被试 / 加 session / 加新条件
- **patch**: 元数据笔误 / 注释修正 / sidecar 补全

**首版默认 1.0.0**,允许 owner 显式使用 0.x.y 表示 pre-release / 未稳定状态。

**反例**:不采用任意字符串版本号。理由:OpenNeuro / PhysioNet 实践证明 SemVer 能传递变更语义,任意字符串无法机器解析。

### 5.4 紧急下架通道 (DEC-2026-0531-D)

- 仅 `superadmin` 角色可触发
- 跳过审核流程,直接 `published → withdrawn`
- **必须事后补审计**:`dataset_withdrawal_requests.decision = 'emergency'`,`admin_notes` 必填
- 使用场景:PII 泄露、法律强制下架、严重数据错误

## 6. 业内调研对照

| 平台 | 已发布能否删 | 撤回后墓碑 | DOI 处理 | 版本机制 |
|---|---|---|---|---|
| **OpenNeuro** | owner 自助即可删 | 弱:默认无墓碑,支持 redirect URL | landing page 持久 | git tag = snapshot,推荐 SemVer |
| **Zenodo** | 30 天内可自删;之后需提交理由审核 | **强**:固定墓碑页,保留 DOI + URL + 撤回原因 | DOI 永久,解析到墓碑 | "New Version"按钮,已发布版不可改 |
| **PhysioNet** | 几乎不允许 | 未公开 | 每版独立 DOI + Latest DOI | 强制 x.y.z SemVer |
| **OSF** | Project 可删;Registration 不可删但可 withdraw | 强 (registration 必留墓碑) | DOI 保留 | Registration 不版本化 |
| **Dryad** | "exceptional action",类比文章撤稿 | 弱:原数据保留 + warning | 单一 DOI 跨版本共享 | 可发新版,旧版保留 |

**ELYS 采纳的实践**:

1. **Zenodo 模式**:撤回需审核 + 强制墓碑 (`dataset_withdrawal_requests` 表)
2. **PhysioNet 模式**:强制 SemVer x.y.z 格式
3. **Zenodo 双 DOI**:`DatasetAsset.concept_doi` + `DatasetVersion.version_doi`
4. **OpenNeuro 失败教训**:不允许 owner 一键删除已发布版本 (避开 Issue #1176 同类问题)

**ELYS 差异化**:做下游引用追踪 (`dataset_version_references`),撤回时主动通知。这是 OpenNeuro / Zenodo 都没做好的环节。

## 7. 6 阶段迁移路线

设计原则:**加法优先,破坏最后**。前 4 个阶段全部是"加字段、加表、加状态机",不破坏现有 API,每阶段独立可发布、可回滚。

| 阶段 | 做什么 | 风险 | 估算 | 可独立交付 |
|---|---|---|---|---|
| **0. 落档** | 本文档 + 数据现状盘点 | 无 | 半天 | ✓ |
| **1. 扩展 schema** | 加字段/加表,全部 nullable,不改业务逻辑 | 低 | 1-2 天 | ✓ |
| **2. 历史数据回填** | 旧 dataset 自动归 working 版本;旧 mount 绑 working;主 Study 推断 | 中 | 1-2 天 | ✓ |
| **3. 发布状态机** | draft→published 流程、挂载锁版本、跨 Study 引用解锁 | 中 | 3-5 天 | ✓ |
| **4. 撤回流程** | 申请 + 审核 + 紧急下架 + 墓碑 + 引用追踪通知 | 中 | 3-4 天 | ✓ |
| **5. Study 解耦 (大手术)** | `datasets.study_id` 去掉、改名 `recordings`、API 路径迁移 | **高** | 5-7 天 | ⚠️ |
| **6. 清理** | 删别名、删 `recordings_view`、删冗余字段 | 低 | 1-2 天 | ✓ |

!!! info "本路线写于 5-31;6-04『A 重构』已抢先完成其中几项(以 DROP 重建方式)"

## 8. 风险预警

下列坑点在实施时必须注意:

| 风险 | 阶段 | 预防 |
|---|---|---|
| SemVer 校验过严会拒掉历史数据 | Phase 2 回填 | 回填时统一写 `1.0.0`;允许 `0.x.y` 表示 pre-release |
| `content_hash` 计算阻塞主线程 | Phase 3 | 异步任务化,published 状态先标 pending,hash 完成后转 done |
| mount 锁版本后用户体验受阻 | Phase 3 | UI 提示"有新版本"+一键升级 mount,避免感受到额外摩擦 |
| 审计事件覆盖不全 | Phase 3-4 | publish / withdraw / emergency_takedown / mount_upgrade 全覆盖 `audit_events` |
| 跨 Study 引用泄露不该看的数据 | Phase 3 | 必须同时检查 Study visibility (Study 表需加 `visibility` 字段,待补充) |
| `recordings.study_id` 删除时下游查询全部断裂 | Phase 5(改名部分已由 A 重构完成) | 调试期无真实数据、走 DROP 重建,不做"nullable 维持几周"式软迁移;真正要去掉 `study_id` 前,先把所有按 `study_id` 过滤的 service / 路由切到 `dataset_asset_id` / `recording_id` 维度,再一次性重建表 |

## 10. 现状：真实表与 API 端点（6-04 A 重构后）

设计落地后，命名与端点已按下表统一（事实源 `backend/app/models/study.py` 与 `backend/app/routers/datasets.py`）。这一节回答"第 1 节那张矛盾表里的命名并存，现在实际长什么样"。

ORM 类 / 表名 / 中文含义对照：

| ORM 类 | 表名 | 含义 |
|---|---|---|
| `DatasetAsset` | `dataset_assets` | 用户视角的"数据集"（数据资产，独立物理身份） |
| `DatasetVersion` | `dataset_versions` | 数据集的发布版本（承载 draft/published/withdrawn 生命周期） |
| `Recording` | `recordings` | 采集记录：一条 BIDS subject/session/task/run（原 `Dataset`，A 重构改名） |
| `RecordingVersion` | `recording_versions` | 采集记录的上传/重传版本（原 `DatasetUpload`，A 重构改名） |
| `DatasetFile` | `dataset_files` | 文件索引，外键为 `recording_id` + `recording_version_id` + `dataset_version_id` |

API 端点（前缀 → 职责）：

- `/api/v1/dataset-assets`（`asset_router`）：`POST /bootstrap`（唯一创建入口）、`GET ""`、`GET`/`POST /{asset_id}/versions`、`GET /{asset_id}/files`、`GET /{asset_id}/bids-tree`、`POST /{asset_id}/raw-bids-build`、`POST /{asset_id}/canonical-fif-rebuild`、`PATCH /{asset_id}`。
- `/api/v1/studies/{study_id}/recordings`（`recording_router`）：`GET ""`、`GET /{recording_id}/versions`、`GET /{recording_id}/files`、`POST /import`（同步,201）、`POST /import-task`（异步,201）、`GET /{recording_id}/qa`、`POST /{recording_id}/qa/mock-run`、`POST /{recording_id}/qa/review`。
- `/api/v1/studies/{study_id}/datasets`（`router`）：现在只剩挂载——`GET`/`POST /mounts`、`PATCH`/`DELETE /mounts/{mount_id}`。第 1 节提到的"旧两套 API"已收敛：原 `GET /datasets`、`POST /datasets/import`、`/datasets/{id}/qa` 全部迁到 `/recordings/*`，不再存在。
