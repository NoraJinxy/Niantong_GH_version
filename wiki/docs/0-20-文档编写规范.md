## 2. 页面模板

| 模板 | 适用页面 | 主体内容 |
|---|---|---|
| 入口 / 总览 | `index.md`、`*-00-*` | 一句话现状、推荐入口、能力地图、关键流程 |
| 规范 / 治理 | `0-xx` | 规则、编号体系、反面案例；变更记录集中在 9-00（按周汇总），其他页只写当前状态 |
| 网络 / 数据 / 文件 | `2-00`、`3-00`、`4-00` | Mermaid 图、表结构、目录树、配置与约束 |
| 工作流 | `5-00` | NodeSpec、定义、校验、运行、缓存、异步 |
| 前端页面 | `6-00` | 路由、组件、API 客户端、状态、导航 |
| 后端架构 | `7-00` | FastAPI 组织、路由清单、分层契约、执行任务 |
| 功能模块 | `8-00` | M0-M12 状态、依赖、主线、拆分原则 |

## 3. CSS 组件用法

| 组件 | 何时用 | 示例 |
|---|---|---|
| `elys-meta` | 每页页头元信息 | 见本页页头 |
| `elys-badge` | 状态徽章 | `<span class="elys-badge elys-badge--done">已实现</span>` |
| `elys-flow` | Mermaid 图外框 | 流程图、架构图、数据流 |
| `elys-tree` | 文件与目录树 | 研究项目录、前端组件树 |
| `elys-tags` | 技术栈或关键词 | 首页技术栈 |

不要随意发明新组件。需要新增组件时，先记录到 [9-00 更新日志](9-00-更新日志.md)。

## 4. 流程图

| 场景 | 推荐 Mermaid 类型 |
|---|---|
| 架构结构 | `flowchart` |
| 接口调用顺序 | `sequenceDiagram` |
| 状态机 | `stateDiagram-v2` |
| 数据库关系 | `erDiagram` |

不要用 ASCII 框线画流程图，移动端和不同字体下容易错位。

## 5. 文档链接

- `wiki/docs` 内部链接使用相对路径并保留 `.md` 后缀。
- 优先链接到页面本身，不轻易写中文标题锚点。
- 代码路径放进反引号，不写成 Markdown 链接。

## 6. 代码与文档同步

| 改了什么 | 必须同步 |
|---|---|
| 数据库表或字段 | [3-00 数据库设计](3-00-数据库设计总览.md) |
| 研究项目录、导入、版本策略 | [4-00 文件管理](4-00-文件管理总览.md) |
| Study、Pipeline、Execution 或工作流节点 | [5-00 研究管理](5-00-研究管理总览.md) |
| 前端路由或页面 | [6-00 前端页面](6-00-前端页面总览.md) |
| 后端路由或实现 | [7-00 后端架构](7-00-后端架构总览.md) |
| 模块状态 | [8-00 功能模块](8-00-功能模块总览.md) |
| 状态徽章语义 | [0-10 术语与统一约束](0-10-术语与统一约束.md) |

文档页头、会议日志和自动生成分析文档中的 `生成时间` / `更新` 字段统一写到秒级，格式为 `YYYY-MM-DD HH:mm:ss +08:00`。只写日期会让多轮 Codex 修改、会议记录和回归结论难以排序。

## 7. 代码文件头注释

`backend`、`database`、`deploy` 下的脚本和代码文件都应有简短文件头，方便人和大模型快速判断“这个文件干嘛、和哪里有关”。

Python 文件使用模块 docstring，放在文件最顶部、`from __future__` 和 imports 之前：

```python
"""
Purpose: Create the FastAPI application, register routers, configure CORS, and expose health checks.
Related: app/config.py, app/routers/*, wiki/docs/2-50 and wiki/docs/7-10.
"""
```

SQL、shell、PowerShell 和 `.env` 使用对应语言的注释。Shell 脚本必须保留 shebang 第一行：

```bash
#!/bin/bash
# Purpose: Server-side Linux deployment script for the ELYS hybrid entry/compute architecture.
# Related: deploy/deploy_remote.ps1, deploy/profiles/*.env, backend app, frontend build, wiki/docs/2-10.
```

文件头只写职责和关联，不写实现细节；实现细节放函数注释、章节文档或对应 wiki 页面。

## 8. 术语与黑话：可以用，但要铺垫

文档读者既包括开发者和接手的大模型，也包括非全栈背景的项目成员（信号处理 / 脑电研究出身）。专业术语和工程黑话（SSH、反向代理、乐观锁、零复制、幂等等）**可以用、也鼓励用**，但第一次出现时顺带一句大白话点一下它在这里指什么，别甩个词就过去。

| 写法 | 评价 |
|---|---|
| “raw_bids 用零复制（zero-copy，不实际拷文件、只建符号链接指过去）挂载到工作目录” | ✅ 术语 + 一句铺垫 |
| “execution 用乐观锁（optimistic lock，提交时拿版本号比对、对不上就拒绝，免得覆盖别人的改动）控制并发” | ✅ 术语 + 一句铺垫 |
| “raw_bids 走 zero-copy 挂载” | ❌ 甩词不解释 |
| “execution 用 optimistic lock 控制并发” | ❌ 甩词不解释 |

- 铺垫只需一次：同一页里某术语已经解释过，后文再出现可直接用。
- 分清两类读者：本 wiki 是**技术文档**，铺垫是为了让非全栈成员也跟得上；面向平台终端用户（神经科学家 / 医生）的**产品界面**用语是另一套更严的规矩，见 [6-05 信息分级与领域语言](6-05-信息分级与领域语言.md)。

## 9. 反面案例

- 把规划能力写成"已实现"。
- 在多个页面重复维护同一张事实表。
- 把代码路径写成文档链接。
- 页面只有标题，没有事实源、状态和相关入口。
- 新增后端脚本但没有 `Purpose` / `Related` 文件头。
- 在规范 / 总览页里嵌入带日期的变更记录（如 `## 2026-06-04 端点收敛`、行内 `（2026-06-04 改为…）`）。规范 / 总览页只描述**当前状态**；带日期的"什么时候改了什么"统一进 [9-00 更新日志](9-00-更新日志.md)（按周汇总）。页头 `更新` 字段和稳定的决策编号（如 `DEC-2026-0531-A`）不在此列。
