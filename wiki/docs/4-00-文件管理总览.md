# 4-00 文件管理总览

> 本页是 v2 文件管理入口。文件管理的目标不是让用户理解服务器目录，而是让 Dataset、Study、Pipeline、Execution 都能通过数据库索引、权限和追溯关系稳定找到自己的文件。

## 一句话标准

Dataset 目录按 BIDS 管“数据是什么”；Study 目录按 Execution/Artifact 管“做了什么”；数据库管身份、版本、来源、依赖和权限；文件系统只负责可靠存放大文件。

## 1. 核心原则

| 原则 | 说明 |
|---|---|
| 路径不暴露给用户 | 用户不直接操作服务器目录，所有访问都经过 API |
| Raw BIDS 是权威入口 | `raw_bids/` 是标准原始数据视图，不一定物理复制大文件 |
| 原始上传是证据源 | `sourcedata/original_uploads/` 保留用户上传原貌，便于追溯和重新导入 |
| canonical FIF 是工作副本 | 放在 `derivatives/elys-canonical-fif/`，可重建，可缓存，不替代 Raw BIDS |
| 数据库记录身份 | 文件角色、逻辑 BIDS 路径、物理 URI、hash、版本、来源和依赖关系都在数据库 |
| Study 不复制 Dataset | Study 只挂载 Dataset 版本，Execution 输入快照引用具体文件 |
| Execution 输出可清理 | Execution 记录长期保留，大文件按 `retention_status` 管理 |
| 本地优先，兼容对象存储 | MVP 用本地文件系统；字段统一使用 `storage_uri`，未来可迁移 MinIO/S3 |

## 2. 四个对象的文件边界

| 对象 | 文件责任 | 不负责 |
|---|---|---|
| Dataset | `sourcedata`、`raw_bids`、`derivatives/elys-canonical-fif`、基础 QC、事件/通道摘要 | 某个研究问题下的滤波、ICA、epoch、ERP、统计报告 |
| Study | Execution manifest、日志、Artifact、预览、缓存、导出包 | Dataset 原始文件副本 |
| Pipeline | 工作流定义快照可导出，事实源仍在数据库 | 具体输入数据和输出文件 |
| Execution | 冻结输入、参数、软件版本、输出索引和日志 | 修改 Dataset 原始文件 |

Study 通过 `study_dataset_mounts` 挂载 Dataset，通过 `pipeline_execution_inputs` 冻结某次 Execution 实际使用的文件。不要为了一个 Study 复制一份 Dataset。

## 3. 标准目标目录

```text
/mnt/elys_data/
  storage/
    datasets/
      ds-000001/
        versions/
          working/
            sourcedata/
              original_uploads/
            raw_bids/
            derivatives/
              elys-canonical-fif/
            qc/
    studies/
      202605000001/
        executions/
        derived/
        previews/
        temp/
        exports/
        pipeline_snapshots/
    exports/
    trash/
  backups/
  logs/
```

当前代码仍保留 `STUDIES_DIR=/mnt/elys_data/studies` 和 `studies.data_root` 兼容旧上传、旧 Execution 和旧预览；新 Dataset 文件优先写入 `DATASETS_STORAGE_ROOT`，新 Study 输出优先写入 `STUDIES_STORAGE_ROOT`。MVP 不要求立刻搬旧目录，先保证新写入都有 `storage_uri` 和数据库索引。

## 4. Dataset 内部三层

| 层 | 含义 | 是否权威 | 是否可清理 |
|---|---|---|---|
| `sourcedata/original_uploads` | 用户上传原貌，可能是厂商格式、压缩包、杂乱目录 | 证据源 | 原则上不清理 |
| `raw_bids` | 平台整理出的标准 Raw BIDS 入口 | 原始数据权威入口 | 原则上不清理 |
| `derivatives/elys-canonical-fif` | 从 Raw BIDS 生成的 MNE-ready FIF | 工作副本 | 可重建，可按策略清理 |

`raw_bids` 当前就是**纯数据库逻辑视图**：`dataset_files` 里看起来是标准 BIDS（`logical_path`），但 `storage_uri` 直接指向原始上传文件，导入时不复制、不建链接。硬链接 / reflink / `storage_objects` 物理对象引用都是**规划项、尚未实现**（`storage_objects` 表当前不存在），详见 [4-60](4-60-raw_bids视图与零复制策略.md)。

## 7. 仍需注意的边界

1. 导入已有异步路径：`POST /recordings/import-async` 请求内落盘 + Celery worker 后台转 FIF；同步入口 `POST /recordings/import` 继续保留。更彻底的 staged upload（大文件分片直传）仍待后续。
2. `derived_dataset_cleanup` 当前只做数据库逻辑删除，不做物理删除。
3. 调试期不写迁移、不做旧目录回填工具（无 `file_backfill.py`）；升级走 DROP + 重建，新写入直接进新目录并带 `storage_uri` 索引。
4. 本地回归覆盖代码链路，真实 PostgreSQL、Celery worker、MNE 端到端需要 staging 环境继续验证。
